# Правила разработки neiroleptik

Этот файл обязателен для всех участников проекта, ИИ-агентов и субагентов.
Правила действуют на весь репозиторий. Перед работой прочитай этот файл,
относящиеся к задаче спецификации и инструкции затрагиваемых модулей.
В вопросах процесса разработки этот файл имеет приоритет над README и
`.github/CI.md`. Локальные инструкции могут уточнять, но не ослаблять правила.

## 1. Работа с main и pull request

- Все изменения в `main` вносятся только через pull request (PR).
- Запрещены прямой push в `main`, force push и обход процесса ревью.
- Работай в отдельной ветке. Один PR должен содержать одно связное изменение.
- Описание PR должно объяснять, что изменилось, зачем, какие спецификации
  затронуты и как проверена совместимость с актуальным `main`.
- Пока техническая защита ветки недоступна на тарифе GitHub, эти правила
  всё равно обязательны. Возможность нажать Merge не является разрешением.

## 2. Одобрение PR — только человеком

- Финальное одобрение PR даёт только человек. ИИ-агенты, субагенты и боты
  не имеют права выставлять `Approve` или выдавать своё ревью за одобрение.
- Ответственный за финальное одобрение — владелец проекта `@kirit0zxc`.
  Иного ответственного может назначить только владелец проекта.
- Автоматические проверки и ревью агентов предоставляют данные человеку,
  но не заменяют его решение.
- PR нельзя сливать до завершения проверок и явного одобрения человеком
  актуальной версии изменений. Самостоятельное слияние агентом запрещено.
- Автор PR не может выставить `Approve` собственному PR в GitHub. Если PR
  принадлежит ответственному за одобрение, владелец назначает другого человека
  для независимого ревью. До этого PR не готов к слиянию.

## 3. Проверка совместимости перед одобрением

До передачи PR человеку на одобрение проведи автоматическое ревью изменений
в сочетании с актуальной версией `main`:

1. Обнови рабочую ветку относительно актуального `main` и разреши конфликты.
2. Проверь совместимость фронта, бэка, API-контрактов, схем данных,
   миграций, зависимостей и настроек в пределах затронутого изменения.
3. Запусти сборку, проверки типов и относящиеся к изменению автотесты.
   Для изменения общего сценария проверь взаимодействие компонентов вместе.
4. Зафиксируй в PR версии проверенных коммитов `main` и рабочей ветки,
   результаты команд, обнаруженные проблемы и ограничения проверки.

Если после ревью изменился код PR или `main`, прежнее одобрение перестаёт
считаться достаточным. Повтори проверку совместимости для нового сочетания
версий и получи новое явное одобрение человека после её завершения.
Зелёные отдельные сборки
фронта и бэка сами по себе не доказывают, что компоненты работают вместе.
Не выдавай непроведённую проверку или пропущенную задачу CI за успешный тест.

## 4. Три субагента перед каждым push

Перед каждым push рабочей ветки запускай не менее трёх субагентов.
Проверка распространяется и на изменения документации, конфигурации и CI;
её глубина должна соответствовать изменению.

1. **Первый субагент** независимо формулирует гипотезы о возможных ошибках,
   регрессиях и нарушениях контрактов. Проверяет их по коду, спецификациям
   и тестам; приводит доказательства или объясняет, почему гипотеза опровергнута.
2. **Второй субагент** независимо выполняет ту же работу. До сдачи собственных
   первоначальных отчётов первые два субагента не получают отчёты друг друга
   и не обсуждают выводы, чтобы проверки не свелись к повторению одного
   предположения.
3. **Третий субагент** получает оба отчёта, рассматривает все гипотезы,
   включая опровергнутые и неопределённые, и повторно проверяет их основания.
   Он ищет неверные выводы, пропущенные случаи и недостаточные доказательства.

Каждый отчёт должен содержать гипотезу, способ проверки, фактический результат
и статус: подтверждена, опровергнута или требует дополнительной проверки.
Основной агент организует цикл, сопоставляет отчёты, исправляет подтверждённые
проблемы и прикладывает краткие результаты к PR. Рецензенты не меняют файлы,
не делают push и не запускают других субагентов. Существенные непроверенные
гипотезы об ошибках или несовместимости должны быть проверены до push.
Если после проверки изменились файлы, повтори цикл на итоговой версии до push.

Если субагенты или необходимые проверки недоступны, остановись до push,
объясни ограничение человеку и не имитируй завершённое ревью. Только владелец
проекта может явно разрешить исключение из проверки субагентами при их
технической недоступности. Это не разрешает прямой push в `main`, одобрение
агентом или пропуск проверки совместимости.

## 5. Комментарии на русском

- Все новые и изменяемые авторские комментарии, docstring и описания
  назначения модулей, классов и методов пиши на русском языке.
- Сопровождай код содержательными пояснениями назначения, контрактов,
  нетривиальной логики, ограничений и причин архитектурных решений.
- Не заменяй комментарии пересказом каждой очевидной строки. Код должен
  оставаться читаемым за счёт понятных имён и структуры.
- Имена API, идентификаторы, технические термины и обязательные директивы
  инструментов сохраняй в требуемом формате. Не переписывай сторонний
  или автоматически сгенерированный код ради перевода комментариев.

## 6. Классы и методы

- Основную бизнес-логику организуй в классах с понятной ответственностью;
  связанные операции оформляй преимущественно как методы этих классов.
- Не создавай набор разрозненных функций, между которыми неясно распределена
  ответственность. Не превращай один класс в контейнер всей логики проекта.
- Свободные функции оставляй для небольших чистых утилит, точек входа и случаев,
  где этого требует принятая модель фреймворка.
- React-компоненты и hooks пиши в принятом для React стиле. Требование классов
  относится прежде всего к организации бизнес-логики и не требует переводить
  функциональные React-компоненты в классовые.
- Не усложняй простую задачу искусственными классами или лишними абстракциями.

## 7. Спецификации

- До реализации новой функциональности или изменения общего поведения
  опиши требования, интерфейсы, входные и выходные данные, ошибки и критерии
  приёмки в `specs/`. Обновление существующей спецификации предпочтительнее
  создания дублирующего документа.
- Поддерживай спецификации в актуальном состоянии в том же PR, что и код.
- Фиксируй HTTP API в общем OpenAPI-контракте, когда API будет определён.
  Фронт, бэк, заглушки и тесты должны опираться на один согласованный контракт.
- Изменения API, форматов данных и общих сценариев сначала согласуй с человеком,
  ответственным за затронутую интеграцию. Не меняй договорённости молча.

## 8. Автотесты

- Для новой логики и изменения поведения пиши автотесты.
- При исправлении ошибки добавляй регрессионный тест, воспроизводящий её.
- Проверяй основной сценарий, граничные случаи, ошибки и взаимодействие
  компонентов, если изменение затрагивает их связь.
- Тесты должны проверять ожидаемое поведение из спецификаций, а не просто
  повторять реализацию. Не ослабляй проверки ради зелёного CI.
- Для ML используй воспроизводимые проверки, небольшие фикстуры и явно
  заданные допустимые отклонения. Долгое обучение не включай в обычный PR CI.
- Запускай тесты перед push; результаты должны быть доступны в PR и CI.
  Для изменений только документации выбирай соответствующие проверки
  документации и ссылок; бессодержательные тесты не нужны.

## 9. Архитектура и структура файлов

- Раскладывай код по модулям и файлам с понятной ответственностью.
  Не собирай приложение, бизнес-логику, доступ к данным и ML в одном файле.
- Используй основную структуру: `frontend/` для React + TypeScript,
  `backend/` для FastAPI и серверной логики HoneyForge, `specs/` для спецификаций,
  `.github/` для CI и правил совместной работы.
- Внутри компонентов разделяй интерфейсы, бизнес-логику, доступ к данным,
  интеграции и ML-код. Группируй тесты по проверяемым модулям.
- Соблюдай направление зависимостей, избегай циклических импортов и
  дублирования контрактов. Общий код выноси только при реальной необходимости.
- Новые модули, их назначение и связи отражай в `specs/architecture.md`.
  Обновляй документ при изменениях архитектуры в том же PR.
- Не коммить секреты, локальные окружения, артефакты сборки, большие датасеты
  и веса моделей. Для них используй подходящее хранилище и конфигурацию.

## Готовность изменения к слиянию

Изменение готово, когда актуализированы спецификации, выполнены необходимые
автотесты и проверки совместимости, завершён цикл трёх субагентов, CI прошёл
для итоговой версии, а человек одобрил эту версию PR. Если какой-либо пункт
не выполнен, явно укажи это в PR и не считай изменение готовым к слиянию.
