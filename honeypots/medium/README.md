# Образ Medium: доставка и закрепление Cowrie

Статус: **образ не проверялся живым прогоном.** Ни сборка поверх апстрима Cowrie, ни
точка входа, ни сгенерированная конфигурация не запускались с настоящим Docker Engine
и настоящим Cowrie. Проверено только построение команды `docker run` и подготовка
каталогов хоста юнит- и loopback-тестами с подменой контейнерного backend
([specs/runtime-drivers.md](../../specs/runtime-drivers.md), раздел «Не проверено»).

Код ловушки Medium в этом репозитории не разрабатывается: ловушка — апстрим Cowrie.
Здесь лежат только слой образа HoneyForge (точка входа и раскладка каталогов) и
инструкции доставки. Конфигурацию `cowrie.cfg` и `userdb.txt` создаёт драйвер агента
(`agent/runtime/drivers/medium.py`) отдельно для каждого экземпляра.

## 1. Что делает драйвер и чего он не делает

Драйвер **не собирает и не скачивает образы**: `docker run` выполняется с
`--pull never`. Образ `honeyforge-medium` должен существовать на runtime-хосте до
первой команды `start` уровня medium. Исполнитель включает уровень medium только при
заданном `--medium-state-root`; без него команда medium получает failed ACK
`UNSUPPORTED_COMMAND` без обращения к Docker.

Драйвер передаёт контейнеру ровно два аргумента:

```text
--config-dir=/honeyforge/conf     только для чтения: cowrie.cfg, userdb.txt
--state-dir=/honeyforge/state     записываемый: log, lib/tty, lib/downloads, run, keys
```

Профиль центра, имя хоста, баннер SSH и учётные данные в аргументы не попадают:
аргументы контейнера видны в `docker inspect` и в списке процессов хоста. Пароли
существуют только в файле `userdb.txt` с правами 0600, смонтированном только для
чтения.

## 2. Сборка и закрепление

Сборка выполняется заранее на машине сборки, из корня репозитория (контекст сборки —
корень, потому что `COPY` берёт файл по пути `honeypots/medium/entrypoint.sh`):

```bash
docker build --file honeypots/medium/Dockerfile --tag honeyforge-medium:local .
```

Апстрим задаётся аргументом сборки и закрепляется digest при публикации:

```bash
docker build --file honeypots/medium/Dockerfile \
  --build-arg COWRIE_IMAGE=cowrie/cowrie:3.1.1@sha256:ЗАКРЕПЛЁННЫЙ_DIGEST \
  --tag honeyforge-medium:local .
```

Кандидат на закрепление (релиз и официальный образ) согласован в
[infra/runtime/README.md](../../infra/runtime/README.md), раздел 3; конкретный digest
подставляется после живого spike. `latest` и незакреплённая ветка не используются.

## 3. Доставка на runtime-хост

Публикация в реестр проекта остаётся отдельным этапом, как и для образа Low. До неё
образ переносится экспортом и импортом, после чего проверяется его наличие:

```bash
docker image inspect honeyforge-medium:local --format '{{.Id}}'
```

Тег, который ожидает исполнитель, задаётся аргументом `--medium-image`; значение по
умолчанию — `honeyforge-medium:local`.

## 4. Пользователь и права

Контейнер запускается непривилегированным пользователем. `uid:gid` в образе,
`--medium-user` исполнителя и владелец каталогов экземпляра на хосте должны совпадать,
иначе Cowrie не сможет писать в смонтированное состояние. Значение по умолчанию
`1000:1000` соответствует пользователю апстрим-образа Cowrie и **требует проверки** на
закреплённом релизе: при расхождении задайте `--medium-user` и пересоберите образ с тем
же `uid:gid`.

Передача владения каталогами экземпляра требует у агента root или `CAP_CHOWN`; доступ к
сокету Docker и так равносилен root на хосте. На платформе без `os.chown` (разработка на
Windows) шаг пропускается, и такая подготовка не проверяет POSIX-права.

## 5. Что нужно подтвердить живым прогоном

Перед объявлением Medium работающим нужно проверить на закреплённом релизе Cowrie:

1. Способ указать Cowrie домашний каталог и путь поиска `etc/cowrie.cfg`
   (`COWRIE_HOME` и рабочий каталог в `entrypoint.sh`).
2. Флаг запуска без демонизации (`cowrie start -n`) и то, что процесс остаётся
   основным процессом контейнера.
3. Имена параметров `cowrie.cfg`, которые формирует драйвер: пути журнала, состояния,
   TTY и ключей хоста, `auth_class`, `listen_endpoints`, `version`, отключение telnet,
   проброса портов и SFTP.
4. Расположение `userdb.txt` и то, что Cowrie принимает пароль как литерал.
5. Что первый запуск создаёт ключи хоста в `keys/` смонтированного состояния при
   `--read-only` корне, и что `/tmp` в tmpfs достаточно.
6. Что `cowrie.json` и TTY-записи появляются в каталоге экземпляра на хосте.

Формат, в котором сборщик читает журнал Cowrie, с участником 4 ещё не согласован:
драйвер только создаёт каталог экземпляра и не объявляет контракт телеметрии.
