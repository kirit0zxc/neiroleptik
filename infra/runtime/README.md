# Подготовка runtime и Cowrie spike D1

Статус: **pending**. Linux/KVM-хоста пока нет. Этот документ описывает будущий
живой прогон; локальные тесты Python не подтверждают работу KVM, Cowrie,
сетевой изоляции или интеграции с центром. Сроки остаются D1-D5, 30 часов.

## 1. Статический preflight

На предполагаемом Linux runtime-хосте из корня репозитория:

```bash
python3 -m infra.vm.preflight > preflight.json
```

CLI возвращает 0 только при PASS всех статических предпосылок. Ненулевой код
означает FAIL либо UNKNOWN. Результат включает отдельные `manual_checks` для
создания VM, сетевых прав и изоляции; здесь они всегда UNKNOWN. Даже успешная
статика не разрешает объявить High готовым. На Windows проверки Linux
пропускаются и диагностические Linux-команды не запускаются.

Проверяются текущий пользователь, символьный `/dev/kvm` и права чтения/записи,
версии qemu-img/virsh/ip и nft либо iptables, системное подключение libvirt.
Команды не меняют состояние; их общий stdout/stderr ограничен 8192 байтами,
ожидание каждой команды - 5 секундами. Для диагностики можно изменить пределы
через `--timeout` (до 30 секунд) и `--output-limit` (до 65536 байт).

## 2. Подготовить отдельный стенд

До запуска гостя согласовать с владельцем хоста разрешённые действия,
поддержку KVM у провайдера и таблицу сетевых направлений. Затем на предназначенном
для теста хосте вручную проверить создание и запуск одной VM, сетевые права
и отрицательные подключения. Результаты записать отдельно от статического JSON.
Этот репозиторий пока не создаёт VM и не применяет firewall-правила.

Для High использовать один подготовленный Linux-образ, один qcow2 overlay
и Cowrie **simple backend**. Отдельный доверенный менеджер VM управляет libvirt;
Cowrie не получает libvirt socket, Docker socket или токен центра. Образ,
размеры ресурсов, адрес гостя и порт SSH зафиксировать в протоколе стенда.

Перед подключением клиента подтвердить: proxy может обращаться к SSH гостя,
а guest не может инициировать соединения в интернет, к центру, mgmt, хосту,
metadata и другим ловушкам. Проверить IPv4, IPv6 и мостовой трафик. Isolated
bridge сам по себе не является доказательством. Для первого spike вход
ограничить отдельным тестовым клиентом. До успешной проверки держать вход закрытым.

## 3. Отдельно запустить Cowrie shell и proxy

Выбрать явную версию-кандидат Cowrie, совместимую с Python 3.12, по официальной
инструкции установки. Не использовать `latest` или незакреплённую ветку main.
Создать отдельные state-каталоги/окружения для Medium и High, отдельные порты и
проверочные credentials. Credentials теста не должны совпадать с доступом к хосту.

В каждом state-каталоге выполнить документированный `cowrie init`, затем
отредактировать свой `etc/cowrie.cfg` и `etc/userdb.txt`. Названия параметров
проверить для выбранной версии. Для Medium:

```ini
[honeypot]
backend = shell

[ssh]
forwarding = false
forward_redirect = false
forward_tunnel = false
sftp_enabled = true

[telnet]
enabled = false
```

Для High меняется backend и задаётся реальный адрес подготовленной VM:

```ini
[honeypot]
backend = proxy

[proxy]
backend = simple
backend_ssh_host = АДРЕС_ИЗОЛИРОВАННОЙ_VM
backend_ssh_port = 22
backend_user = ТЕСТОВЫЙ_ПОЛЬЗОВАТЕЛЬ_VM
backend_pass = ОТДЕЛЬНЫЙ_ТЕСТОВЫЙ_ПАРОЛЬ_VM

[ssh]
forwarding = false
forward_redirect = false
forward_tunnel = false
sftp_enabled = true

[telnet]
enabled = false
```

Это фрагменты, а не готовые конфигурации: подставить согласованные значения,
явно задать `ssh.listen_endpoints` с правильным адресом и отдельным портом
каждого экземпляра. Проверить JSON-логирование и TTY-запись в выбранной версии.
Логи `var/log/cowrie/cowrie.json`, TTY `var/lib/cowrie/tty/` и загрузки
`var/lib/cowrie/downloads/` должны сохраняться на хосте вне guest и его overlay.
Доступ к этим данным дать только сборщику и оператору; секреты не коммитить.

Запустить каждый экземпляр через `cowrie start` в его state-каталоге. Записать
реальные сообщения запуска и адрес/порт. Для Medium получить реальный логин,
команду, JSON и TTY; передать участнику 4 пример с явно указанным источником.

## 4. Проверить PTY и exec на реальной VM

Ниже переменные `HIGH_HOST`, `HIGH_PORT`, `DEMO_USER` задаются оператором для
своего стенда. Сначала подключиться отдельным тестовым клиентом:

```bash
ssh -tt -p "$HIGH_PORT" "$DEMO_USER@$HIGH_HOST"
```

В сессии выполнить следующие действия и сохранить внешнюю запись:

1. `uname -s` и `id`: проверить реальную ОС и пользователя подготовленной VM.
2. `printf 'Проверка Unicode: ёж\n'`: увидеть тот же текст в терминале и replay.
3. `stty size`: изменить размер окна клиента, повторить и сравнить значения.
4. `sleep 30`, затем Ctrl-C: процесс прерывается, shell принимает новую команду.
5. Создать `/tmp/honeyforge-marker` и убедиться в наличии файла.

Отдельно проверить exec без PTY:

```bash
ssh -T -p "$HIGH_PORT" "$DEMO_USER@$HIGH_HOST" 'printf "exec-ok\n"; uname -s; exit 7'
```

Сразу зафиксировать код завершения клиента: ожидается 7. Внешний журнал/запись
должен содержать контрольный вывод exec и позволять отличить эту сессию от PTY.
Проиграть TTY штатным `playlog` выбранной версии Cowrie и проверить Unicode,
вывод и отсутствие смешивания сессий. Конкретную поддержку resize и кода exec
засчитать только по фактическому тесту. SSH replay не является аудитом всех
процессов и файловых операций внутри ОС.

## 5. SFTP: две копии в D1, третья в D3

На тестовом Linux-клиенте создать безопасную бинарную фикстуру размером 1 МиБ:

```bash
python3 -c "from pathlib import Path; Path('sftp-fixture.bin').write_bytes(bytes(range(256)) * 4096)"
sha256sum sftp-fixture.bin
sftp -P "$HIGH_PORT" "$DEMO_USER@$HIGH_HOST"
```

В SFTP последовательно выполнить `put sftp-fixture.bin /tmp/sftp-fixture.bin`,
дождаться завершения и корректно закрыть SFTP. D1 засчитывается после сравнения
двух копий: оригинала клиента и файла, реально сохранённого Cowrie **снаружи VM**.
Наличие файла только внутри VM не достаточно. Проверить размер и SHA-256,
а также связь события `cowrie.session.file_upload` с сессией. Путь сохранения
искать по фактическому событию, не по предположению о названии файла.

На D3 после интеграции участника 4 скачать артефакт из центра штатным интерфейсом;
проверить его SHA-256 и размер относительно оригинала и внешней копии runtime.
До этого третья копия имеет статус pending. Общий HTTP API здесь не задаётся.

Дополнительно оборвать тестовую загрузку и записать наблюдаемое поведение:
есть ли частичный артефакт и как он помечен. Не объявлять прерванную загрузку
полностью сохранённой. Параллельные файлы, произвольные размеры и legacy SCP
не считаются поддержанными по одному успешному SFTP-тесту. Для release заранее
согласовать лимиты размера/квоты и отказ при их превышении.

## 6. Закрепить результат и передать команде

После успешного spike закрепить точный релиз Cowrie и, при использовании
контейнера, digest. Сохранить версии Python, SSH/SFTP-клиента, QEMU/libvirt,
SHA-256 базового образа, конфигурации без секретов, дату и результаты команд.
Не ставить PASS на основании документации стороннего продукта.

| Проверка | Текущий результат | Доказательство после прогона |
| --- | --- | --- |
| Linux/KVM и подключение libvirt | pending | preflight.json с хоста |
| Создание VM и сетевые права | pending | отдельный живой протокол |
| Отрицательные сетевые проверки | pending | направления, IPv4/IPv6, контрольные endpoints |
| Medium login/command/JSON/TTY | pending | реальный журнал и replay |
| High PTY/Unicode/resize/Ctrl-C/exec | pending | команды, код exec, replay |
| D1 SFTP: оригинал и внешняя копия | pending | одинаковые размер и SHA-256 |
| D3 SFTP: скачивание из центра | pending | SHA-256 третьей копии и связь с instance/session |
| Выбранный релиз/digest | pending | закрепляется после фактического spike |

Следующие рубежи D2-D4 требуют lifecycle, TTL, локального seal и reset. Закрытие
входа должно прекращать также существующие соединения. Старый overlay нельзя
удалять до подтверждённого локального сохранения доказательств; недоступность
центра не отменяет этот барьер. Здесь эти операции ещё не реализованы.

Первичные инструкции: [установка Cowrie](https://docs.cowrie.org/en/stable/INSTALL.html),
[proxy](https://docs.cowrie.org/en/stable/PROXY.html),
[конфигурация](https://github.com/cowrie/cowrie/blob/main/src/cowrie/data/etc/cowrie.cfg.dist),
[изоляция libvirt](https://libvirt.org/formatnetwork.html#isolated-network-config).
Проверять документацию и настройки именно закреплённого релиза; ссылки на stable/main
могут со временем измениться.
