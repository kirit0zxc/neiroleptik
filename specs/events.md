# Телеметрия D1: Event v1 и локальная очередь

Основание: `HoneyForge-plan.html` и `HoneyForge-4-Telemetry.html`, 09.10.2026.
Статус: локальная реализация первого шага D1. Схема Event следует общему плану;
формат исходного Low JSONL ниже — предложение участнику 3, ещё не подтверждённое
реальными журналами. Это не отчёт о завершении общего D1.

## Граница первого изменения

Реализуются валидатор Event v1, JSON Schema, фикстуры event/batch/ACK/replay,
Low adapter, SQLite WAL spool и локальный долговечный карантин окончательных
отказов. Добавлен HTTP sender существующей очереди с backoff и проверкой ACK.
PostgreSQL ingest, outbox и WS следуют следующим шагом. Готовая инфраструктура
участника 2 уже есть в backend/src/honeyforge: db.py, api/dependencies.py.
Новые таблицы и instance/session согласуются с владельцами. Реальный журнал Low
и экран frontend нужны для совместной приёмки.

## Event v1

Обязательные поля: `schema_version=1`, UUID `event_id`, UUID `agent_id`,
`deployment_id`, `instance_id`, `source_seq` в пределах 0..9007199254740991, `occurred_at` с часовым поясом,
`type`, `source={ip,port}`, `service={protocol,port}`, `data`, `artifact_ids`,
`profile_revision>=1`. `session_id` — UUID или null, поле необязательно на входе. Время нормализуется в UTC.
`received_at` и `stream_seq` назначает центр, агент их присылать не должен.
Неизвестные поля запрещены. Boolean не считается integer. NaN/Infinity запрещены.
`data` — JSON-объект максимум 8192 байта в компактном UTF-8. Превышение
не обрезается молча: адаптер возвращает ошибку без продвижения offset.

Типы: `connection.opened`, `auth.attempt`, `session.command`, `session.output`,
`http.request`, `artifact.observed`, `token.triggered`, `session.closed`,
`runtime.state`. IP валидируется как IPv4/IPv6, source.port 0..65535, service.port 1..65535, protocol: tcp/http/ssh.
`source.ip` принимается только строкой; числа, boolean и другие типы отклоняются.

Batch: `batch_id` (UUID), `schema_version=1`, `events`; максимум 100 событий
и 256 КиБ всего компактного UTF-8 JSON. Абсолютный request cap 2 МиБ относится
к будущему HTTP ingress. ACK: `batch_id`, `accepted_ids`, `rejected`.
ACK после commit PostgreSQL; принятые дубли включаются в `accepted_ids`.
Одинаковый `(agent_id,event_id)` с другим содержимым — ошибка целостности.

## Low adapter и позиция источника

Предлагаемая строка Low JSONL: `occurred_at`, `type`, `source`, `service`,
`data`, опциональные `session_id`, `artifact_ids`. Идентичность агента,
deployment/instance/revision поступает из доверенной конфигурации runtime.
`source_id` — стабильный ID конкретного поколения журнала, а не только путь.
Участник 3 сохраняет его при рестарте и меняет при ротации/обнулении файла.

Позиция — байтовый offset, `next_offset` указывает за полной строкой с LF.
Адаптер принимает только одну завершённую UTF-8 JSON-строку. Не читает
незавершённый хвост. `source_seq` равен начальному байтовому offset в данном
поколении источника. UUIDv5 детерминирован по agent/deployment/instance,
source_id и начальному offset; повтор чтения даёт прежний ID.
Повторяющиеся JSON-ключи на любой глубине, включая одинаковые значения и
эквивалентные ключи с escape-последовательностями, отклоняются до создания записи.

`SpoolRepository.append(record)` сохраняет событие и next_offset одной
транзакцией. Начало записи должно равняться текущему checkpoint, иначе
`OffsetConflict`; транзакция не меняет ни очередь, ни позицию. Первый offset=0.
Один spool принадлежит одному агенту; попытка другого агента отклоняется.
До записи проверяется, что весь Event помещается в одиночный batch вместе
с конвертом в пределах 256 КиБ. Превышение возвращает ошибку без изменения
pending и checkpoint; проверка действует для публичного append, независимо
от ограничения исходной строки Low в 64 КиБ.
Повторная доставка читает неизменный JSON. `acknowledge(batch, ack)` применяет
только полный корректный ответ: accepted удаляются, временные отказы остаются,
окончательные атомарно переносятся в карантин. Подробный контракт ниже заменяет
прежнее правило частичного ACK. HTTP retry/backoff описан в разделе доставки ниже.

## Критерии проверки первого шага

- Валидатор отвергает некорректные IP, время без timezone, лишние поля,
  превышение payload и некорректные типы данных.
- Пример Event совпадает с опубликованной JSON Schema.
- 100 строк Low сохраняются offline; после открытия SQLite заново все 100
  ID и payload совпадают, checkpoint сохранён.
- Повтор чтения не создаёт новый ID; конфликт позиции не теряет данные.
- Без ACK события остаются; неполный ACK не меняет очередь и карантин.
- ACK с чужим batch/ID ничего не удаляет.
- Пачки соблюдают ограничения на количество и полный размер JSON.

## ACK и карантин после согласования с бэкендом

Последний ответ сохранён в work/telemetry-handoff/04_CONTEXT.md; он заменяет прежние противоречащие

## Область работы

Реализовать безопасное применение batch ACK к SQLite spool. Сохранить текущие
Event v1, атомарную запись event+offset, устойчивость после рестарта и лимиты
100 событий/256 КиБ. Один spool принадлежит одному агенту. События в очереди
уже прошли агентский валидатор; схема приёма недоверенного HTTP batch на сервере
проектируется отдельно и не должна отвергать все хорошие элементы из-за одного
плохого. Нельзя использовать строгий исходящий Batch как единственный входной
серверный валидатор для будущего частичного приёма.

## Формат ответа

ACK содержит batch_id UUID, accepted_ids массив UUID, rejected массив объектов.
Каждый rejected содержит обязательные index (строгий integer >=0), event_id
(UUID или null), code и retryable (строгий boolean). Неизвестные поля запрещены.
index — исходная нулевая позиция в events отправленного batch, обязателен даже
при валидном event_id. Каждый элемент получает ровно один результат:
accepted либо rejected (временный или окончательный). В корректном исходящем
batch агента event_id уникальны, поэтому accepted_ids однозначно задают позиции.

Коды проекта:

| code | retryable | Смысл |
| --- | --- | --- |
| INVALID_EVENT | false | Элемент не соответствует входному контракту |
| EVENT_ID_CONFLICT | false | Такой agent_id/event_id уже есть с другим содержимым |
| DEPLOYMENT_MISMATCH | false | Deployment не принадлежит авторизованному агенту |
| INSTANCE_NOT_REGISTERED | true | Регистрация экземпляра пока не видна центру |
| TEMPORARILY_UNAVAILABLE | true | Временный отказ обработки элемента |

Неизвестный код или несовпадение code/retryable означает неподдерживаемый ACK:
сохранить всю очередь, вернуть наблюдаемую ошибку. Переклассификация unknown
instance зависит от итоговой договорённости backend/runtime; сейчас это
предложение, без автоматического удаления и без бесконечного быстрого retry.

event_id=null допустим только для INVALID_EVENT: сервер не смог доверенно
разобрать ID, но знает index. Агент применяет отказ к исходному событию по index.
Для непустого event_id требуется точное совпадение с событием по этому index.

Пример ACK на batch из трёх событий:

```json
{
  "batch_id": "00000000-0000-0000-0000-00000000000a",
  "accepted_ids": ["00000000-0000-4000-8000-000000000011"],
  "rejected": [
    {"index": 1, "event_id": "00000000-0000-4000-8000-000000000012", "code": "EVENT_ID_CONFLICT", "retryable": false},
    {"index": 2, "event_id": "00000000-0000-4000-8000-000000000013", "code": "TEMPORARILY_UNAVAILABLE", "retryable": true}
  ]
}
```

## Проверка до изменения очереди

1. Повторно валидировать модели batch и ACK, включая вложенные изменяемые поля.
2. Проверить batch_id и принадлежность batch агенту spool.
   `next_batch()` до возврата фиксирует в SQLite неизменяемые канонические
   байты всей выдаваемой пачки, связанные с batch_id: состав, порядок и payload.
   `acknowledge()` требует существующую привязку и точное совпадение переданной
   модели с этим снимком; проверки полноты и index выполняются по сохранённой
   пачке. Изменение списка events (удаление, добавление, перестановка, подмена)
   или payload, а также новая модель с тем же batch_id и иным составом
   отклоняются целиком. Нельзя регистрировать снимок впервые при получении ACK.
   Снимки сохраняются после применения ACK и рестарта для безопасных повторных
   и поздних ответов. Автоматическая очистка снимков пока не предусмотрена.
   Пачка, созданная вручную или выданная старой версией без снимка, не может
   подтверждаться: pending сохраняется, нужно получить новую next_batch().
3. accepted_ids не повторяются и принадлежат batch. Индексы rejected уникальны
   и входят в диапазон. Непустые rejected.event_id не повторяются.
4. Разрешить каждый rejected в конкретный исходный event. Пересечение с
   accepted_ids запрещено, в том числе когда rejected.event_id=null.
5. Проверить полное покрытие исходных позиций: каждая встречается ровно один раз
   среди accepted и rejected. Пустой или частичный ACK на непустой batch ошибочен.
6. Для существующей pending-записи проверить, что canonical payload исходного
   batch совпадает с сохранённым payload. Чужой/изменённый снимок с тем же ID
   не может удалить очередь. Весь ACK при таком конфликте отклоняется.

Если хотя бы один результат отсутствует, сохранить всю очередь и весь карантин
без изменений. Ошибка любой проверки не допускает изменений даже для других,
корректных accepted_ids этого ACK. Проверка полноты относится к исходному batch,
даже если часть его событий уже удалена ранее применённым ACK.
Ошибка описывает причину без вывода всего payload или секретов.

## Одна транзакция применения

- Accepted: удалить соответствующую pending-запись.
- Retryable: оставить событие и его порядок неизменными.
- Permanent: устойчиво сохранить исходный канонический Event, batch_id,
  code, index и rejected_at UTC в карантин, затем удалить из pending.
- Accepted и permanent после успешного локального применения ACK больше не
  включаются в next_batch, включая после рестарта. Если серверный commit прошёл,
  но ACK не дошёл или агент упал до локального commit, повтор неизбежен и должен
  безопасно подтверждаться центром. Без полученного и сохранённого ACK агент
  не может знать, что сервер уже принял событие.
- Переносы и удаления одного ACK выполняются одной транзакцией. Ошибка БД
  откатывает все действия ACK. Checkpoints источников ACK не меняет.
- Повтор того же ACK безопасен. В карантине максимум одна запись на event_id
  этого spool; повтор не меняет первичную причину, время или payload.
- Уже отсутствующий pending не восстанавливать. Поздний ACK не удаляет
  карантин и не перезаписывает его. При отсутствии pending не создавать
  карантин из присланного batch: источником доказательств служит локальная запись.

Новые SQLite-структуры добавлять без потери существующих pending/checkpoints
и metadata владельца. Автоочистки карантина и requeue в этом шаге нет.
Чтение pending и фиксация снимка `next_batch()` выполняются одной транзакцией;
ошибка сохранения снимка не выдаёт пачку и не меняет очередь/checkpoint.

Регрессионные критерии: после выдачи [A,B] удаление B из списка не позволяет
применить ACK только для A; после выдачи [A] подмена A другим pending B не
позволяет перенести B в карантин через index=0/event_id=null. В обоих случаях
pending, карантин и checkpoints неизменны. Перестановка, добавление события,
подмена модели с тем же ID и эти сценарии после рестарта также отклоняются.

## Публичный API для тестов

Сохранить SpoolRepository.append/checkpoint/count/next_batch/close.
acknowledge(batch, ack) по-прежнему возвращает integer: число pending-записей,
удалённых именно как accepted. Перенесённые в карантин сюда не входят.

Добавить quarantine_count() -> int и list_quarantine(limit=100) -> list.
Элементы list_quarantine имеют атрибуты event: Event, code: str, batch_id: UUID,
index: int, rejected_at: datetime с timezone UTC. limit — строгий int 1..500;
по умолчанию 100, порядок — порядок первого помещения в карантин. Возвращаемые
объекты не предоставляют изменяемого доступа к хранилищу. Внутренняя схема таблиц
и класс записи остаются выбором исполнителя. Семантика count() — только pending.

## Точная нормализация для проверки конфликтов

Сравнивается входное событие до маскирования, удаления паролей и форматирования
для UI. Редактирование UI не меняет оригинал и его отпечаток. Алгоритм v1:

1. Разобрать JSON без NaN/Infinity и без повторяющихся ключей объектов на любом
   уровне. Повтор ключа отклоняется как неоднозначный ввод, а не last-key-wins.
   Проверить входную модель Event; неизвестные/серверные поля на входе запрещены.
2. Сформировать объект только из полей входного Event: schema_version, event_id,
   agent_id, deployment_id, instance_id, session_id, source_seq, occurred_at,
   type, source, service, data, artifact_ids, profile_revision. Отсутствующий
   schema_version принимает 1, отсутствующий session_id — null. Другие обязательные
   поля нельзя придумывать. UUID записываются lowercase с дефисами; IP — стандартным
   строковым представлением IPv4 или сжатым IPv6 без изменения адреса.
3. occurred_at преобразуется в UTC. Использовать ровно формат Event.model_dump(mode="json")
   закреплённого Pydantic: Z, без дробной части для нулевых микросекунд, шесть цифр
   для ненулевых. Вход с точностью выше микросекунд отклонять, а не терять точность
   молча. data, строки и массивы не нормализуются по смыслу; Unicode NFC не применять.
4. Сериализовать через json.dumps(value, ensure_ascii=False, sort_keys=True,
   separators=(",", ":"), allow_nan=False), затем UTF-8. Ключи всех JSON-объектов
   сортируются рекурсивно в порядке Unicode code points. Порядок массивов, включая
   artifact_ids, сохраняется. Пробелы между токенами и выбор JSON escape во входе
   не влияют на результат. JSON integer 1 и float 1.0 в data различаются; 0.0 и
   -0.0 различаются согласно этой сериализации. Это явное правило v1, не JCS.
5. Исключить batch_id, received_at, stream_seq и другие серверные метаданные:
   они не входят в объект пункта 2. Не исключать agent_id и другие входные поля.
   SHA-256 канонических байтов допустим как индекс/быстрая проверка; для равенства
   при одинаковом ID окончательно сравнить сами канонические байты. Нормализованный
   оригинал хранить неизменным и отдельно от маскированного представления.

Границы чисел — поведение закреплённого Python JSON/Pydantic v1; не пытаться
незаметно воспроизвести алгоритм через JavaScript Number или jsonb::text. При смене
алгоритма версионировать нормализацию и сохранить возможность сравнить старую запись.
Тесты локальной канонизации и отказа от потери точности времени выполняются
в tests/telemetry. Duplicate keys и проверку исходных JSON-байтов нужно
дополнительно покрыть на будущей границе HTTP-приёма; текущий шаг её не добавляет.

## Авторизация и следующий серверный этап

Не реализуется текущим заданием. Сервер получает узел/agent_id из проверенного
Bearer-токена, проверяет его отзыв и не доверяет идентичности из JSON. Переданный
agent_id должен совпасть с установленным сервером; несовпадение отклоняется,
а не молча заменяется. Deployment ищется с привязкой к этому узлу; revision
проверяется по deployment. instance_id проверяется по lifecycle, согласованному
с Данилом: одного корректного UUID недостаточно. Временную политику INSTANCE_NOT_REGISTERED
нельзя превращать в обход проверки принадлежности. Каждый элемент нормализуется отдельно.
Дедупликация — по (agent_id,event_id); сравнение нормализованного неизменяемого
Event без batch_id, received_at и stream_seq. Одинаковый повтор подтверждается;
конфликт содержания не перезаписывает оригинал и не создаёт outbox.

Уникальность events(agent_id,event_id) и публикации конкретного события задаётся
UNIQUE/PRIMARY KEY в PostgreSQL, а не только предварительным SELECT. В publication
нужна уникальная ссылка на внутренний event PK либо полную пару agent_id/event_id;
одного event_id недостаточно. Для event также не создавать повторный outbox.
Конкурентную вставку разрешать через ограничения и повторное чтение committed
оригинала: одинаковый payload подтверждается, другой получает EVENT_ID_CONFLICT.

Новое событие и outbox сохраняются атомарно; ACK после commit. Потеря ответа
после commit безопасна. При ошибке commit нет положительного ACK. Один worker
устойчиво публикует committed outbox в журнал; публикация и отметка outbox
обработанным атомарны, уникальная ссылка event предотвращает повтор публикации.
Сбой до commit публикации оставляет outbox пригодным для повтора и не выпускает
событие в WS. Сбой после commit оставляет одну публикацию и обработанный outbox;
после рестарта вторую публикацию не создавать. WS отправляет только committed
строку журнала. Повтор передачи одной stream_seq по сети возможен при reconnect,
но повторной записи публикации в БД быть не должно.
Выдаваемые stream_seq монотонны в видимом committed журнале; watermark — его
последняя доступная позиция. WS/REST читают этот журнал, а не автоинкремент events.

Ошибки всего запроса: timeout/обрыв/429/5xx сохраняют данные для повторной
отправки с backoff; 401/403 сохраняют их и сигнализируют проблему доступа.
400/422 конверта не разрешают удалять отдельные события без валидного ACK.
HTTP sender/backoff реализован отдельно от ещё не готового серверного ingress.

### Обязательные интеграционные тесты следующего серверного этапа

Эти проверки спроектированы, но пока не выполняются локальными SQLite-тестами.
Нужны реальные соединения и транзакции PostgreSQL в отдельной honeyforge_test.

| Сценарий | Критерий приёмки |
| --- | --- |
| Commit event+outbox прошёл, ACK потерян | Оборвать ответ после commit и повторить batch; один event/outbox, повтор accepted, исходные received_at и payload неизменны |
| Конфликт среди хороших элементов | Заранее сохранить A, отправить [новый B, изменённый A, новый C]; B/C accepted, A rejected с index=1/EVENT_ID_CONFLICT, оригинал A и публикации B/C сохранены |
| Конкурентные одинаковые повторы | Два соединения/транзакции стартуют через барьер; оба accepted, UNIQUE оставляет один event/outbox/publication |
| Конкурентные разные payload одного ID | Один оригинал, второй ответ EVENT_ID_CONFLICT; нет перезаписи и нового outbox |
| Ошибка ingest commit | Нет положительного ACK и частичной записи event/outbox |
| Worker упал до commit публикации | Прервать после INSERT publication, до commit; outbox не processed, WS ничего не выпустил, после восстановления одна committed публикация |
| Worker упал после commit публикации | Прервать после commit publication+processed, до сетевой отправки; после рестарта нет второй публикации, REST/WS используют прежний stream_seq |
| Bearer identity и принадлежность | Токен A с agent_id/deployment/instance B не даёт вставку; проверка UUID не заменяет lifecycle |
| Разные агенты с одинаковым event_id | Разные разрешённые события; outbox/publication уникальны по внутреннему event PK или полной паре agent_id/event_id |
| Обратный порядок ingest commit и WS hello/REST | Единый committed журнал, watermark не пропускает поздний commit, нет дыр между REST-догрузкой и live |
| Канонизация до UI | Перестановка ключей — повтор; изменение массива или исходного пароля при одинаковом UI — конфликт |
| Сырые HTTP JSON-байты | Duplicate keys/NaN/Infinity и точность выше микросекунд отвергаются явно; хорошие элементы получают свои результаты |

## HTTP-доставка существующей очереди

Отправитель использует существующие Batch/ACK без изменения формата. Адрес
приёма задаётся конфигурацией; серверный `/agent/v1/events` разрабатывается отдельно.
`TelemetrySender.step()` выполняет не более одного POST, возвращая наблюдаемый
результат и задержку до следующей попытки. Вызывающий цикл соблюдает задержку;
сам sender также проверяет монотонный deadline и не отправляет раньше срока.
Пустая очередь не вызывает HTTP. Один sender и spool используются одним потоком.

- Отправляется неизменный снимок batch с Bearer token и Content-Type application/json.
  При сетевом сбое, 429/5xx или некорректном ACK следующий запрос повторяет те же
  байты и batch_id. Рестарт может создать новый batch_id, но event_id и payload
  сохраняются в SQLite; сервер обязан дедуплицировать события.
- Только HTTP 200 с полным корректным ACK допускает применение к spool.
  Duplicate JSON keys, NaN/Infinity, неизвестные поля/коды, лишние ID, неверный
  batch_id и неполное покрытие отклоняются без изменения pending/карантина.
  Ответ ограничен 256 КиБ; тело ошибки не попадает в диагностику.
- Временные отказы внутри ACK остаются в pending и повторяются с backoff;
  accepted удаляются, окончательные отказы переносятся в карантин по существующему
  атомарному контракту. После применения ACK новая пачка содержит только pending.
- Экспоненциальная пауза: база 1 с, предел 60 с, jitter в диапазоне
  [половина текущей паузы, полная пауза]. Успешный ACK без временных отказов
  сбрасывает счётчик. Retry-After для 429/503 учитывается как минимальная пауза
  (секунды либо HTTP-date); максимум ожидания по этому заголовку — 24 часа.
- 401/403 и остальные неожиданные HTTP-статусы, включая 3xx и 400/422,
  приостанавливают sender до явного `resume()` после исправления конфигурации.
  События сохраняются. Неизвестный или повреждённый ACK вызывает видимую ошибку
  протокола и ограниченные по частоте повторы, а не удаление очереди.
- Транспорт не следует редиректам, не использует proxy из окружения; TLS
  проверяется стандартным доверенным хранилищем. HTTP разрешён только для
  localhost/loopback dev-стенда. Credentials в URL, fragment и query запрещены.
  Таймаут задаётся конфигурацией и ограничивает общий сетевой обмен: подключение,
  TLS, отправку, заголовки и тело ACK, включая chunked framing. Таймер разрывает
  соединение через отдельный дескриптор уже подключённого сокета, сохраняемый
  до завершения чтения HTTPResponse; фоновые сетевые worker-потоки не создаются.
  При истечении срока события остаются в spool и повторяются с обычным backoff.
  Системный DNS (`getaddrinfo`) переносимо не отменяется: после его возврата
  истёкший запрос отклоняется до подключения. Перебор адресов использует остаток
  общего срока. Bearer token, payload и тело ответа не логируются.
- Endpoint поддерживает IPv4, IPv6 в URL-скобках и DNS hostname. Если порт не
  указан, соединение получает 80 для HTTP и 443 для HTTPS; явный порт сохраняется.
  IPv6 передаётся соединению без скобок и с отдельным числовым портом, чтобы
  конструктор HTTPConnection/HTTPSConnection не разбирал адрес как host:port.

Приёмка: потеря ответа после приёма сервером; 429/503 и Retry-After;
401/403 без быстрого retry; повреждённый/неполный/чужой ACK; смешанный ACK;
неизменность событий после рестарта; ограничение ответа и отсутствие переноса
credentials при redirect; настоящие HTTP-запросы к локальному тестовому серверу.
Общий срок и закрытие реального соединения проверяются при медленных заголовках,
теле Content-Length, строке размера chunk и зависшем TLS handshake. После таймаута
проверяются сохранение очереди и успешная последующая доставка с подтверждением.
Дополнительно без сетевого подключения проверяются фактические host/port
созданных HTTPConnection/HTTPSConnection: IPv6 loopback без порта → (::1, 80),
HTTPS IPv6 без порта → (исходный IPv6, 443), явный нестандартный порт сохраняется;
IPv4 и DNS получают стандартный либо явно заданный порт. Подмена подключения
исключает зависимость от внешней сети и наличия IPv6 на машине.
Эти тесты доказывают работу sender, но не PostgreSQL commit и не живую ленту.

CLI: `python -m agent.telemetry.deliver --spool PATH --agent-id UUID --endpoint URL`.
Токен задаётся только через `HF_AGENT_TOKEN`. `--once` выполняет один шаг:
exit 0 — пусто/ACK применён, 1 — нужен повтор, 2 — конфигурация/доступ/локальная
ошибка, 130 — прерывание пользователем. Без `--once` процесс ждёт пополнения
существующей очереди и соблюдает backoff; при paused завершается с кодом 2.
Отправитель не собирает журнал и не запускает ловушки, не очищает snapshots.
Пауза хранится в памяти: после перезапуска возможна первая немедленная попытка;
устойчивость event_id/payload обеспечивает spool. Несколько sender на одном spool
не являются поддержанным режимом; runtime запускает один экземпляр доставки.

# История событий и поток: спецификация второй ветки

Статус: протокол подтверждён Дианой 10.10.2026 в 20:07 (Москва), см.
07_DECISIONS.md. Ответ frontend не утверждает production-миграцию backend
или окончательную политику маскирования. До этих согласований — реализация
сервисов и тестового приложения с явно внедрённым хранилищем.

## 1. Область

GET /api/v1/events, GET /api/v1/stream-events, WS /api/v1/stream.
Replay, summary, DTO расследования, Low-адаптер, TCP Event type, ingest и
авторизация агента не входят. Предлагаемое размещение: отдельные модули history,
cursors, stream и presentation внутри backend/src/honeyforge/telemetry.
Router и WS transport держать отдельно от бизнес-сервисов.

Источник истины — committed publication первого агента, не память процесса,
не необработанный outbox и не sequence таблицы events. Уведомления могут ускорять
чтение, но пропуск уведомления не должен терять событие. MVP может читать журнал
периодически ограниченными страницами без новой инфраструктуры pub/sub.

## 2. История

Запрос: deployment_id, from, to, source_ip, type, cursor, limit.
Ответ: `{items: [EventV1], next_cursor: string|null}`.
limit 1..200, по умолчанию 50. from включительно, to исключительно;
фильтрация по occurred_at; from >= to — 422.
Сортировка: received_at DESC, event_id DESC, agent_id DESC.
Идентичность UI — пара agent_id/event_id, не один event_id.

Первая страница фиксирует committed publication watermark W. Все следующие
страницы ограничены stream_seq <= W, даже если новая публикация имеет старое
received_at. Одна только последняя тройка сортировки не задаёт стабильный snapshot.
Курсор включает версию, W, последнюю тройку сортировки и нормализованные фильтры/
порядок; защищён от подмены. Использовать keyset, не OFFSET. Размер декодирования
ограничен; неверный, повреждённый или несовместимый с фильтрами cursor — 422.
Способ подписи и передача ключа тестов — внутренние детали; новую публичную
настройку или ключ production согласовать с backend. Секрет в cursor не хранить.

GET /events и cursor не должны выдавать canonical_bytes, digest, PK, токены,
внутренние exception или полный validation input. Не включать параметры
session_id/sort из DTO расследования в обязательную первую реализацию.

## 3. Догрузка committed stream

`GET /api/v1/stream-events?after=100&until=120&limit=100`.
Ответ по подтверждению frontend:

```json
{"items":[{"stream_seq":"101","event":{}}],"watermark":"120","next_cursor":"101"}
```

В примере event сокращён; фактически нужен полный EventV1.
В REST item обязательны stream_seq/event; discriminator `type` нужен для WS.
Старый пример specs/frontend-protocol-v1.md содержал type и в REST: уточнить
документ по этому ответу и фактическому StreamRecord/GapPage фронта, не распространять
изменение на WS. Зафиксировать точный ответ тестом совместимости.

after — исключительная, until — включительная граница. Сортировка seq ASC.
limit 1..500, по умолчанию 100. until отсутствует — зафиксировать текущий W и
вернуть его; следующие страницы клиент запрашивает с этим until.
next_cursor равен seq последней записи страницы только при наличии продолжения,
иначе null; клиент использует его как следующий after. Не увеличивать seq на 1
в предположении отсутствия промежутков. При after=until — пустой завершённый ответ.
watermark остаётся равным until на всех страницах, новые публикации его не меняют.

seq, watermark и next_cursor снаружи — десятичные строки bigint; значения выше
2^53 не преобразовывать в float/JavaScript Number. Проверять диапазон PostgreSQL
bigint, знак, формат и отношения границ. Некорректные/будущие границы — 422.
Утраченную retention историю обозначать 410 только при доказуемой нижней границе
хранилища; отсутствие одной строки из-за допустимого промежутка не означает 410.
Retention/удаление сейчас не реализовывать. В тестах можно внедрить явную политику
нижней границы; такой тест не доказывает работу ещё не написанного cleanup.

## 4. WebSocket

Первое сообщение: `{type: "hello", watermark: "W"}`.
Далее: `{type: "event", stream_seq: "N", event: EventV1}`, где N > W.
История перед W по WS не отправляется; параметр after в WS не добавляется.
События читаются из журнала по последнему прочитанному seq, поэтому commit между
снимком W и началом ожидания уведомлений остаётся доступен. Сначала отправить
hello, затем live в возрастающем порядке. События до commit не видны.

Сетевые повторы допустимы; пропуск без сигнала — нет. Ограничить страницы/очередь
и время ожидания отправки; медленный клиент не должен удерживать транзакцию,
блокировку publisher или расти в памяти без предела. При невозможности продолжить
закрыть соединение с документированным временным статусом и восстановлением
через REST; новый специальный close code согласовать, существующие 4401/4403
использовать только для их текущего назначения.
На disconnect/ошибке закрывать Session и фоновые задачи; простой WS не держит
долгую PostgreSQL-транзакцию. Синхронные DB-операции не блокируют async event loop.

## 5. Пользовательский доступ и публичная проекция

REST использует существующую cookie-сессию/Reader. WS проверяет cookie и Origin
по текущим Settings, затем проверяет сессию перед данными и периодически при простое.
Истечение/отзыв — 4401, запрет доступа — 4403. На начальном отказе допустим
handshake с немедленным закрытием без hello/events. Ошибки не раскрывают секреты.
Не заменять проверки always-true dependency, даже в будущей рабочей интеграции.
Тестовое приложение подключает настоящую auth-логику к тестовой БД.

Оригинал остаётся в хранилище; PublicEventPresenter создаёт отдельный объект.
Фронт сейчас маскирует auth.attempt.password, но это не серверная политика
доступа. До её подтверждения использовать только синтетические fixtures и
не подключать router к рабочему приложению с реальными оригиналами. Подготовить
тестовую маскирующую политику, сохраняющую исходные bytes; окончательное правило
записать после ответа backend. Отсутствие ответа не разрешает raw JSON fallback.

Поля, которые читает frontend: auth.attempt — username/password/success;
session.command — input; session.output — output; http.request — method/path;
token.triggered — token_id; runtime.state — state. Для connection.opened и
session.closed достаточно source/service. data.truncated=true означает известное
усечение; отсутствие флага не доказывает полноту Low payload. query/user_agent/status
предложены Дианой, не обязательны и не выдумываются сервером при отсутствии данных.
Не переписывать исходный Event при построении UI-проекции.

## 6. Совместимость frontend

Подтверждённый алгоритм: hello W → буфер live >W → страницы `(last,W]` →
сохранение W → объединение с буфером и удаление повторов.
410/422 догрузки: новое соединение/hello и свежая история /events.
422 «Показать ещё»: сброс и первая страница один раз; повторный 422 — видимая ошибка.
Отдельное переключение ленты/потока и при необходимости «Последних событий»
выполняет Диана. Overview summary/replay/расследование остаются на моках.
Не добавлять второй конфликтующий frontend feature flag.

## 7. Готовность

Независимые unit/contract-тесты можно закончить до storage SHA. SQL-тесты и
совместный publisher → read/WS прогон — только после включения проверенного
коммита первой ветки. Подключение production routes и реального frontend требует
оставшихся согласований и миграции. Итоговый отчёт разделяет эти состояния.
## Локальное ядро PostgreSQL, 10.10.2026

### Требования ядра до согласования интеграций

Статус: локальное транзакционное ядро и проверяемый проект схемы. Согласованные
инварианты взяты из specs/events.md; предлагаемые имена классов/таблиц внутренние.
Production-миграция, общий Event-пакет и HTTP ingest требуют ответа backend.

### 1. Границы и размещение

Основной код: `backend/src/honeyforge/telemetry/`, тесты:
`backend/tests/telemetry/`. В спецификации архитектуры отметить, что код ещё
не подключён к приложению. Разделить типы/таблицы, запись, публикацию и чтение.
Не создавать параллельный backend, движок БД или глобальную сессию.

Прототип таблиц использует собственную SQLAlchemy MetaData/registry, явно
передаваемую схему и тот же backend Engine/Session. Его импорт не регистрирует
таблицы в общей метаинформации Alembic. В тестах создавать и удалять только
схему вида telemetry_test_<случайный идентификатор> в honeyforge_test.
Не использовать search_path, способный случайно направить запись в public.
Создание таблиц выполняет только тестовый setup, не рабочий код приложения.
После согласования модель переносится в общую метаинформацию с миграцией
от фактического Alembic head. Этот перенос сейчас не требуется.

### 2. Внутренний вход и результат

Вход хранилища — неизменяемый PreparedEvent: исходный index, UUID agent_id,
event_id, deployment_id, instance_id, profile_revision, canonical_bytes и
нормализованные поля, необходимые для чтения. Они представляют уже проверенный
Event v1, включая тип, время, source/service, session_id и data.
Это внутренний тип, не новый сетевой DTO и не доказательство полномочий.
Подготовка/авторизация настоящего внешнего ввода остаются будущей границей.
При наличии дублирующих проекций требовать их соответствия canonical_bytes;
не сохранять два противоречащих друг другу представления.

Канонические байты создаются единственным действующим алгоритмом specs/events.md.
Для тестов допустимы заранее проверенные golden fixtures и генератор в агентском
окружении. Runtime-зависимость backend от agent через sys.path, копия валидаторов
и новая трактовка JSON/Pydantic запрещены. Размещение общей библиотеки ожидает ответа.

Сервис записи возвращает упорядоченные по исходному index результаты:
новая/повторная запись принята либо EVENT_ID_CONFLICT. Результат принятия доступен
вызывающему только после успешного commit. Это внутренний результат, не HTTP ACK.
При ошибке commit или неопределённом результате соединения — исключение без
положительного результата; повтор безопасен за счёт дедупликации.
Внутренний пустой список — no-op; ограничения внешнего Batch не меняются.

### 3. Логическая схема

| Сущность | Необходимые данные и ограничения |
| --- | --- |
| Event | внутренний PK; agent_id/event_id UNIQUE; canonical_bytes BYTEA неизменны; версия канонизации; SHA-256 как вспомогательное поле; received_at с timezone; поля проекции для фильтров |
| Outbox | UNIQUE/FK на внутренний event PK; состояние ожидает/обработан либо processed_at; один outbox на событие |
| Publication | положительный bigint stream_seq PK/UNIQUE; UNIQUE/FK на внутренний event PK; время публикации |
| Состояние publisher | одна стабильная строка для блокировки и транзакционного счётчика; непустая инициализация в тестовом setup |

FK между собственными таблицами обязательны. Связи с host/deployment/instance
описать в проекте, но не считать реализованной авторизацией и не добавлять
несогласованную production-миграцию. Внешние UUID в этом этапе — тестовые данные.
Удаление события не должно оставлять outbox/publication-сироты; очистка и retention
не входят в этап. Не включать каскадное удаление исторических событий без согласования.

Одинаковый хеш недостаточен: окончательно сравнивать canonical_bytes. При повторе
не менять оригинал, received_at, PK или уже выданный stream_seq. JSONB/text JSON
не заменяют исходные канонические байты для проверки равенства.

### 4. Транзакции записи

Event и outbox записываются атомарно. Разрешение конкурентного повтора опирается
на UNIQUE в PostgreSQL. Нельзя ограничиться SELECT перед INSERT. При READ COMMITTED
после ожидавшего ON CONFLICT нужен корректный повторный SELECT committed строки:
один CTE со старым snapshot может не увидеть победившую конкурентную вставку.

Конфликт содержания одного элемента не откатывает хорошие элементы batch.
Ожидаемый результат [новый B, изменённый A, новый C] — B/C приняты, A конфликт,
старый A неизменён. Неожиданная ошибка БД откатывает весь текущий batch и не выдаёт
принятия его новым элементам. Не ловить все IntegrityError как повтор события:
различать ожидаемое ограничение и остальные неисправности.

При пересекающихся batch [A,B] и [B,A] обеспечить предсказуемый порядок захвата
уникальных ключей либо ограниченный безопасный повтор всей транзакции.
Внутренний порядок обработки не меняет индексы возвращаемых результатов.
Дубли идентичности внутри одного входного списка отклонить до записи как нарушение
предусловия; не придумывать новую семантику внешнего Batch.

### 5. Publisher и committed порядок

Publisher — вызываемый класс с ограниченным шагом publish_once(limit).
Отдельный процесс/CLI/Compose пока не подключается. На пустом outbox — no-op.

Один шаг берёт блокировку стабильной строки состояния в PostgreSQL, затем выбирает
committed pending outbox, назначает номера, вставляет publication и отмечает outbox
обработанным. Все эти изменения и счётчик входят в одну транзакцию; блокировка
удерживается до commit. Все экземпляры класса используют одну блокировку
для одного журнала и одинаковый порядок: состояние → outbox → publication.
Случайный второй publisher не может публиковать обходным путём.

Обычный nextval без сериализации commit не обеспечивает watermark. Значение W
означает, что впоследствии не появится ранее невидимая publication с seq <= W.
Поздно committed Event получает публикацию после уже видимого W независимо от
его PK/occurred_at/received_at. Непрерывность номеров не является внешним контрактом.
Пустой committed журнал имеет watermark 0. Граница bigint и переполнение
обрабатываются ошибкой без частичной публикации.

Сбой до commit откатывает publication и processed вместе; повтор публикует один раз.
Сбой после commit сохраняет одну publication и processed; повтор не создаёт новую.
Никаких сетевых отправок из транзакции. Публикация в БД не означает доставку клиенту.

### 6. Интерфейс для второй ветки

Предоставить read-only интерфейс, конкретные Python-сигнатуры записать в handoff:

- чтение committed watermark;
- чтение публикаций `(after, until]` по stream_seq ASC с ограниченным limit;
- чтение опубликованных событий в snapshot `publication.stream_seq <= W`
  по `received_at DESC, event_id DESC, agent_id DESC` с keyset-границей;
- фильтры deployment, occurred_at[from,to), source_ip и type.

Read-модель включает внутренний event PK, UUID идентичности, received_at,
stream_seq и оригинал для последующей безопасной проекции. Она не является
пользовательским ответом. Canonical bytes и hash нельзя случайно сериализовать в UI.
W и строки читаются с согласованными условиями; поздние публикации не попадают
в уже зафиксированный снимок. Методами чтения нельзя менять outbox или counter.
Курсор HTTP, JSON-ответ и WS остаются ответственностью второго агента.

### 7. Готовность

Код и спецификации, реальные транзакционные тесты, build/type/lint, локальный
коммит и STORAGE_READY.md. До согласований готовность относится только к ядру.
Политика старых instance, неизвестных instance, Bearer, HTTP-парсинг, миграции,
общая канонизация и реальный Low остаются отдельными пунктами.

### Исполняемые интерфейсы и проверка прототипа

Внутренние сигнатуры: EventStorage(engine, tables).store(events: Sequence[PreparedEvent])
→ list[WriteResult]; OutboxPublisher(engine, tables).publish_once(limit=100) → int;
PublicationReader(engine, tables).watermark() → int;
stream(after: int, until: int, limit=100) → list[StoredEvent];
history(watermark: int, limit=50, before: HistoryKey|None=None,
filters: EventFilters|None=None) → list[StoredEvent]. Методы освобождают собственные
Session/connection. Reader возвращает bounded страницы без HTTP next_cursor.
Внутренние пределы reader: stream 1..501, history 1..201, чтобы сервис мог читать
limit+1 при публичных пределах 500/200. Проверка будущих курсоров — задача
stream-сервиса.

PreparedEvent содержит index, четыре UUID, profile_revision, canonical_bytes.
Нормализованные type/time/source/service/session/data извлекаются из готового
оригинала; второй изменяемой JSON-проекции в памяти или JSONB нет. UUID/revision
сверяются с bytes до записи. Это не валидатор недоверенного JSON: корректная
канонизация Event остаётся предусловием. original() возвращает новый объект.
Тестовый generate.py вызывается из корня через runpy и использует агентский Event;
приложение и исполняемые PostgreSQL-тесты не импортируют агентский пакет.

Setup backend/tests/telemetry/conftest.py использует защищённый общий Engine,
случайную схему telemetry_test_<uuid>, create_all и singleton id=1,last_seq=0;
cleanup удаляет только эту схему. Общую Alembic Base прототип не затрагивает.
Тестовые SQL lock/statement timeout — 10/15 секунд; Barrier/Event/future — 10 секунд.
Для всех backend pytest использовать scripts/run_backend_tests_locked.ps1:
передать абсолютные UvPath, BackendPath и общий LockPath из BRANCH_HANDOFF.md,
затем аргументы tests/telemetry -q либо без testpath для полного прогона.
Wrapper держит FileShare.None весь pytest, включая штатные миграции и cleanup;
ожидание lock ограничено 30 секундами. Установить HF_TEST_DATABASE_URL отдельно,
секреты в handoff и коммит не записывать. Недоступный стенд означает ошибку,
а не skip. test_prepared.py явно изолирован и не требует PostgreSQL.

### Управляемое завершение WS DB-операций

Каждый внутренний вызов чтения или проверки сессии имеет бюджет 3 секунды.
Перед каждым SQL в контексте WS устанавливается локальный PostgreSQL
statement_timeout: не более 1000 мс и оставшегося бюджета. Настройка действует
только в транзакции вызова; вне WS SQL не изменяется. При cancel, disconnect
или shutdown запрещается следующий SQL и обязательно ожидается завершение
учтённого worker с rollback/close. Повторная отмена не прерывает очистку.
При доступной PostgreSQL активный запрос и соединение освобождаются в течение
2 секунд после отмены, до снятия внешней SQL-блокировки. Event loop не блокируется.
Получение соединения ограничивается pool_timeout/connect_timeout Engine;
потеря сети подчиняется таймаутам драйвера. Синхронные внутренние адаптеры не
должны выполнять неограниченную работу вне SQL. Python не прерывает произвольный
синхронный код, поэтому завершение worker всегда ожидается явно.
Hello/live, seq, страницы, cookie/Origin, отзыв сессии и close codes сохраняются.
На простое транзакция не удерживается. Production router не подключается.

Даты from/to, UTC-нормализация которых выходит за диапазон datetime,
отклоняются DomainError(422) с общим сообщением без внутренних данных.
Корректные даты нормализуются в UTC; from включительно, to исключительно.

## Дополнительная проверка доставки при отказах

`tests/telemetry/test_sender_durable_http.py` запускает настоящий
TelemetrySender/HttpBatchTransport с временной spool и loopback HTTP.
Приёмник использует собственную SQLite-базу: канонические Event и попытки
фиксируются commit до обрыва сокета. Дедупликация переживает отдельные запросы;
повторы сравниваются побайтно, после рестарта сравниваются Event согласно
действующему разрешению нового batch_id. Проверяются отказ подключения/503,
backoff, потеря ACK, рестарт, неверный ACK, полный ACK, смешанный accepted,
permanent/retryable и доставка новых событий после восстановления.
Это явно тестовый приёмник, не production ingest, PostgreSQL или Low → UI.

производственного перехода raw → Event пока нет.
