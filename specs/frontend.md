# Спецификация: frontend HoneyForge

| | |
|---|---|
| Статус | **черновик** — до согласования контрактов в D1 |
| Владелец | участник 1 (frontend) |
| Код | `frontend/` |
| Основание | ТЗ «Мадригал. Конструктор» (FR-C1…C7, FR-A5…A6, §7.3, §10), план команды «HoneyForge — план на 5 дней» |

## 1. Назначение и границы

Пульт оператора SOC: вход, парк ловушек, конструктор профилей, запуск и
команды, живая лента событий, паспорт атаки (timeline, replay,
артефакты, honeytoken, алерты), CSV IoC, аудит.

**Входит:** интерфейс, клиент API и потока событий, моки, тесты UI и E2E.

**Не входит:** проверка прав (её делает API; UI только скрывает
недоступное), формирование CSV (делает сервер), STIX, геокарта,
LLM-сводка. Маскот «Юми» — только зарезервированное место (раздел 9).

## 2. Термины

| Термин | Что это |
|---|---|
| Профиль | Шаблон ловушки; каждое сохранение — неизменяемая ревизия |
| Ловушка (deployment) | Профиль определённой ревизии на хосте |
| Хост / агент | Runtime-узел и его агент; статус связи ≠ статус ловушки |
| Job | Асинхронная операция: requested → leased → running → succeeded / failed / expired |
| Событие | Запись v1 из `contracts/` (`event_id`, `type`, `occurred_at`, …) |
| `stream_seq` | Монотонный номер публикации события для живой ленты |
| Паспорт атаки | Экран сессии: timeline, replay, артефакты, honeytoken, алерты |

## 3. Требования

### 3.1. Доступ

- **F1.** Без сессии доступны только «Вход» и ошибки; остальное
  перенаправляет на вход и возвращает на исходную страницу после входа.
- **F2.** Роли `admin` / `operator` / `viewer`: viewer не видит кнопок
  изменения; запрет всё равно определяет API (403 → «нет прав»).
- **F3.** 401 на любом запросе — «сессия истекла», переход на вход.

### 3.2. Парк и ловушки

- **F4.** Список хостов: online / offline / degraded, last_seen,
  backlog, свободный диск. Online — это связь, а не работа ловушки.
- **F5.** Список ловушек: уровень (low / medium / high), состояние
  (planned / deploying / running / stopping / stopped / failed / unknown —
  «состояние не подтверждено»: центр потерял подтверждение агента),
  desired и applied revision. Если ревизии не совпадают — «drift»
  (предупреждение), а не успех.
- **F6.** Команды start / stop / reset — только operator/admin, опасные
  с подтверждением; reset — только High.
  После команды виден прогресс job до итогового состояния.
#### Команды ловушки (F6, control OpenAPI)

Центр выполняет `start` / `stop` / `reset` по `specs/commands.md`. Фронт
отправляет их на настоящий API; демо и тесты на MSW повторяют тот же
контракт. `apply_config` и `rotate_credentials` на сервере не реализованы —
в UI их нет, вернутся отдельным этапом. Первая цель — запуск и остановка
Low; правила доступности общие для всех уровней.

**Отправка.** `POST /api/v1/deployments/{id}/commands` с телом
`{command, idempotency_key, expected_generation}` → `202 {job_id}`.
`expected_generation` — поле `generation` из актуального `DeploymentRead`.
`idempotency_key` — UUID, создаётся один раз на действие пользователя
(нажатие кнопки или подтверждение в диалоге). Если запрос не дошёл
(сетевой сбой), «Повторить» отправляет то же тело с тем же ключом —
сервер вернёт прежний `job_id`, а не создаст второе задание. Новое
действие — новый ключ.

| Команда | Доступна, когда | Подтверждение |
|---|---|---|
| `start` | planned, stopped, failed | нет |
| `stop` | running, failed, unknown | да: «ловушка перестанет принимать подключения» |
| `reset` | только High, running или failed | да: «доказательства сохранятся, среда вернётся к чистому образу» |

В `deploying` и `stopping` команд нет: идёт предыдущая. Сервер проверяет
то же самое; таблица только не даёт нажать заведомо отклонённое.

- Кнопки только у operator и admin; у viewer их нет (запрет всё равно
  проверяет API).
- Защита от повторных кликов: пока запрос отправляется или задание не
  завершено, кнопки ловушки неактивны.

**Ход задания.** Принятие команды (202) ещё не значит, что ловушка
запустилась. По `job_id` опрашиваем `GET /api/v1/jobs/{id}` (`JobRead`:
`{job_id, deployment_id, command, state, error, error_code, generation,
created_at, completed_at}`) раз в секунду до итога и показываем:

| `state` | Подпись |
|---|---|
| `requested`, `leased` | ожидает |
| `running` | выполняется |
| `succeeded` | успешно |
| `failed` | ошибка: <причина> |
| `expired` | истёк срок — агент не выполнил команду вовремя |

После итога данные ловушек перечитываются. Сбой сети, обрыв тела ответа или 5xx
при опросе — это не итог: показываем «нет связи — проверяем снова», опрос продолжается,
кнопки остаются неактивными. Отказ сервера при опросе (404, 403) или полный ответ не в JSON (например,
страница прокси вместо API) —
«не удалось проверить задание: <причина>», опрос останавливается, данные
ловушек перечитываются. Истечение срока, как в центре: `DELIVERY_EXPIRED`
(агент не взял команду, состояние ловушки не меняется) или
`EXECUTION_EXPIRED` (взял, но не подтвердил — ловушка становится `unknown`).
Операции с ловушками (действие, ключ, задание, отправка, ошибка) хранятся
на уровне приложения (`Operations`), а не в строке таблицы: их не теряют
сбой обновления списка, временное исчезновение ловушки из списка и уход
со страницы парка. Сбой обновления списка (после повторов клиента) не
убирает таблицу, если данные уже загружены: показываем последние данные и
предупреждение «не удалось обновить» (`role=status`, чтобы не перебивать
работу при «мигающей» связи) с «Повторить» — так же для списка хостов. Ход задания — в одной постоянной живой области (`role=status`); после
нажатия (после закрытия диалога подтверждения) фокус переходит к ней,
после «Отмена» в диалоге — к кнопке. После перезагрузки страницы ход
прерванного задания не восстанавливается, но состояние ловушки
(`deploying` / `stopping`) показывает, что команда идёт.

Причина ошибки берётся из `error_code`: коды драйвера (участник 3)
переводятся в понятный текст, иначе — `error`, иначе код как есть:

| Код | Текст |
|---|---|
| `UNSUPPORTED_PROFILE` | профиль не поддерживается этим хостом |
| `HEALTHCHECK_FAILED` | проверка работоспособности не прошла |
| `START_FAILED` | не удалось запустить |
| `BACKEND_UNAVAILABLE` | среда запуска недоступна (Docker или KVM) |
| `CLEANUP_FAILED` | не удалось убрать после остановки |
| `INVALID_STATE` | команда недопустима в текущем состоянии |

**Отказ при отправке.** 409 с полем `code` в `ErrorResponse` — понятное
сообщение без автоматической повторной отправки:

| Код | Сообщение и действие |
|---|---|
| `STALE_GENERATION` | «Ловушку уже изменили — данные обновлены.» Данные ловушек перечитываются; когда они пришли и команда всё ещё доступна — «Повторить?» с кнопкой (новое действие с новым ключом и свежим `generation`), иначе — «Команда больше недоступна в текущем состоянии» |
| `COMMAND_BUSY` | у ловушки уже выполняется команда |
| `INVALID_STATE` | команда недоступна в текущем состоянии |
| `UNSUPPORTED_COMMAND` | сброс доступен только для High |
| `PROFILE_ARCHIVED` | профиль в архиве — запуск невозможен |
| `UNSUPPORTED_PROFILE` | хост не поддерживает уровень профиля |
| `AGENT_REVOKED` | доступ агента отозван |
| `IDEMPOTENCY_CONFLICT` | запрос с этим ключом уже был другим — начните действие заново |

После любого 409 данные ловушек перечитываются. Неизвестный код — текст
`detail` от сервера. Сетевой сбой, обрыв тела ответа (в том числе неполный 202), ответ не в
JSON или 5xx при отправке — результат неизвестен, запрос мог дойти —
сообщение и «Повторить» с тем же ключом; пока команда не отправлена, другие
команды ловушки неактивны. «Отменить» снимает блокировку без перезагрузки
страницы (данные ловушек перечитываются — видно, дошла ли команда).

#### Мастер назначения (F7, control OpenAPI)

Адрес `/fleet/new`, кнопка «+ Запустить ловушку» в парке (operator и admin).

1. **Хост.** Online можно выбрать; offline/revoked недоступны.
2. **Профиль и ревизия.** Профиль из списка; ревизия — по умолчанию
   последняя, можно выбрать любую из истории (ловушка привязывается к
   неизменяемой ревизии). Возможности узла low/medium/high проверяются
   по выбранной ревизии; несовместимая latest не мешает выбрать старую.
3. **Проверка.** Сводка: хост, профиль, ревизия, уровень, сервисы и
   порты. «Запланировать» → `POST /api/v1/deployments`
   `{host_id, profile_id, revision}` → `201 DeploymentRead`.
4. **Итог.** «Ловушка запланирована» со ссылкой в парк. Это намерение,
   не подтверждение запуска процесса. Для запуска нужен отдельный command и ACK.

Шаги проходятся по порядку («Далее» / «Назад»); выбранное не теряется при
возврате. Ошибка 422 показывается на шаге, к которому относится поле.

- **F7.** Мастер запуска: хост → профиль и ревизия → запуск (202 +
  job_id) → прогресс → результат или ошибка.

#### Обзор (`/`, черновик до OpenAPI)

Первый экран после входа — состояние парка и атак одним взглядом.

- Плитки из `GET /api/v1/analytics/summary` →
  `{deployments: {total, running, failed}, hosts: {total, online, degraded},
  events_last_hour, alerts_open}`; перечитываются раз в 15 с.
  - «Ловушки»: работают из всего; упавшие — красным с числом.
  - «Хосты»: на связи из всего; с ошибками — жёлтым.
  - «События за час».
  - «Открытые алерты»: больше нуля — красным.
  Каждая плитка ведёт на свой экран (парк, события, алерты).
- «Последние события»: 10 последних (`GET /events?limit=10`), новые из
  потока сверху; ссылка «вся лента». Вывод — по правилам S1–S4.
- «Активные источники»: топ-5 IP за час из того же ответа
  (`top_sources: [{ip, count}]`); IP — ссылка на ленту с фильтром.
- Сводка не загрузилась — плитки показывают ошибку и «повторить»,
  последние события при этом работают.

### 3.3. Профили

- **F8.** CRUD профиля со всеми полями FR-C1: уровень, сервисы и порты,
  баннеры, учётные данные-приманки, логирование, параметры канала и
  маскировки, легенда. Проверка формы — Zod-схемой.
- **F9.** Сохранение создаёт новую ревизию; виден список ревизий.

#### Поля профиля (по контракту `openapi.json`: ProfileCreate / ProfileConfigInput)

Имя и описание — на верхнем уровне (`ProfileCreate`), остальное — в `config`
(`ProfileConfigInput`). Значения формы совпадают с ограничениями сервера.

| Поле | Правило |
|---|---|
| `name` | 1–80 символов, обязательно (верхний уровень) |
| `description` | до 500 символов (верхний уровень) |
| `config.interaction_level` | `low` / `medium` / `high` |
| `config.hostname` | легенда: RFC 1123, до 63 символов |
| `config.services[]` | 1–8 сервисов: Low — не больше одного TCP и одного HTTP, Medium только SSH, High один SSH; `port` 1–65535 без повторов, `banner` до 200 символов, одной строкой; у TCP баннер обязателен и состоит только из печатных ASCII (0x20–0x7E) |
| `config.credentials[]` | до 8 пар `username` (1–64, маска `[a-zA-Z0-9_.-]`) / `password` (1–128); Medium/High требуют учётки. При правке `null` сохраняет секреты; замена выбирается явно |
| `config.logging.max_payload_bytes` | точное целое число байт 256–8192 |
| `config.channel` | `flush_interval_ms` 100–5000, `batch_size` 1–100 |
| `config.high` | только для High: `template` (`ubuntu-ssh-v1`), `ttl_seconds` 60–3600, `cpu` 1–2, `memory_mb` 1024–4096; по умолчанию в форме — как в центре: TTL 900 с, 2 vCPU, 2048 МБ |

Обновление профиля (`ProfileUpdate`) требует `expected_revision` — ожидаемую
текущую ревизию; при расхождении сервер отвечает 409. История ревизий —
`GET /profiles/{id}/revisions` (`RevisionRead`).

Сочетания уровней и протоколов:

- **Low** — только `tcp` и `http`, не больше одного каждого (драйвер
  участника 3 поднимает один TCP-баннер и одну HTTP-заглушку). Баннер TCP
  обязателен (не из одних пробелов): только печатные ASCII (0x20–0x7E),
  до 200 символов;
- **Medium** — только `ssh` (Cowrie), хотя бы один сервис;
- **High** — только `ssh` (шлюз к VM), ровно один сервис.

Подпись поля `banner` зависит от протокола: у HTTP — «Текст страницы-заглушки»
(это тело ответа заглушки), у TCP и SSH — «Баннер».

Учётные данные-приманки нужны Medium и High; для Low поле не показывается.
Сервисы заменяются только при явной смене уровня пользователем: если
текущий список новому уровню подходит, он сохраняется, иначе весь список
заменяется набором по умолчанию для уровня (Low — HTTP 8080, Medium —
SSH 2222, High — SSH 2224). При открытии профиля и при правке полей
сервисы не заменяются: нарушение правил видно ошибкой у поля сразу при
открытии, текст подсказывает, что сделать.
Выпадающий список протоколов всегда
показывает значение, реально записанное в форме.
На Low кнопка «+ Сервис» добавляет недостающий протокол (TCP или HTTP);
когда есть оба (или на Medium уже 8 сервисов), вместо неё подсказка о
правиле, а фокус переходит на
новый сервис. Профиль, созданный в обход формы и нарушающий эти правила
(например, два TCP или кириллица в баннере TCP), открывается как есть,
но сохранить его можно только после исправления — ошибка видна у поля.
Ошибки показываются у полей; сохранить можно только валидный профиль.
После сохранения — сообщение с номером новой ревизии.

### 3.4. События

- **F10.** Живая лента: новые события появляются без перезагрузки;
  состояние потока видно (live / переподключение / отстаём).
- **F11.** Фильтры: ловушка, период, IP источника, тип. Пагинация по
  курсору; браузер не загружает журнал целиком.
- **F12.** Восстановление после обрыва без потерь и дублей (раздел 5).
- **F13.** Время в API — UTC, на экране — локальное с часовым поясом.

#### Лента: фильтры и живой поток

- Фильтры: ловушка (`deployment_id`), тип (`type`), IP источника
  (`source_ip`, IPv4/IPv6 — проверяется до запроса), период: `from`
  **включительно**, `to` **исключительно**; в поле — локальное время, в
  API — RFC 3339 с часовым поясом (UTC, `Z`); `from` раньше `to`.
  Фильтры хранятся в адресе страницы — ссылкой можно поделиться, «назад»
  работает.
- Первая страница — `GET /api/v1/events?<фильтры>&limit=50`, ответ
  `{items, next_cursor}`, новые сверху; «Показать ещё» — следующая
  страница по `next_cursor` (курсор непрозрачный, frontend его не
  разбирает). `next_cursor: null` — страниц больше нет. При смене
  фильтров курсор сбрасывается.
- Живые события из потока добавляются сверху, **только если подходят
  под фильтры**; при заданном `to` в прошлом живые не добавляются.
- Пауза: новые события не сдвигают таблицу, а копятся в счётчике
  «N новых — показать».
- Live и pending ограничены 500 записями каждый; загруженные REST-страницы
  сохраняются для просмотра истории. Переполнение pending требует явного
  свежего снимка; пропуск не скрывается счётчиком «500 новых».
- Повтор пары `(agent_id, event_id)` из REST и потока показывается один раз.
- Индикатор потока в шапке: «онлайн» / «подключение…» /
  «переподключение…» / «нет потока».

### 3.5. Расследование

- **F14.** Паспорт атаки: timeline событий сессии; клик по событию
  переводит replay к его моменту.
- **F15.** Replay: ввод и вывод по времени, пауза, скорость; обрезанные
  и неизвестные части отмечены. Чанк (согласовано с командой):
  `{seq, offset_ms, direction: "in" | "out", data_base64, truncated}` —
  `offset_ms` от начала сессии; байты декодируются потоковым UTF-8
  декодером отдельно для каждого направления (символ может быть разрезан
  между чанками); `truncated: true` показывается как пропуск данных.
  Проигрыватель текстовый: без HTML и опасных последовательностей (S2).
- **F16.** Артефакты: pending / available / failed / expired, размер,
  SHA-256; скачать можно только available.
- **F17.** Honeytoken и алерт показывают основание (исходные события).
- **F18.** Скачивание CSV IoC (файл формирует сервер).
- **F19.** Журнал аудита: кто, что, когда, результат.

#### Журнал аудита (F19, control OpenAPI)

`GET /api/v1/audit?limit=&offset=` → массив `AuditRead`
`{id, actor_id, action, target_id, details, created_at}`, новые сверху;
`limit` 1–100 (берём 50), `offset` от 0. Доступен только admin: у operator
и viewer пункт меню «Аудит» есть, но экран сообщает «Журнал аудита доступен
только администратору» и не делает запрос. 403 от API — то же сообщение.

Таблица: **Когда** (локальное время с поясом, F13) · **Кто** · **Действие**
· **Объект** · **Подробности** · **Результат**.

- **Кто.** `actor_id` текущего пользователя — «вы (имя)»; id зарегистрированного
  хоста — имя хоста из `/hosts` (действия агента); иначе — сокращённый id
  (первые 8 символов, полный — во всплывающей подсказке); `null` — «система».
- **Объект.** id профиля — его название (ссылка на профиль), id ловушки —
  ссылка в парк, id хоста — имя хоста; иначе сокращённый id. Справочники —
  уже загружаемые списки профилей, хостов и ловушек; если список недоступен,
  показываем id (журнал от этого не ломается).
- **Действие** — понятная подпись; неизвестное действие показывается как есть:

  | `action` | Подпись | Результат |
  |---|---|---|
  | `auth.login` | вход в систему | успех |
  | `auth.login_failed` | неудачный вход | ошибка |
  | `auth.logout` | выход | успех |
  | `user.created_cli` | пользователь создан (CLI) | успех |
  | `enrollment.created` | выдан токен регистрации агента | успех |
  | `agent.enrolled` | агент зарегистрирован | успех |
  | `agent.revoked` | доступ агента отозван | успех |
  | `profile.created` | профиль создан | успех |
  | `profile.updated` | профиль изменён | успех |
  | `profile.archived` | профиль в архиве | успех |
  | `deployment.planned` | ловушка назначена | успех |
  | `command.requested` | команда отправлена | успех |
  | `command.acknowledged` | агент подтвердил команду | по `details.outcome`: succeeded — успех, failed — ошибка |
  | `command.expired` | команда истекла | ошибка |

- **Подробности** из `details` — только текстом (S1): `revision` → «ревизия rN»,
  `command` → подпись команды, `generation` → «поколение N», `outcome` →
  «успешно» / «ошибка», `code` → код (известные коды драйвера — понятным
  текстом), `role` → роль, `username` → «логин: …». Прочие ключи —
  «ключ: значение»; пароли и токены сервер в журнал не пишет.
- **Пагинация** offset: «Новее» / «Старее»; общего числа записей API не
  отдаёт, поэтому «Старее» доступна, если пришла полная страница (`limit`
  записей). Страница — в адресе (`?page=`), переживает перезагрузку.
- Состояния: загрузка, пусто («Записей пока нет»), ошибка с «Повторить».


### 3.6. Безопасность отображения

- **S1.** Данные атакующего (payload, команды, вывод, имена файлов,
  баннеры) выводятся только как текст: без `innerHTML`,
  `dangerouslySetInnerHTML` и автоматических ссылок.
- **S2.** В replay управляющие escape-последовательности терминала
  удаляются; остаются печатные символы, `\n`, `\t`. Также удаляются
  переключатели направления текста (U+061C, U+200E, U+200F, U+202A–U+202E,
  U+2066–U+2069) и невидимые символы U+200B, U+2060–U+2064, U+FEFF, чтобы
  нельзя было визуально подменить команду. ZWNJ/ZWJ сохраняются.
- **S3.** URL honeytoken не кликабелен и не предпросматривается.
- **S4.** Учётные данные атакующего замаскированы по умолчанию.
- **S5.** Артефакты не предпросматриваются; только скачивание.

## 4. Интерфейс с backend

### Локальный стенд с настоящим control API

Без `VITE_API_MOCK=1` frontend обращается к настоящему FastAPI через Vite
proxy. Пока серверная телеметрия не подключена, главная страница ведёт в
парк; события показывают экран запланированной функциональности. Не создаются
WS-соединение и запросы events/analytics к отсутствующим ручкам.
`VITE_TELEMETRY_ENABLED=1` явно включает эти экраны и поток для настоящего
сервера после их реализации. Режим моков включает их автоматически.
Control-сценарии auth/profiles/hosts/deployments доступны независимо от флага.
Dev origin `http://localhost:5173` соответствует локальному allowed_origins;
при использовании другого origin настройка backend обновляется явно.

Критерии: настоящий режим открывает парк, не создаёт WebSocket и не вызывает
events/analytics; прямой переход на /events сообщает о готовящемся экране;
MSW-сценарии сохраняют прежнее поведение.

### Уточнение исправлений интеграции PR #5

- Редактор сохраняет `expected_revision` снимка, из которого создана форма.
  Фоновый refetch не меняет эту версию и не подменяет введённые значения.
  После 409 оператор явно перечитывает профиль; после успеха обновляются
  снимок формы и его версия. Поля отключены во время сохранения/перечитывания.
- Для существующего Medium/High режим по умолчанию — сохранить учётные
  данные (`credentials: null`). Замена выбирается явно и требует непустого
  списка пар логин/пароль. Новый Medium/High тоже требует учётные данные.
  Medium допускает только SSH. Изменение уровня учитывает правила backend.
  При уходе с High скрытые поля VM сбрасываются в допустимые значения и
  не блокируют сохранение Low/Medium невидимыми ошибками.
- `max_payload_bytes` редактируется точным целым числом байт 256..8192;
  открытие/сохранение не округляет исходное значение.
- Мастер назначения использует конфигурацию выбранной ревизии для проверки
  возможностей узла и подтверждения портов/уровня/легенды. До получения
  ревизии и при ошибке её чтения отправка назначения недоступна.
- Парк читает полный `DeploymentRead` (состояние, уровень, desired/applied
  revision, generation) и отправляет команды start/stop/reset на настоящий
  API; моки повторяют тот же контракт (раздел «Команды ловушки»).
- История `/events` использует `cursor=next_cursor`; журнал публикаций
  `/stream-events` использует `after=next_cursor` при неизменном `until`.
  Моки и регрессионные тесты соблюдают это различие и стабильный снимок истории.
- Перестроение REST-страниц сохраняет отдельно показанные live-события и
  pending на паузе. Показанные записи не становятся новыми при догрузке.
- Переполнение ограниченного pending-буфера отображается явно. Возобновление
  или показ новых после переполнения перечитывает свежий снимок истории;
  пользователь может догрузить его старые страницы без скрытого пропуска.
- Первое подключение и восстановление после 410 сначала получают WS hello
  и начинают буферизацию live, затем ожидают перечитывания истории. Курсор
  принимает watermark только после успешной синхронизации. После 410
  уведомление о перечитывании не выполняется до нового handshake.
  Это правило действует для ленты и последних событий обзора.

Критерии приёмки: тесты конкурентной правки, сохранения секретов и точного
лимита байт; выбора исторической ревизии; настоящего DeploymentRead;
обеих пагинаций; сохранения паузы/видимой ленты; overflow и события между
410 и новым hello. Работа будущих telemetry-ручек проверяется управляемым
транспортом, их серверная реализация этим исправлением не добавляется.

Контракт стадии 1 — общий `contracts/openapi.json` (control API). Типы
frontend для поверхностей стадии 1 (auth, профили, хосты, развёртывания)
точно повторяют его схемы (`AuthRead`, `UserRead`, `ProfileRead`,
`ProfileConfigPublic`, `RevisionRead`, `HostRead`, `DeploymentRead`,
`DeploymentCreate`). Фикстуры `contracts/fixtures/*.draft.json` повторяют эти
формы для моков.

Поток событий, команды ловушек, задания и аналитика в контракте стадии 1
**отсутствуют** (см. `specs/architecture.md`, «Границы первого этапа»): это
работа этапов 3–4. Соответствующие экраны (лента, команды парка, обзор)
работают как помеченные превью на моках; их пути и формат события
(`event-v1.schema.json`) ещё не закреплены в OpenAPI и подлежат согласованию
с участником 4. Событие v1: `schema_version` (=1), `event_id`, `agent_id`,
`deployment_id`, `instance_id`, `session_id` (может быть `null`), `source_seq`,
`occurred_at`, `received_at`, `type`, `source`, `service`, `data`,
`artifact_ids`, `profile_revision`; уникальность — пара `(agent_id, event_id)`.

| Использует | Путь | Статус |
|---|---|---|
| Сессия | `POST /api/v1/auth/login`, `POST /api/v1/auth/logout`, `GET /api/v1/auth/me` | контракт |
| Профили | `GET/POST /api/v1/profiles`, `GET/PATCH /api/v1/profiles/{id}`, `GET /api/v1/profiles/{id}/revisions` | контракт |
| Парк | `GET /api/v1/hosts`, `GET/POST /api/v1/deployments` (создание — `planned`) | контракт |
| Команды и jobs | `POST /api/v1/deployments/{id}/commands`, `GET /api/v1/jobs/{id}` | контракт (start/stop/reset) |
| События | `GET /api/v1/events?cursor=&limit=`, `WS /api/v1/stream`, `GET /api/v1/stream-events?after=&until=&limit=` | превью (этап 4) |
| Аналитика | `GET /api/v1/analytics/summary` | превью (этап 4) |

Вход: тело `{username, password}` (`LoginInput`); ответ `AuthRead`
(`{user: {id, username, role}, csrf_token}`). Пагинация истории — `cursor=<next_cursor>`;
догрузка журнала публикаций — `after=<next_cursor>`.

**Сессия и CSRF.** Сессия — HttpOnly-cookie `hf_session`; все запросы с
`credentials: 'include'`. CSRF-токен приходит полем `csrf_token` в ответах
`POST /api/v1/auth/login` и `GET /api/v1/auth/me`; frontend хранит его
только в памяти и отправляет в заголовке `X-CSRF-Token` на изменяющих
запросах (POST, PUT, PATCH, DELETE). WebSocket — по cookie и проверке
Origin, без CSRF.

**Ошибки** — контейнер `detail`: строка (`{"detail": "…"}`) или для 422
список `{loc, type, msg}`; исходный ввод в ошибку не включается. Логика
frontend опирается на HTTP-статус, а не на текст: 401 — сессии нет
(кроме входа: там это неверный пароль), 403 — нет прав, 409 —
конфликт версий («перечитайте»), 422 — ошибки полей (по `loc` в форму),
5xx — сбой сервера. Текст `detail` только показывается.

## 5. Поток событий (`StreamClient`)

Источник истины — БД; WebSocket только доставляет новое. `stream_seq` и
`watermark` — **строки** с целым числом (сравниваются как BigInt), чтобы
не терять точность JavaScript number.

Сообщения WebSocket `/api/v1/stream`:

```json
{"type": "hello", "watermark": "120"}
{"type": "event", "stream_seq": "121", "event": {"event_id": "…", "…": "…"}}
```

Догрузка: `GET /api/v1/stream-events?after=100&until=120&limit=100` →
`{items: [{stream_seq, event}], watermark, next_cursor}`; на всех
страницах тот же `until`, следующая — по `next_cursor`.

Алгоритм:

1. Подключить WS; все `event` до окончания догрузки складывать в буфер.
2. Дождаться `hello` и его `watermark`.
3. Если курсора нет (первое подключение или после 410), дождаться свежего
   `GET /events`, начатого после hello, затем принять watermark. Live всё
   это время буферизуется. Обычное переподключение: догрузить журнал
   `after=<курсор>&until=<watermark>` постранично; next_cursor становится after.
4. Слить догруженное и буфер по возрастанию `stream_seq`, отбросить записи
   с `stream_seq` ≤ курсора и повторы пары `(agent_id, event_id)`.
5. Передать подписчикам; курсор сдвигать только после передачи.
   Каждый подписчик получает только записи новее последней принятой им.
   Если подписчик бросил исключение, курсор не сдвигается, и при повторе
   записи получит только он; остальные дублей не видят.
6. Обрыв — повторное подключение с нарастающей задержкой
   (1 → 2 → 4 … до 30 с), с шага 1.

Коды закрытия WS: **4401** — сессия истекла или отозвана → переход на
вход; **4403** — нет доступа → поток остановлен, без переподключения;
**1006** и прочие сбои — проверить `GET /auth/me` (401 → вход, иначе
переподключение).

Состояния: `connecting` → `live`; при обрыве `reconnecting`; 4403 —
`forbidden`. Подписчики: лента, обзор, адаптер маскота.

## 6a. Оформление

Решение команды: стиль «досье» — тёмный лист с тонкими линиями-рамками в
лавандовом монохроме, как изображение на CRT-экране. Продукт и окно Юми
выглядят одним целым.

- **Общие токены** в `app/theme.css` — единственный источник цветов,
  шрифтов, рамок; окно Юми (`--yumi-*`) берёт значения из них же.
  - окно: `--win-border`, `--win-border-dark`, `--win-title`,
    `--win-title-text`, `--win-body`, `--win-shadow`;
  - фон и линии: `--bg`, `--bg-elev`, `--bg-panel`, `--line`,
    `--line-faint`; текст: `--text`, `--text-dim`; состояния: `--ok`,
    `--warn`, `--bad`, `--idle`; акценты: `--accent`, `--accent-2`.
- **Каркас — один лист** в высоту экрана: шапка (название, статус потока,
  пользователь, выход), слева меню и окно Юми, справа контент; под листом
  пристыкована консоль Юми. Страница не прокручивается — прокручиваются
  контент, меню, консоль и широкие таблицы; скроллбары тонкие, в цвет линий.
  На узком экране меню становится строкой, окно Юми скрывается.
- **Панель = окно-лист**: рамка 1 px цвета линий, заголовок-полоска с
  пиксельным шрифтом и пиктограммой-сердечком, тёмное полупрозрачное тело.
  Так же оформлены плитки обзора, фильтры, карточка входа, диалоги.
- **Фон**: звёзды, каркасный рельеф с холмами (canvas) и строки развёртки;
  декоративный, скрыт от читалок, не перехватывает клики.
- **Шрифты** из пакетов сборки (без запросов к Google: центр изолирован):
  заголовки, меню, полоски окон — Press Start 2P (с кириллицей); текст
  интерфейса — Pixelify Sans; данные — моноширинный.
- Неона и свечения по минимуму: мягкий ореол только у пиксельных подписей.
- Состояния по-прежнему не только цветом (текст/иконка), контраст текста
  не ниже 4.5:1; анимации отключаются при `prefers-reduced-motion`.
