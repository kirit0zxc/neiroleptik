# Спецификация: frontend HoneyForge

| | |
|---|---|
| Статус | **черновик** — до согласования контрактов в D1 |
| Владелец | участник 1 (frontend) |
| Код | `frontend/` |
| Основание | ТЗ «Мадригал. Конструктор» (FR-C1…C7, FR-A5…A6, §7.3, §10), план команды «HoneyForge — план на 5 дней» |

## 1. Назначение и границы

Пульт оператора SOC: вход, парк ловушек, конструктор профилей, запуск и
команды, живая лента событий, паспорт атаки (timeline, replay,
артефакты, honeytoken, алерты), CSV IoC, аудит.

**Входит:** интерфейс, клиент API и потока событий, моки, тесты UI и E2E.

**Не входит:** проверка прав (её делает API; UI только скрывает
недоступное), формирование CSV (делает сервер), STIX, геокарта,
LLM-сводка. Маскот «Юми» — только зарезервированное место (раздел 9).

## 2. Термины

| Термин | Что это |
|---|---|
| Профиль | Шаблон ловушки; каждое сохранение — неизменяемая ревизия |
| Ловушка (deployment) | Профиль определённой ревизии на хосте |
| Хост / агент | Runtime-узел и его агент; статус связи ≠ статус ловушки |
| Job | Асинхронная операция: requested → leased → running → succeeded / failed / expired |
| Событие | Запись v1 из `contracts/` (`event_id`, `type`, `occurred_at`, …) |
| `stream_seq` | Монотонный номер публикации события для живой ленты |
| Паспорт атаки | Экран сессии: timeline, replay, артефакты, honeytoken, алерты |

## 3. Требования

### 3.1. Доступ

- **F1.** Без сессии доступны только «Вход» и ошибки; остальное
  перенаправляет на вход и возвращает на исходную страницу после входа.
- **F2.** Роли `admin` / `operator` / `viewer`: viewer не видит кнопок
  изменения; запрет всё равно определяет API (403 → «нет прав»).
- **F3.** 401 на любом запросе — «сессия истекла», переход на вход.

### 3.2. Парк и ловушки

- **F4.** Список хостов: online / offline / degraded, last_seen,
  backlog, свободный диск. Online — это связь, а не работа ловушки.
- **F5.** Список ловушек: уровень (low / medium / high), состояние
  (planned / deploying / running / stopping / stopped / failed),
  desired и applied revision. Если ревизии не совпадают — «drift»
  (предупреждение), а не успех.
- **F6.** Команды start / stop / apply_config / rotate_credentials /
  reset — только operator/admin, с подтверждением; reset — только High.
  После команды виден прогресс job до итогового состояния.
#### Команды ловушки (F6, черновик до OpenAPI)

`POST /api/v1/deployments/{id}/commands` с телом
`{command, idempotency_key}` → `202 {job_id}`; прогресс —
`GET /api/v1/jobs/{id}` → `{job_id, deployment_id, command, state, error}`,
`state`: requested → leased → running → succeeded / failed / expired.
`idempotency_key` — новый UUID на каждое нажатие: повтор того же запроса
(обрыв сети) не создаёт второе задание.

| Команда | Доступна, когда | Подтверждение |
|---|---|---|
| `start` | stopped, failed, planned | нет |
| `stop` | running | да |
| `apply_config` | running и есть drift (applied ≠ desired) | нет |
| `rotate_credentials` | running, уровень medium или high | да |
| `reset` | только high, running или failed | да: «доказательства сохранятся, среда вернётся к чистому образу» |

- Кнопки только у operator и admin; у viewer их нет (запрет всё равно
  проверяет API).
- Пока у ловушки идёт задание, её кнопки неактивны; виден ход задания
  («поставлено → взято агентом → выполняется»).
- Задание опрашивается раз в секунду до итогового состояния; затем
  список ловушек перечитывается.
- Итог: «выполнено» / «ошибка: <текст>» / «истекло — агент не взял
  задание вовремя». 409 от API (у ловушки уже есть задание) — понятное
  сообщение, без повторной отправки.

#### Мастер запуска (F7, черновик до OpenAPI)

Адрес `/fleet/new`, кнопка «+ Запустить ловушку» в парке (operator и admin).

1. **Хост.** Список хостов: online — можно выбрать; degraded — можно, с
   предупреждением (очередь, свободное место); offline — нельзя.
2. **Профиль и ревизия.** Профиль из списка; ревизия — по умолчанию
   последняя, можно выбрать любую из истории (ловушка привязывается к
   неизменяемой ревизии). Профиль уровня High — только на хост с
   возможностью `kvm` (`host.capabilities`); иначе выбор недоступен с
   объяснением.
3. **Проверка.** Сводка: хост, профиль, ревизия, уровень, сервисы и
   порты. «Запустить» → `POST /api/v1/deployments`
   `{host_id, profile_id, profile_revision, idempotency_key}` →
   `202 {deployment_id, job_id}`.
4. **Ход.** Тот же ход задания, что у команд; итог — «Ловушка
   запущена» со ссылкой в парк, либо ошибка и «Назад».

Шаги проходятся по порядку («Далее» / «Назад»); выбранное не теряется при
возврате. Ошибка 422 показывается на шаге, к которому относится поле.

- **F7.** Мастер запуска: хост → профиль и ревизия → запуск (202 +
  job_id) → прогресс → результат или ошибка.

#### Обзор (`/`, черновик до OpenAPI)

Первый экран после входа — состояние парка и атак одним взглядом.

- Плитки из `GET /api/v1/analytics/summary` →
  `{deployments: {total, running, failed}, hosts: {total, online, degraded},
  events_last_hour, alerts_open}`; перечитываются раз в 15 с.
  - «Ловушки»: работают из всего; упавшие — красным с числом.
  - «Хосты»: на связи из всего; с ошибками — жёлтым.
  - «События за час».
  - «Открытые алерты»: больше нуля — красным.
  Каждая плитка ведёт на свой экран (парк, события, алерты).
- «Последние события»: 10 последних (`GET /events?limit=10`), новые из
  потока сверху; ссылка «вся лента». Вывод — по правилам S1–S4.
- «Активные источники»: топ-5 IP за час из того же ответа
  (`top_sources: [{ip, count}]`); IP — ссылка на ленту с фильтром.
- Сводка не загрузилась — плитки показывают ошибку и «повторить»,
  последние события при этом работают.

### 3.3. Профили

- **F8.** CRUD профиля со всеми полями FR-C1: уровень, сервисы и порты,
  баннеры, учётные данные-приманки, логирование, параметры канала и
  маскировки, легенда. Проверка формы — Zod-схемой.
- **F9.** Сохранение создаёт новую ревизию; виден список ревизий.

#### Поля профиля (по контракту `openapi.json`: ProfileCreate / ProfileConfigInput)

Имя и описание — на верхнем уровне (`ProfileCreate`), остальное — в `config`
(`ProfileConfigInput`). Значения формы совпадают с ограничениями сервера.

| Поле | Правило |
|---|---|
| `name` | 1–80 символов, обязательно (верхний уровень) |
| `description` | до 500 символов (верхний уровень) |
| `config.interaction_level` | `low` / `medium` / `high` |
| `config.hostname` | легенда: RFC 1123, до 63 символов |
| `config.services[]` | 1–16 сервисов: `protocol` (`tcp` / `http` / `ssh`), `port` 1–65535 без повторов, `banner` до 200 символов |
| `config.credentials[]` | до 8 пар `username` (1–64, маска `[a-zA-Z0-9_.-]`) / `password` (1–128) — приманки; на чтение сервер отдаёт только `credential_usernames`, пароли при правке вводятся заново |
| `config.logging.max_payload_bytes` | 256–8192 (в форме — КиБ 1–8, пересчитывается в байты) |
| `config.channel` | `flush_interval_ms` 100–5000, `batch_size` 1–100 |
| `config.high` | только для High: `template` (`ubuntu-ssh-v1`), `ttl_seconds` 60–3600, `cpu` 1–2, `memory_mb` 1024–4096 |

Обновление профиля (`ProfileUpdate`) требует `expected_revision` — ожидаемую
текущую ревизию; при расхождении сервер отвечает 409. История ревизий —
`GET /profiles/{id}/revisions` (`RevisionRead`).

Сочетания уровней и протоколов:

- **Low** — только `tcp` и `http` (баннеры и заглушки);
- **Medium** — обязателен хотя бы один `ssh` (Cowrie), можно `http`;
- **High** — только `ssh` (шлюз к VM), ровно один сервис.

Учётные данные-приманки нужны Medium и High; для Low поле не показывается.
При смене уровня сервисы, которые ему подходят, сохраняются; иначе
подставляется набор по умолчанию для уровня (Low — HTTP 8080, Medium —
SSH 2222, High — SSH 2224). Выпадающий список протоколов всегда
показывает значение, реально записанное в форме.
Ошибки показываются у полей; сохранить можно только валидный профиль.
После сохранения — сообщение с номером новой ревизии.

### 3.4. События

- **F10.** Живая лента: новые события появляются без перезагрузки;
  состояние потока видно (live / переподключение / отстаём).
- **F11.** Фильтры: ловушка, период, IP источника, тип. Пагинация по
  курсору; браузер не загружает журнал целиком.
- **F12.** Восстановление после обрыва без потерь и дублей (раздел 5).
- **F13.** Время в API — UTC, на экране — локальное с часовым поясом.

#### Лента: фильтры и живой поток

- Фильтры: ловушка (`deployment_id`), тип (`type`), IP источника
  (`source_ip`, IPv4/IPv6 — проверяется до запроса), период: `from`
  **включительно**, `to` **исключительно**; в поле — локальное время, в
  API — RFC 3339 с часовым поясом (UTC, `Z`); `from` раньше `to`.
  Фильтры хранятся в адресе страницы — ссылкой можно поделиться, «назад»
  работает.
- Первая страница — `GET /api/v1/events?<фильтры>&limit=50`, ответ
  `{items, next_cursor}`, новые сверху; «Показать ещё» — следующая
  страница по `next_cursor` (курсор непрозрачный, frontend его не
  разбирает). `next_cursor: null` — страниц больше нет. При смене
  фильтров курсор сбрасывается.
- Живые события из потока добавляются сверху, **только если подходят
  под фильтры**; при заданном `to` в прошлом живые не добавляются.
- Пауза: новые события не сдвигают таблицу, а копятся в счётчике
  «N новых — показать».
- В памяти не больше 500 событий ленты; старые вытесняются (их можно
  снова догрузить по REST).
- Повтор события (тот же `event_id`) из REST и потока показывается один раз.
- Индикатор потока в шапке: «онлайн» / «подключение…» /
  «переподключение…» / «нет потока».

### 3.5. Расследование

- **F14.** Паспорт атаки: timeline событий сессии; клик по событию
  переводит replay к его моменту.
- **F15.** Replay: ввод и вывод по времени, пауза, скорость; обрезанные
  и неизвестные части отмечены. Чанк (согласовано с командой):
  `{seq, offset_ms, direction: "in" | "out", data_base64, truncated}` —
  `offset_ms` от начала сессии; байты декодируются потоковым UTF-8
  декодером отдельно для каждого направления (символ может быть разрезан
  между чанками); `truncated: true` показывается как пропуск данных.
  Проигрыватель текстовый: без HTML и опасных последовательностей (S2).
- **F16.** Артефакты: pending / available / failed / expired, размер,
  SHA-256; скачать можно только available.
- **F17.** Honeytoken и алерт показывают основание (исходные события).
- **F18.** Скачивание CSV IoC (файл формирует сервер).
- **F19.** Журнал аудита: кто, что, когда, результат.

### 3.6. Безопасность отображения

- **S1.** Данные атакующего (payload, команды, вывод, имена файлов,
  баннеры) выводятся только как текст: без `innerHTML`,
  `dangerouslySetInnerHTML` и автоматических ссылок.
- **S2.** В replay управляющие escape-последовательности терминала
  удаляются; остаются печатные символы, `\n`, `\t`. Также удаляются
  переключатели направления текста (U+061C, U+200E, U+200F, U+202A–U+202E,
  U+2066–U+2069) и невидимые символы U+200B, U+2060–U+2064, U+FEFF, чтобы
  нельзя было визуально подменить команду. ZWNJ/ZWJ сохраняются.
- **S3.** URL honeytoken не кликабелен и не предпросматривается.
- **S4.** Учётные данные атакующего замаскированы по умолчанию.
- **S5.** Артефакты не предпросматриваются; только скачивание.

## 4. Интерфейс с backend

Контракт стадии 1 — общий `contracts/openapi.json` (control API). Типы
frontend для поверхностей стадии 1 (auth, профили, хосты, развёртывания)
точно повторяют его схемы (`AuthRead`, `UserRead`, `ProfileRead`,
`ProfileConfigPublic`, `RevisionRead`, `HostRead`, `DeploymentRead`,
`DeploymentCreate`). Фикстуры `contracts/fixtures/*.draft.json` повторяют эти
формы для моков.

Поток событий, команды ловушек, задания и аналитика в контракте стадии 1
**отсутствуют** (см. `specs/architecture.md`, «Границы первого этапа»): это
работа этапов 3–4. Соответствующие экраны (лента, команды парка, обзор)
работают как помеченные превью на моках; их пути и формат события
(`event-v1.schema.json`) ещё не закреплены в OpenAPI и подлежат согласованию
с участником 4. Событие v1: `schema_version` (=1), `event_id`, `agent_id`,
`deployment_id`, `instance_id`, `session_id` (может быть `null`), `source_seq`,
`occurred_at`, `received_at`, `type`, `source`, `service`, `data`,
`artifact_ids`, `profile_revision`; уникальность — пара `(agent_id, event_id)`.

| Использует | Путь | Статус |
|---|---|---|
| Сессия | `POST /api/v1/auth/login`, `POST /api/v1/auth/logout`, `GET /api/v1/auth/me` | контракт |
| Профили | `GET/POST /api/v1/profiles`, `GET/PATCH /api/v1/profiles/{id}`, `GET /api/v1/profiles/{id}/revisions` | контракт |
| Парк | `GET /api/v1/hosts`, `GET/POST /api/v1/deployments` (создание — `planned`) | контракт |
| Команды и jobs | `POST /api/v1/deployments/{id}/commands`, `GET /api/v1/jobs/{id}` | превью (этап 3) |
| События | `GET /api/v1/events?after=&limit=`, `WS /api/v1/stream`, `GET /api/v1/stream-events?after=&until=&limit=` | превью (этап 4) |
| Аналитика | `GET /api/v1/analytics/summary` | превью (этап 4) |

Вход: тело `{username, password}` (`LoginInput`); ответ `AuthRead`
(`{user: {id, username, role}, csrf_token}`). Пагинация ленты — `after=<next_cursor>`.

**Сессия и CSRF.** Сессия — HttpOnly-cookie `hf_session`; все запросы с
`credentials: 'include'`. CSRF-токен приходит полем `csrf_token` в ответах
`POST /api/v1/auth/login` и `GET /api/v1/auth/me`; frontend хранит его
только в памяти и отправляет в заголовке `X-CSRF-Token` на изменяющих
запросах (POST, PUT, PATCH, DELETE). WebSocket — по cookie и проверке
Origin, без CSRF.

**Ошибки** — контейнер `detail`: строка (`{"detail": "…"}`) или для 422
список `{loc, type, msg}`; исходный ввод в ошибку не включается. Логика
frontend опирается на HTTP-статус, а не на текст: 401 — сессии нет
(кроме входа: там это неверный пароль), 403 — нет прав, 409 —
конфликт версий («перечитайте»), 422 — ошибки полей (по `loc` в форму),
5xx — сбой сервера. Текст `detail` только показывается.

## 5. Поток событий (`StreamClient`)

Источник истины — БД; WebSocket только доставляет новое. `stream_seq` и
`watermark` — **строки** с целым числом (сравниваются как BigInt), чтобы
не терять точность JavaScript number.

Сообщения WebSocket `/api/v1/stream`:

```json
{"type": "hello", "watermark": "120"}
{"type": "event", "stream_seq": "121", "event": {"event_id": "…", "…": "…"}}
```

Догрузка: `GET /api/v1/stream-events?after=100&until=120&limit=100` →
`{items: [{stream_seq, event}], watermark, next_cursor}`; на всех
страницах тот же `until`, следующая — по `next_cursor`.

Алгоритм:

1. Подключить WS; все `event` до окончания догрузки складывать в буфер.
2. Дождаться `hello` и его `watermark`.
3. Первое подключение (курсора нет): история не догружается — её даёт
   `GET /events`; курсор = `watermark`. Переподключение: догрузить
   `after=<курсор>&until=<watermark>` постранично.
4. Слить догруженное и буфер по возрастанию `stream_seq`, отбросить записи
   с `stream_seq` ≤ курсора и повторы по `event.event_id`.
5. Передать подписчикам; курсор сдвигать только после передачи.
   Каждый подписчик получает только записи новее последней принятой им.
   Если подписчик бросил исключение, курсор не сдвигается, и при повторе
   записи получит только он; остальные дублей не видят.
6. Обрыв — повторное подключение с нарастающей задержкой
   (1 → 2 → 4 … до 30 с), с шага 1.

Коды закрытия WS: **4401** — сессия истекла или отозвана → переход на
вход; **4403** — нет доступа → поток остановлен, без переподключения;
**1006** и прочие сбои — проверить `GET /auth/me` (401 → вход, иначе
переподключение).

Состояния: `connecting` → `live`; при обрыве `reconnecting`; 4403 —
`forbidden`. Подписчики: лента, обзор, адаптер маскота.

## 6. Состояния и ошибки

| Ситуация | Поведение |
|---|---|
| Загрузка | Скелетон, не пустой экран |
| Пустой список | Объяснение и действие («создать профиль») |
| Ошибка API | Сообщение и «повторить»; остальной экран работает |
| 401 / 403 | Вход / «нет прав» |
| Поток оборван | Лента остаётся, индикатор «переподключение» |
| Неизвестный тип события | Показ как «неизвестное событие», без падения |

## 6a. Оформление

Решение команды: тёмный интерфейс в стиле плавающего окна Юми — продукт и
маскот выглядят одним целым.

- **Общие токены** в `app/theme.css` — единственный источник цветов,
  шрифтов, рамок; окно Юми (`--yumi-*`) берёт значения из них же.
  - окно: `--win-border`, `--win-border-dark`, `--win-title`,
    `--win-title-text`, `--win-body`, `--win-shadow`;
  - фон и текст: `--bg`, `--text`, `--text-dim`; состояния: `--ok`,
    `--warn`, `--bad`, `--idle`; акценты: `--accent`, `--accent-2`.
- **Панель = ретро-окно**: заголовок-полоска цвета `--win-title` с
  пиктограммой и пиксельным шрифтом, рамка 3 px, ступенчатая тень,
  тёмное тело. Так же оформлены плитки обзора, фильтры, карточка входа,
  диалоги.
- **Шрифты**: заголовки окон — Pixelify Sans из пакета сборки (без
  запросов к Google: центр изолирован); данные — моноширинный; текст
  интерфейса — системный.
- Состояния по-прежнему не только цветом (текст/иконка), контраст текста
  на заголовке окна — не ниже 4.5:1.

## 7. Нефункциональные требования

- **Производительность:** лента держит 1000+ событий без подтормаживаний
  (окно в памяти + виртуальный скролл); первая загрузка ≤ 300 КБ gzip JS
  без графиков.
- **Доступность:** клавиатура, видимый фокус; состояние не только цветом
  (текст или иконка).
- **Совместимость:** последние Chrome / Edge / Firefox; ноутбук и проектор.
- **Безопасность:** S1–S5; никаких секретов в коде и сборке.
