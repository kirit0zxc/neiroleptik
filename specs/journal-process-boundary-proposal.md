# Предложение: доверенный протокол границы процесса журнала Low

**Статус:** предложение к согласованию (AGENTS §7), не реализованный контракт.
**Уточнение 11.10.2026:** сборщик предложил вариант A — атомарный JSON-снимок.
Ниже конкретизирован §6; поля актуальности, барьер завершения и свёртка записей
ещё требуют совместного подтверждения. Реализация runtime/сборщика не менялась.
**От:** участник 3 (runtime, Данил). **Кому:** Дима (читатель/сборщик), с участием backend (доверенный сигнал).
**Зачем:** снять блокировку читателя на «переходе через незакрытый predecessor и поздний `previous=null`». Нужен безопасный порядок пересечения границы процесса без молчаливого сброса checkpoint.

Опора: `honeypots/low/journal.py` (`RotatingJournalSink`) и `specs/low-journal-v1.md`.

---

## 1. Проблема

Читатель (сообщение Димы) сейчас блокирует переход через незакрытый предшествующий файл и поздний `previous_journal_id = null`: нет доверенного признака, что предыдущий процесс действительно завершил запись и файл можно считать финальным. Контент журнала сам по себе этого не доказывает.

---

## 2. Что писатель гарантирует (из кода и спеки)

- **`journal_seq` выбирается по памяти sink и существующим именам.** Номер = `max(в памяти, максимум в каталоге) + 1`, файл создаётся `O_EXCL`. Отказ до создания не расходует номер. Ошибка header с неудачным удалением созданного файла может оставить имя и пропуск; новый sink после удаления всех старых файлов теряет дисковый максимум. Поэтому непрерывность номеров через любой сбой не обещается. Этот sink не перезаписывает существующий файл; `O_EXCL` сам по себе не доказывает единственность писателя.
- **Поля заголовка:** `schema, journal_id, journal_seq, previous_journal_id, instance_id, deployment_id, profile_revision, opened_at, first_seq`.
- **Концовка при попытке штатного закрытия:** sink пишет `footer{journal_id, last_seq, closed_at, reason=rotation|shutdown}` и пытается выполнить `fsync` при ротации/закрытии. Авария до этой операции может оставить файл без footer; авария после записи footer либо отказ fsync/обрезания могут оставить видимую концовку без успешно завершённой синхронизации. Сам footer не доказывает успешное закрытие, сохранность при потере питания или seal.
- **Запись строк.** Файл открыт без буфера; при ошибке записи sink пытается обрезать хвост до последней подтверждённой записи и закрывает файл. Обрезание тоже может не удаться. Следующая попытка события открывает новое поколение. Неполная строка без LF не создаёт Event. `fsync_each_event` включает fsync каждого события; обычный режим не доказывает устойчивость каждой строки к потере питания.
- **Порядок при одном писателе:** `(journal_seq, смещение строки)`. Ключ идемпотентной позиции — доверенная привязка + `journal_id + byte_offset`; UUID сам не задаёт порядок файлов.

---

## 3. Что писатель НЕ гарантирует на границе процесса

- **`previous_journal_id` через границу процесса.** Связь ведётся в памяти (`self._previous_id`). Новый sink начинает с `None`, даже при старых файлах того же UUID. Поздний null отмечает отсутствие восстановленной связи; сам по себе он не доказывает смерть старого процесса или единственность нового.
- **`seq` через границу процесса.** Новый процесс Low начинает счётчик с нуля. Рестарт только агента при живом Low не сбрасывает этот счётчик. Действующая спека допускает новый процесс с прежним instance; это не доказательство завершения старого писателя. Исполнитель при отсутствии контейнера своей попытки возвращает RECOVERY_UNCERTAIN, а не делает повторный run. Предлагаемый запрет нового запуска UUID действует после finalized-барьера (§6.2) и ещё не реализован. Пропуск seq может быть отказом emit внутри одного процесса, а не перезапуском.
- **Хвост аварийного файла.** Без концовки часть событий могла не дойти до диска — это **пропуск**, не ошибка формата. Наличие/отсутствие концовки не является seal.

## 4. Модель границы

| Случай | Признаки | Трактовка |
|---|---|---|
| Чистая ротация (внутри процесса) | predecessor закрыт `footer{reason=rotation}`; у наследника `previous_journal_id` = journal_id predecessor; `seq` продолжается | Цепочка цела; читать последовательно |
| Штатная остановка | `footer{reason=shutdown}` | Структурное завершение по заявлению писателя; полнота захвата, отсутствие другого писателя и доставка не доказаны |
| Возможная граница процесса / разрыв | `previous_journal_id=null` при `journal_seq>1` или повтор seq; предшественник может быть без footer | Отметить разрыв; не сбрасывать checkpoint; окончательное завершение подтвердить по §6 |
| Новый экземпляр | другой `instance_id` (новая попытка start; пересоздание на уровне драйвера) | Разные экземпляры; порядок между ними — по доверенному реестру, не по контенту. Исполнитель выполняет только start/stop для Low; неподдерживаемые действия получают failed ACK с UNSUPPORTED_COMMAND. Этот документ не добавляет действия командного API |

## 5. Протокол для читателя (предложение)

1. **Канонический порядок** доступных файлов при подтверждённом единственном писателе — `(journal_seq, byte_offset)`, а не seq. Пропуски номеров и повтор номера с другим journal_id диагностируются; непрерывность не выдумывается.
2. **Независимый checkpoint** на доверенную привязку и journal_id. `(instance_id,journal_seq)` — индекс поиска, а не второй независимо изменяемый checkpoint. Null никогда не сбрасывает прогресс старого файла.
3. **Обнаружение разрыва:** поздний null, повтор seq или несовпадение predecessor → диагностика, не доказательство нового процесса. Пропуск seq из-за ошибки emit тоже возможен. Необратимый переход через спорный predecessor ждёт условий §6.
4. **Незакрытый файл (без footer):** читать все полные LF-строки; не продвигать checkpoint за неполную последнюю строку без LF. Концовка для чтения байт не требуется.
5. **Финальность:** применяются только условия §6. Больший номер в недоверенном каталоге сам по себе не доказывает закрытие предыдущего файла. Пока условия не подтверждены, читать полные строки и сохранять позиции; спорный переход не финализировать.
6. **Финальный ≠ полный ≠ удаляемый.** Отсутствие концовки = возможный пропуск: читатель фиксирует gap. Удаление файла по этому признаку запрещено — нужен seal/подтверждение сохранности (барьер cleanup, отдельное согласование).
7. **Идентичность.** `instance_id`, `deployment_id`, ревизию сверять с доверенной конфигурацией агента / реестром экземпляров, а не доверять контенту журнала (спека 3.4). Session выводить из доверенной привязки и `connection_id`, не из `journal_id`.

## 6. Что runtime добавит, чтобы снять блокировку

### 6.1. Снимок и актуальность наблюдения

Предложение сборщика A: отдельный `instances.json`, атомарно заменяемый runtime.
В заголовке: `format`, доверенный `host_id`, `publisher_epoch` (новый UUID на
каждый запуск исполнителя), `snapshot_seq` (строго возрастает внутри epoch),
`generated_at` и массив `instances`. Изменения происхождения UUID сначала
фиксируются в ExecutionStore; наблюдение живого писателя получается отдельно.
Нельзя считать старый result/phase свежим наблюдением Docker.

На канонической записи экземпляра:

| Поле | Смысл |
|---|---|
| `writer_alive` | `true` — успешно наблюдён принадлежащий instance живой писатель; `false` — успешная полная сверка не обнаружила живого писателя; `null` — неизвестно |
| `writer_observed_at` | UTC-время начала фактической успешной проверки; не время перепубликации старого результата |
| `writer_valid_until` | Предложение: `writer_observed_at + 15 s`; истёкшее наблюдение становится unknown |
| `writer_finalized` | Долговечно зафиксированный запрет дальнейшей записи этого instance; условия в §6.2 |

Предлагаемый интервал проверок — 5 s. Публикация по accept/run/complete/abandon,
изменению наблюдения и по таймеру; таймер не обновляет возраст старого inspect.
Числа 5/15 s — параметры для согласования, не уже реализованный SLA.

Ошибка/timeout inspect, спорные метки, неизвестный исход Docker-операции или
непроверенное состояние после рестарта дают `null` с пустыми timestamps.
Истёкшее `true/false` читатель трактует как unknown. `failed`, `abandoned`, ACK,
generation и `superseded` сами не дают false или finalized.
Отсутствие контейнера по имени не доказывает отсутствие других писателей UUID:
сверка должна покрыть все принадлежащие этому instance ресурсы и операции.

Читатель проверяет срок каждого instance, не только generated_at. Отсутствующий,
недоступный/повреждённый снимок, конфликт, откат snapshot_seq и возврат к уже
заменённому epoch не разрешают финализацию. Возраст кэша дополнительно ограничен
15 s по монотонным часам читателя; повтор чтения той же версии его не продлевает.
Для UTC нужна согласованная синхронизация часов. Timestamp из будущего дальше
5 s, обнаруженный скачок времени или невозможность проверить время дают unknown.

При новом запуске runtime сначала публикует новый epoch с неизвестными текущими
наблюдениями, затем выполняет reconciliation. Рестарт исполнителя не доказывает
остановку Low. Потеря lease не отменяет уже начатый Docker run: пока его исход
и возможные писатели не сверены, финальность не подтверждается.

### 6.2. Почему fresh false недостаточно

False — наблюдение момента. Prepared-попытка ещё может стартовать; run уже может
выполняться; остановленный контейнер может быть перезапущен. Поэтому для новейшего
файла без footer предлагается дополнительный **барьер `writer_finalized=true`**:

1. Все начатые операции этого instance завершены и сверены; незавершённого run нет.
2. Все его писатели подтверждённо прекращены, их ресурсы удалены либо ограждены
   от повторного запуска. Неопределённая остановка/ошибка backend барьер не дают.
3. UUID закрыт для следующих start/recovery с запуском: следующая жизнь Low
   получает новый instance_id. Это ограничение должно соблюдаться runtime и
   оператором; повторное использование закрытого UUID — нарушение/конфликт.
4. Барьер записан в устойчивое состояние до публикации. Фаза команды или ACK
   этого не заменяют. Для завершения процесса нет необходимости ждать сеть ACK.

До барьера публикуется finalized=false, даже при свежем writer_alive=false.
При противоречии «живой писатель у уже finalized UUID» нельзя молча снять барьер
и продолжить тот же поток: привязка блокируется, runtime сообщает конфликт.
После рестарта барьер не забывается; неизвестная текущая сверка остаётся unknown.
Новая свежая запись false+finalized после reconciliation вновь разрешает решение.

### 6.3. Несколько записей одного instance

Ключ — `(host_id, deployment_id, instance_id)`, а не только UUID из журнала.
Предлагаем экспортировать **одну каноническую запись** на ключ. Все причины, по
которым он известен (attempt/expected/result/history, разные команды), находятся
в массиве `references`. Фаза/ACK относятся к конкретной reference; актуальность
писателя относится к целому instance и не копируется из последнего результата.
`revision` экземпляра — исторически применённая/наблюдённая ревизия; целевая
`requested_revision` команды не должна её подменять.

Если читатель всё же получил несколько записей ключа, он:

1. Проверяет неизменяемую привязку и известные revision; противоречие блокирует
   привязку этого ключа. Null revision не является разрешением брать её из header.
2. Объединяет согласованные references, удаляя точные дубли. Ключ reference —
   `(command_id, role)`, а для history без command_id — `(history, generation)`.
   Конфликт одного ключа блокирует новую привязку и финализацию instance до
   исправления; сохранённые raw/checkpoint остаются. Не выбирает «последнюю generation»:
   stop и ошибки тоже увеличивают generation, сохраняя прежний instance.
3. Принимает writer-состояние только если все записи содержат одинаковый набор
   `writer_alive/observed_at/valid_until/finalized` из одного снимка и он свежий.
   Несогласованные/отсутствующие данные дают unknown и запрет финализации;
   false в одной исторической строке не перекрывает true/unknown другой.

`superseded` означает замену другим instance, а не просто рост generation и
не подтверждение смерти писателя. История прежних UUID сохраняется для поздних
журналов; исчезновение записи не считается false или разрешением удаления.

### 6.4. Решения читателя

| Состояние после проверки привязки/свежести | Действие |
|---|---|
| true, finalized=false | Читать целые строки, ждать дописывания новейшего файла |
| false, finalized=false | Читать целые строки; окончательную границу пока не фиксировать |
| false, finalized=true | Разрешить закрыть чтение файла «как записан», сохранив полный raw и отметив оборванный хвост/gap при отсутствии footer |
| unknown/stale/конфликт или true+finalized | Не принимать новое решение о финальности; сохранять позиции, ждать сверки/исправления |

Более высокий journal_seq можно использовать для перехода внутри процесса только
после подтверждения доверенной привязки и единственного писателя, который по
согласованному контракту закрывает предыдущий файл до открытия следующего и не
переоткрывает его. Параллельные писатели/повтор UUID/неподтверждённое условие —
не разрешают это упрощение. Поздний null не сбрасывает checkpoint и не заменяет
барьер. Уже сохранённая позиция не перематывается при истечении снимка.

Финальность чтения не доказывает полноту захвата, неизменяемость недоверенных
байтов или право удаления. Повторная проверка префикса, seal/raw receipt и
cleanup — отдельные гарантии. `last_active_journal_seq` runtime не экспортирует.

### 6.5. Минимальная совместная приёмка

- Publisher остановлен, а Low жив: snapshot истекает; читатель не финализирует.
- Prepared без писателя и in-flight run: false/unknown без барьера не закрывают файл.
- Подтверждённый stop/crash: fresh false+finalized закрывают новейший файл без footer;
  целые строки/хвост сохранены, gap отмечен, удаление не запускается.
- Рестарт исполнителя, epoch/sequence rollback, старое observed_at в новом снимке:
  старые результаты не становятся свежими; reconciliation сохраняет checkpoint.
- Один instance в start/stop/failed/history: references объединяются, writer
  определяется наблюдением, не generation/phase. Конфликт false/true блокирует переход.
- Больший journal_seq при двух писателях либо без доверенной привязки не финализирует
  predecessor. Поздний null и пропуск seq отдельно отмечаются без обнуления позиции.
- Повторный запуск закрытого UUID, подмена привязки/revision и ошибка inspect:
  диагностика/ожидание, никаких фиктивных terminal false.

3. Подтвердить каноническую запись с references и обработку дублей §6.3;
   совместно закрепить JSON-формат/контрольные примеры и event ID namespace.
4. Отдельно согласовать cleanup/seal/raw receipt: §6 не разрешает удаление.
5. Обновить действующие specs в runtime PR после согласования. Этот документ
   не меняет honeyforge-low-journal/1, командный OpenAPI или реализацию сборщика.

## 8. Границы ответственности

- **Runtime (я):** актуальные наблюдения/экспорт §6, устойчивый барьер, управление
  единственностью/жизненным циклом писателя и точное описание ограничений §2–§3.
- **Дима:** порядок по `(journal_seq, offset)`, независимые checkpoint, отметки разрыва и gap, чтение без footer — §5.
- **Backend/центр:** проверка принадлежности экземпляра и приём событий незарегистрированного/завершённого экземпляра (увязано с реестром).

Реализация runtime-части начинается после согласования §6–§7. Экспорт JSON,
freshness и finalized-барьер ещё не реализованы. Сроки D1–D5 сохраняются;
предложения не являются отчётом о живом Docker/Linux/центр/UI-прогоне.
