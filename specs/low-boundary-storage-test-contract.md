# Обязательные тесты реализации

Это тестовый контракт для соседнего чата, не готовый исполняемый pytest
и не отчёт об успешном прогоне. Реализация должна добавить настоящие тесты
против выбранных внутренних интерфейсов; пустые skeleton/skip не считаются.

## Фикстуры и оракул

Использовать реальные временные SQLite-файлы, WAL, отдельные connections.
Генерировать небольшие валидные журналы существующими fixtures. Подготовленный
переход P1: writer A → B, P2: B → C в той же области. Есть полный старый raw,
явная тестовая начальная привязка, canonical bytes proof и header с LF.
Неполный хвост содержит в том числе невалидный UTF-8 и сохраняется буквально.
Эта фикстура не является доверенным production proof.

Оракул состояния снимает через независимое соединение логические строки всех
затронутых таблиц, bytes, checkpoints, текущую привязку, историю и usage.
Не сравнивать файлы SQLite побайтно: WAL и внутреннее размещение могут меняться.
Ожидаемые bytes/суммы вычислять из исходных фикстур, не методом реализации.

## A. Миграция

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| M01 | Пустая spool, первое и повторное открытие | Одна актуальная версия, стабильная схема, нет выдуманного anchor. |
| M02 | Legacy spool с raw, обоими видами checkpoint, ledger, pending, quarantine, batch snapshots | Все значения и порядок pending сохранены; usage равен исходным raw bytes. |
| M03 | Ошибка после каждого изменяющего шага миграции | После переоткрытия старое целостное состояние; новая версия не выставлена; повтор миграции успешен. |
| M04 | Неизвестная будущая версия | Понятный отказ без изменения таблиц и metadata. |
| M05 | Старые данные больше новой квоты | Ничего не удалено; новые увеличивающие запись операции отклонены. |
| M06 | Legacy raw без anchor, попытка перехода | Требуется начальная привязка; raw доступен; новый writer отсутствует. |
| M07 | Spool другого agent | Отказ без изменения данных/версии чужого владельца. |

Legacy-файл создавать явной старой схемой и данными, а не текущим constructor,
иначе тест может незаметно проверять повторную инициализацию вместо миграции.

## B. Raw и владение транзакцией

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| R01 | Прежний append: первая строка, повтор, конфликт bytes, неверный offset/header | Сохраняется прежний контракт и безопасные ошибки. |
| R02 | Внешний BEGIN, внутренняя запись, чтение другим connection, ROLLBACK | До commit запись невидима; после rollback нет raw/checkpoint/location/usage. |
| R03 | Та же запись с внешним COMMIT | Все связанные данные видны одновременно после commit. |
| R04 | Нет активной транзакции либо чужой connection/agent | Явный отказ; нет частичной записи. |
| R05 | Исключение после raw INSERT до checkpoint | Владелец откатывает всё; повтор успешен. |

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| B01 | Валидный подготовленный P1 | accepted, A sealed, B active, proof/закрепления/точный хвост записаны; новый checkpoint после LF header. |
| B02 | Хвост 25 bytes после LF-границы 885 | Старый checkpoint 885; хвост [885,910) сохранён; из хвоста нет Event/ledger/pending. |
| B03 | Повтор P1 сразу и после переоткрытия | repeated; состояние/usage неизменны. |
| B04 | P1, P2, повтор P1 с устаревшей ожидаемой версией | repeated, текущий writer остаётся C; версия и usage не меняются. |
| B05 | Тот же ID, другие canonical bytes | conflict; исходный proof не перезаписан. |

| B11 | ACK обычных событий после принятия | Proof, raw, хвосты, история, привязка и закрепления сохранены; существующий контракт pending/ledger не сломан. |

## D. Квоты и конкуренция

| ID | Сценарий | Ожидаемый результат |
| --- | --- | --- |
| Q01 | Proof ровно 1 MiB и +1 byte | Первый допустим по лимиту хранения, второй отклонён целиком. |
| Q02 | 1, 64, 65 и 0 журналов | 1/64 допустимы, 0/65 отклонены. |
| Q03 | Сумма хвостов ровно 4 MiB и +1 byte | Граница допустима; превышение не обрезается. |
| Q04 | raw + proof + tails + новый header ровно общий бюджет и +1 byte | Первый commit; второй без мутаций. |
| Q05 | Повтор при исчерпанной/сниженной квоте | repeated без дополнительных bytes. |
| Q06 | Обычный append после заполнения бюджета proof/хвостами | Нельзя обойти общий лимит проверкой только raw. |
| Q07 | Два connections одновременно принимают один proof | После разрешения busy/retry один accepted, другой repeated; одна запись/квота. |
| Q08 | Два разных перехода от одной версии привязки | Один accepted; второй conflict после повторной проверки; нет развилки. |
| Q09 | Конкурирующие raw append и принятие почти на лимите | Совокупное использование не превышает бюджет, проигравшая операция целиком откатывается. |

Синхронизировать конкуренцию барьерами/events, не вероятностными sleep.
Q01 проверяет предел внутреннего хранения подготовленных bytes, а не
допустимость произвольного padding в будущей внешней схеме proof.

## E. Сбои и долговечность

Параметризовать fault injection по шагам: proof INSERT, закрепления, хвосты,
sealed старого writer, новый writer, raw header, checkpoint, привязка, usage,
непосредственно перед COMMIT. Для каждой точки после ошибки/переоткрытия
состояние равно исходному; повтор даёт ровно одно accepted. Проверять также
ошибку COMMIT через узкий контролируемый адаптер; не подменять весь repository.

Отдельные обязательные проверки:

1. Дочерний процесс открывает БД, пишет часть перехода и завершается аварийно
   без close/rollback. Родитель открывает БД: целостность и исходное состояние.
2. Дочерний процесс завершает COMMIT и аварийно выходит до ответа. Родитель
   повторяет P1: repeated, все записи ровно одни, usage точный.
3. SQLite write failure (например, контролируемый SQLITE_FULL в выделенной
   тестовой БД) не оставляет нового writer или частичной истории. Не заполнять
   диск пользователя. Инъекцию ошибки обозначить как инъекцию, не живой диск-тест.
4. При удерживаемом write lock возвращается безопасная ошибка/busy с возможностью
   повтора; она не классифицируется как accepted или конфликт содержимого.

Crash-процесс должен сообщать достигнутую точку через IPC. Его ненулевой выход
ожидаем; тайм-аут/недостигнутая точка — провал теста, а не успешный crash-тест.

## F. Регрессия и команды

Запустить текущие `test_low_journal_durable.py`, `test_raw_conversion.py`,
collector/reader/rotation/ACK/replay тесты и полный `tests/telemetry`.
Добавить проверку: поздний `previous_journal_id=null` без интегрированного
доверенного consumer по-прежнему ждёт, старый verified raw конвертируется.
Само наличие таблиц boundary не включает автоматическое принятие.

Ориентировочные команды (сверить с актуальным CI, Python 3.12):

```powershell
uv sync --frozen
uv run pytest tests/telemetry
uv run ruff check agent honeypots infra tests
uv run ruff format --check agent honeypots infra tests
uv run mypy
uv build --wheel
```

Зафиксировать команды, exit codes, числа passed/failed/skipped и причины
пропусков. Моки файлового доверия не доказывают Linux права; тест prepared
перехода не доказывает совместимость с producer. Не добавлять фиктивный
producer или ослаблять проверки footer ради прохождения этой задачи.
