# Спецификация: подготовленный Low boundary в SQLite spool

## 1. Статус и область

Изолированный реализованный слой хранения, 14.10.2026. Согласованные
инварианты бэкенда отделены от предлагаемых внутренних интерфейсов ниже:
имена классов/методов не являются внешним контрактом. Публичные HTTP/WS,
Event DTO, source_seq, mapper version и алгоритмы Event ID не меняются.

Результат — изолированный слой хранения с тестами. Наличие его метода
не разрешает production-переход. Доверие, файловая валидация, начальная
авторизация и правила чтения перехода будут реализованы отдельным изменением.

## 2. Данные и область уникальности

Все сущности находятся в существующей SQLite spool raw/checkpoints/ledger/pending.
История процесса scoped по `(agent_id, deployment_id, instance_id)`;
revision проверяется, но не сбрасывает историю. В этой поставке переход
между revision запрещён. Сохраняются:

- Неизменяемые canonical proof bytes и digest; boundary ID, seq, previous ID.
- Текущая привязка и её версия для конкурентной проверки; начальная
  доверенная привязка не создаётся автоматически при миграции.
- История writer/container с состояниями active/sealed и ссылками на переходы.
- Закрепление журналов: writer, journal ID/seq, snapshot ref, digest, размер,
  LF-граница, footer_present. Это метаданные внешних snapshots, не их копия в БД.
- Непрозрачные BLOB хвостов с offset, длиной и digest.
- Учёт логических байтов и версия миграции.

Boundary ID и seq уникальны внутри области. Writer/container и journal ID
не переиспользуются внутри её истории. Один текущий writer на область.
Не обходить существующие ограничения raw и ledger. Метаданные закрепления
после принятия неизменяемы; чужой source_key не может быть включён в переход.

## 3. Внутренние операции

### Raw в транзакции

Выделить из `RawJournalRepository.append()` внутреннюю операцию записи
в переданный transaction context/connection. Она сохраняет прежние проверки,
результат точного повтора, raw, checkpoint, location и учёт bytes, но не делает
BEGIN, COMMIT, ROLLBACK, executescript или закрытие соединения самостоятельно.
Владелец транзакции управляет её завершением. Контекст обязан относиться
к нужной spool/agent и иметь активную транзакцию; неверный контекст отклоняется.
Существующий публичный append остаётся самостоятельной атомарной обёрткой,
совместимой с действующими вызовами. Частичная запись при ошибке невозможна.

### Сохранение подготовленного перехода

Пример внутреннего интерфейса: `accept_prepared_transition(prepared)`.
Тип входа неизменяемый; содержит область/revision, ожидаемую версию текущей
привязки, boundary ID/seq/previous ID, canonical proof bytes, старого/нового
writer, перечень проверенных старых журналов и их LF-границ, точные bytes
хвостов и нового header, его journal identity. Не принимать пути для чтения
произвольных файлов внутри операции. Дублированные поля входа должны быть
согласованы; неоднозначный пакет отвергается, а не нормализуется догадкой.

Внешний валидатор в будущем отвечает за автора proof, canonical schema,
полноту snapshots, hash файлов и правила process seq. Хранилище отвечает
за структурную согласованность своего входа, привязку к сохранённому состоянию,
конкуренцию, уникальность, неизменяемость, квоты и атомарность. Не изображать
отсутствующий внешний валидатор проверкой одного SHA-256.

В одной `BEGIN IMMEDIATE`:

1. Найти принятый proof в области. Совпадают ID и точные canonical bytes —
   вернуть repeated без мутаций, даже после более поздних переходов и при
   уменьшенной квоте. Повтор проверяется до устаревшей ожидаемой версии.
   Тот же ID с другими bytes или занятый seq с другим ID — conflict.
2. Для нового перехода проверить существование привязки, revision, её версию,
   предыдущие writer/container и boundary; seq строго следующий. Для первого
   перехода seq=1, previous ID=null, writer совпадает с начальной привязкой.
3. Проверить отсутствие занятых новых идентичностей и неизменность подготовленных
   raw-позиций. Все полные старые строки уже долговечно сохранены до LF-границы;
   пропуск, несовпадение или несовместимый прогресс после подготовки — отказ.
   Способ доказательства совпадения выбрать по актуальному коду; произвольного
   claimed hash без сравнения с сохранённым raw недостаточно.
4. Атомарно проверить итоговую квоту, записать proof, закрепления и хвосты,
   закрыть старый writer, создать новый, записать header/checkpoint внутренней
   raw-операцией, обновить текущую привязку/версию и учёт bytes.
5. COMMIT; только после успешного завершения вернуть accepted.

При любой ошибке весь шаг принятия откатывается. Подготовленный ранее старый
raw остаётся. Текущая привязка не перемещается; события и ledger не создаются.
Хеширование внешних файлов и ожидание runtime под write lock запрещены.

### Результаты и ошибки

Различать accepted, repeated, conflict, отсутствие начальной привязки,
превышение лимита/квоты и ошибку хранилища. Допускаются типизированные исключения
с безопасными кодами. SQLite busy — повторяемая ошибка хранения, не принятие
и не семантический конфликт. Не раскрывать raw/proof/пути в диагностике.
Непроведённый COMMIT никогда не трактуется как accepted.

## 4. Квоты

Настраиваемые начальные пределы: canonical proof <= 1 MiB, 1..64 закреплённых
журнала, сумма хвостов <= 4 MiB. Ровно предел допустим, превышение отклоняется
целиком. Это внутренние пределы хранения; дополнительные предложения runtime
про 65535 байт на хвост не вводить молча в эту поставку.

Логическое потребление = сохранённый raw + canonical proof + BLOB хвостов;
новый header учитывается как raw ровно один раз. Пустой хвост не увеличивает
счётчик. Не считать сумму размеров snapshots логическим raw spool повторно.
Не учитывать repeated второй раз. Начальный anchor и служебные данные, как
ledger/pending/индексы/WAL, не объявлять охваченными этой формулой: их вклад
в фактический размер диска описать отдельно.

Интеграция квоты должна охватывать и обычный append: нельзя заполнить бюджет
proof/хвостами и затем обойти его прежней проверкой только raw. Существующие
параметры и вызовы сохранить совместимыми; семантику общего бюджета документировать.
Проверка и изменение счётчика сериализованы той же транзакцией, что данные.

Свободное место — отдельный ресурс. Предварительная оценка не гарантирует
запись, поскольку есть WAL и конкуренция; ошибки записи/COMMIT обрабатываются
с rollback и сохранением данных. Очистки, обрезки и удаления по ACK нет.

## 5. Миграция

Версионированная, атомарная, повторно безопасная миграция существующей spool.
Не перезаписывать чужие metadata; выбрать согласованное место версии с учётом
всех repositories. Не использовать executescript так, чтобы неявный commit
разрывал миграцию. Не выполнять DDL-инициализацию внутри принятия перехода.

Сохранить точные raw BLOB, raw/обычные checkpoints, locations, поколения,
ledger и canonical payload, pending с порядком, quarantine и batch snapshots.
Инициализировать usage из существующих данных без двойного учёта. Если данные
уже превышают настроенную квоту — сохранить их и запретить новые увеличения.
База с более новой неизвестной версией отклоняется без записи; ошибка миграции
не оставляет установленную новую версию или частичную схему.
Ни writer, ни anchor не восстанавливать из header/имени/накопленного raw.

## 6. Приёмка

Все обязательные сценарии [тестового контракта](low-boundary-storage-test-contract.md) реализованы и проходят, действующие
telemetry-тесты не ослаблены. Нет production-вызова нового принятия и изменения
поведения позднего null. Спецификации отражают реальную схему, квоту и ошибки.
Совместный producer-тест, Linux права/fencing и обработка промежуточных
поколений без footer явно остаются вне доказанной готовности.


## 7. Реализованная схема и интерфейсы

`StorageMigration` (`agent/telemetry/storage_schema.py`) использует собственный
ключ `metadata.low_storage_version=1`, не `PRAGMA user_version`. Сначала проверяются
agent и версия без записи, затем одна `BEGIN IMMEDIATE` для DDL, owner и usage.
Все statements выполняются отдельно. Оба constructors (`RawJournalRepository`,
`SpoolRepository`) вызывают миграцию; неизвестная версия или чужой agent запрещают
дальнейшую инициализацию. Версия 0 — прежняя схема без этого ключа. Никаких записей
binding/writer при миграции не создаётся. Существующие таблицы не перестраиваются.

Таблицы `low_raw_*` сохраняют прежний формат. `low_raw_usage` остаётся счётчиком
только raw для совместимости; новый `low_storage_usage(singleton=1,bytes)` считает
raw+proof+tails. Он инициализируется суммой `length(raw)` из прежних BLOB.
Параметр `max_raw_bytes` сохранён, но теперь ограничивает весь этот общий бюджет.
Квота задаётся конфигурацией repositories, работающих с одной spool. Уменьшение
квоты не удаляет данные и допускает точные повторы. Snapshot bytes на внешнем
диске в этот бюджет не входят, равно как metadata, ledger, pending, quarantine,
индексы, служебные страницы SQLite и WAL. Предварительная оценка свободного
места не выполняется: SQLite write/COMMIT error откатывает принятие; это не
гарантия наличия свободного физического места.

`low_boundary_bindings` хранит текущий writer/container, revision, version,
последний boundary ID/seq. Scope — JSON `[agent_id,deployment_id,instance_id]`.
`low_boundary_writers` сохраняет active/sealed и opened_by/sealed_by; UNIQUE
по writer/container и partial UNIQUE active запрещают развилку в scope.
`low_boundary_proofs` хранит ID/seq/previous, точные proof BLOB и SHA-256;
ID и seq уникальны в scope. `low_boundary_journals` резервирует ID журнала
нового writer и связывает закрытые журналы с принявшим переходом.
`low_boundary_pins` хранит writer/source_key, seq как TEXT, snapshot ref/hash/size,
LF-end, digest полного raw-prefix и footer_present. `low_boundary_tails` хранит
буквальный BLOB, offset/length/SHA-256. Новые строки не заменяют принятые pins.
Обычный append новых bytes в закреплённое поколение отклоняется
`GENERATION_SEALED`; точный повтор прежних строк по-прежнему допустим.

`RawJournalRepository.append_in_transaction(connection,binding,record,path=None)`
принимает только собственный connection с активной транзакцией и совпадающим
agent. Не управляет BEGIN/COMMIT/ROLLBACK/close. Ошибка требует rollback всей
транзакции владельцем. Обычный `append` делает эту атомарную обёртку сам.

`BoundaryRepository(raw,limits).accept_prepared_transition(prepared)` принимает
frozen `PreparedTransition` с существующим `JournalBinding` и `JournalRecord`
нового header; `PreparedJournal` — frozen метаданные pin и immutable tail bytes,
не Event DTO. Список pins — tuple; header обязан иметь LF, offset=0, согласованные
ID/seq/binding и previous_journal_id=null. Это не разрешает поздний null collector.

До новых записей сравниваются checkpoint/seq, непрерывность и точные bytes raw
через вычисленный SHA-256 prefix. SHA-256 prefix+tail также сверяется с дублированным
snapshot digest; внешних файлов внутри операции нет. Ранее зарезервированный
header текущего writer обязан присутствовать в списке pins. Полноту всей внешней
выборки, process seq и доверие к автору подтверждает будущий validator, а не
эта проверка структурной согласованности.

Внутренние результаты — `accepted`/`repeated`; безопасные `BoundaryError.code`:
`INVALID_PREPARED`, `INVALID_TRANSACTION`, `BINDING_REQUIRED`, `CONFLICT`,
`RAW_CONFLICT`, `STORAGE_LIMIT`, `WRITER_BUSY`, `DB_ERROR`; errors внутренней raw
операции сохраняют её безопасный код. Replay идентифицируется scope+ID+точными
proof bytes до лимитов и stale version; другие подготовленные поля на replay
не переустанавливают сохранённое состояние. Mutable proof bytes отклоняются.

Начальная привязка не имеет production API в этой поставке. Тесты явно вставляют
binding/writer SQL-фикстурой, независимо от raw. В production repository без такой
заранее авторизованной привязки возвращает `BINDING_REQUIRED`.

## 8. Исполняемая приёмка

`tests/telemetry/test_boundary_storage.py` покрывает M01–M07, R01–R05,
B01–B11, Q01–Q09 и E: отдельные SQLite connections, WAL, SQL-оракул,
параметризация каждого шага миграции/принятия, узкая инъекция COMMIT/SQLITE_FULL и настоящий SQLITE_FULL через max_page_count,
детерминированный busy с Event и явным retry, два crash-процесса с flush IPC и проверкой exit code. Q01 допускает bytes
внутреннего storage, не утверждает внешнюю canonical schema произвольного padding.
B02 использует исходный 885-byte sample и явный 25-byte opaque tail.
Реальные footer_present и несколько хвостов проверяются отдельно.
F проверяет, что наличие schema не снимает ожидание позднего null и что старый
verified raw конвертируется; ACK сохраняет proofs/pins/history/usage/ledger.
Результаты команд и ограничения — в `boundary-storage-validation.md`.

Storage основан на зависимом PR #39 SHA
`20f19d2ce3c1aae6ec79205a971a6d358260dfb1`, содержащем main
`01f8272ba37ef16af7b905042b00a7a1d36808ca`. Дублирования mapper в данном diff нет.
Producer, файловое доверие, Linux fencing, footer промежуточных поколений,
bootstrap и реальный consumer с совместным producer/Docker-тестом не входят
в доказанную готовность этой поставки.
