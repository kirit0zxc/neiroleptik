# Журнал Low v1: формат файлов, поколения и ротация

Статус: **предложение** участнику 4 (телеметрия) для первой интеграции с HTTP Low.
Формат не утверждён: изменения согласуются с владельцем сборщика до реализации
адаптера (AGENTS.md, п. 7). Это внутренний формат Low, а не Event центра: адаптацию в
`contracts/event-v1.schema.json` выполняет сборщик. Журнал не заменяет spool сборщика.

Реализация: `honeypots/low/journal.py`, `honeypots/low/service.py`,
`honeypots/low/__main__.py`; подключение к контейнеру — `agent/runtime/drivers/low.py`
([runtime-drivers.md](runtime-drivers.md)).

## 1. Как сборщик получает журнал

Low пишет файлы в каталог `/journal` внутри контейнера. Драйвер монтирует в него
каталог хоста `<journal_root>/<deployment_id>/` (bind mount, чтение и запись). Сборщик
читает этот каталог на хосте вне контейнера; корневая файловая система контейнера
остаётся только для чтения. Каталог должен существовать и принадлежать пользователю
контейнера (`65532:65532`), права `0750`; создаёт его драйвер при запуске, владельца
назначает подготовка хоста (bootstrap). Доступ сборщику и оператору — по группе;
контейнер не получает ничего, кроме этого каталога.

Без `--journal-dir` Low пишет диагностический JSONL в stdout (формат записей `event`
без заголовка и концовки); для интеграции он не предназначен.

## 2. Файлы и поколения

- Имя файла: `low-<instance_id>-<journal_seq>.jsonl`, где `instance_id` — UUID
  экземпляра в нижнем регистре, `journal_seq` — шесть цифр с ведущими нулями
  (`000001`, `000002`, …). Один экземпляр — свой набор файлов; файлы разных
  экземпляров не смешиваются.
- **Поколение журнала** — один файл. Его однозначно определяет `journal_id` (UUID) в
  заголовке; `journal_seq` задаёт порядок файлов внутри экземпляра. Имя файла можно
  менять (переносить, архивировать): поколение определяет заголовок, а не имя.
- Кодировка UTF-8, перевод строки LF, одна JSON-запись на строку, только ASCII
  (`ensure_ascii`), без NaN. Файл только дописывается; закрытые файлы не изменяются.
- Права создаваемых файлов `0640` (POSIX).

## 3. Записи

Каждая строка — объект с полем `record`.

### 3.1 `header` (первая строка файла)

| Поле | Тип | Описание |
|---|---|---|
| `record` | `"header"` | |
| `schema` | `"honeyforge-low-journal/1"` | Версия формата. Несовместимое изменение — новая версия. |
| `journal_id` | UUID | Идентификатор поколения (файла). |
| `journal_seq` | int ≥ 1 | Номер файла внутри экземпляра. |
| `previous_journal_id` | UUID \| null | Предыдущее поколение этого экземпляра; `null` у первого. |
| `instance_id` | UUID | Экземпляр (создаёт драйвер; см. ниже). |
| `deployment_id` | UUID | Назначение центра. |
| `profile_revision` | int ≥ 1 | Ревизия профиля, применённая к экземпляру. |
| `opened_at` | RFC 3339 UTC, `Z` | Время создания файла. |
| `first_seq` | int ≥ 1 | `seq` первого события, которое может оказаться в этом файле. |

### 3.2 `event`

| Поле | Тип | Описание |
|---|---|---|
| `record` | `"event"` | |
| `seq` | int ≥ 1 | Сквозной номер события внутри экземпляра, не обнуляется при ротации. |
| `event` | `"connection"` \| `"request"` | Принято соединение / получены данные запроса. |
| `timestamp` | RFC 3339 UTC, `Z` | Время события на хосте Low. |
| `connection_id` | UUID | Стабильный идентификатор соединения; общий для всех его событий. |
| `protocol` | `"tcp"` \| `"http"` | Вид приманки (повторяет `service.protocol`). |
| `service` | `{protocol, port}` | Порт, который видит клиент (публичный порт профиля). |
| `peer` | `{host, port}` \| null | Адрес клиента. |
| `payload_b64` | string | Недоверенные байты в base64; для `connection` пусто. |

Для HTTP это байты запроса до `\r\n\r\n` (не более лимита `max_payload_bytes`
профиля). Содержимое никогда не интерпретируется и не отражается в ответе.

### 3.3 `footer` (последняя строка завершённого файла)

| Поле | Тип | Описание |
|---|---|---|
| `record` | `"footer"` | |
| `journal_id` | UUID | Совпадает с заголовком этого файла. |
| `last_seq` | int ≥ 0 | `seq` последнего события в файле; `first_seq - 1`, если событий нет. |
| `closed_at` | RFC 3339 UTC, `Z` | |
| `reason` | `"rotation"` \| `"shutdown"` | Причина закрытия. |

Файл **с концовкой** завершён и больше не изменится. Файл **без концовки** либо ещё
пишется (это самый новый `journal_seq` экземпляра), либо оборван сбоем процесса.
Последняя строка файла без концовки без завершающего LF может быть записана не
полностью — сборщик её игнорирует до появления LF.

## 4. Идентификаторы и порядок

- **`instance_id`.** Создаёт и сохраняет runtime (драйвер): новый при `start`,
  `apply_config` и `reset`, прежний при `stop`, `inspect` и рестарте процесса агента
  (хранится в метке контейнера и в журнале команд). `apply_config` пересоздаёт
  контейнер, поэтому смена ревизии меняет `instance_id`; ревизию читать из
  `profile_revision`.
- **`connection_id`.** UUID версии 4 на каждое принятое соединение, неизменен для его
  событий `connection` и `request`, не повторяется между соединениями и экземплярами.
  Подходит как основа идентификатора сессии.
- **Порядок.** Внутри экземпляра события строго упорядочены по `seq` (одно
  процессное время жизни Low = один экземпляр, счётчик не сбрасывается при ротации).
  Эквивалентно ключу `(journal_seq, смещение строки в файле)`. Между экземплярами
  порядок задаёт `opened_at` заголовка и `timestamp` событий.
- **Пропуски `seq`.** Номер выдаётся перед записью. Пропуск означает событие, которое
  не удалось записать (ошибка диска, квота); соединение при этом закрывается без
  ответа. Повторов `seq` внутри экземпляра нет.
- **Идемпотентное чтение.** Позиция записи однозначна: `(journal_id, смещение начала
  строки)`. Повторное чтение того же файла даёт те же позиции.

## 5. Ротация, квота, надёжность

- Ротация по размеру: когда следующая запись не помещается в `--journal-max-bytes`
  (по умолчанию 8 МиБ, не менее 256 КиБ), текущий файл закрывается концовкой
  `rotation`, flush и fsync, затем создаётся следующий с `previous_journal_id`.
- Квота каталога `--journal-quota-bytes` (по умолчанию 256 МиБ) считается по всем
  файлам `low-*.jsonl` каталога. Удалять обработанные файлы может только сборщик,
  Low ничего не удаляет. При исчерпании квоты запись завершается ошибкой, Low
  закрывает соединение без ответа (событие не выдано за сохранённое), а при освобождении
  места продолжает на следующем поколении.
- Ошибка записи: файл закрывается без концовки (его хвост мог быть записан не
  полностью), следующая запись открывает новое поколение с `previous_journal_id`;
  данные неподтверждённой записи не объявляются сохранёнными.
- Устойчивость: каждая запись сбрасывается (`flush`) в ОС; `fsync` выполняется при
  ротации и остановке. Режим `--journal-fsync` включает `fsync` после каждой записи
  ценой пропускной способности. Журнал — буфер для сборщика, а не устойчивое
  хранилище: при потере хоста недоставленные записи теряются.
- Остановка (SIGTERM, на Windows Ctrl+Break) закрывает слушатели, затем пишет концовку
  `shutdown`.

Пробы здоровья драйвера и любые подключения с хоста тоже порождают события: Low не
отличает их от клиентов. Они приходят с адреса хоста или шлюза сети контейнера;
сборщик должен их отфильтровывать (открытый вопрос 5).

## 6. Безопасность

Содержимое `payload_b64` и сами файлы — недоверенный ввод для сборщика: имена файлов и
заголовки проверяются по схеме, размер строки ограничен (запись не больше ~100 КиБ),
base64 декодируется с проверкой. Low не принимает пути, шаблоны и команды от клиента;
пароли профиля в журнал не попадают (Low их не получает).

## 7. Параметры запуска

| Параметр | Значение |
|---|---|
| `--journal-dir` | Каталог журнала. Включает файловый журнал и требует три параметра ниже. |
| `--instance-id`, `--deployment-id`, `--profile-revision` | Данные заголовка. |
| `--journal-max-bytes`, `--journal-quota-bytes` | Ротация и квота. |
| `--journal-fsync` | `fsync` после каждой записи. |
| `--tcp-public-port`, `--http-public-port` | Порты, которые видит клиент (`service.port`); по умолчанию равны портам привязки. |

## 8. Образец и проверка запуска

Образец настоящего журнала лежит в
[samples/low-journal-v1.sample.jsonl](samples/low-journal-v1.sample.jsonl). Его создал
настоящий процесс `python -m honeypots.low`: скрипт отправил на loopback 7 безвредных
соединений (TCP-баннер и произвольные байты, GET, HEAD, POST, слишком большой заголовок,
некорректный запрос), затем остановил процесс корректным сигналом. Это не данные
реальных клиентов. Воспроизведение:

```text
python -m infra.runtime.sample_low_journal --output <пустой каталог>
```

Тест `tests/infra/test_sample_low_journal.py` запускает тот же процесс и проверяет
формат файла по этому документу; он же проверяет и приложенный образец.

## 9. Приёмка и тесты

Заголовок/концовка и поля записей; ротация (граница размера, непрерывность `seq`,
`previous_journal_id`, концовка `rotation`); квота (отказ, закрытие соединения без
ответа, восстановление после освобождения места); ошибка записи и следующее
поколение; номера продолжаются без перезаписи существующих файлов; одинаковый
`connection_id` у событий одного соединения и разный у разных; сквозной запуск
`python -m honeypots.low` как настоящий процесс с корректной остановкой и разбором
получившегося файла; драйвер передаёт параметры и монтирует каталог.

## 10. Открытые вопросы участнику 4

1. Подходит ли чтение каталога на хосте (bind mount) и права доступа по группе.
2. Нужны ли разобранные поля HTTP (метод, путь, версия) в записи, или сборщик
   разбирает `payload_b64` сам.
3. Какие события Low соответствуют `connection.opened`, `http.request` и событиям
   TCP-приманки; нужен ли код ответа Low в записи `request`.
4. Политика удаления обработанных файлов и допустимая задержка чтения.
5. Нужен ли отдельный признак или адрес для проб здоровья драйвера, чтобы их можно было
   надёжно отличать от клиентов.
6. Реальные Cowrie JSON и TTY (Medium/High) здесь не описаны: Cowrie ещё не
   запускался, версия не закреплена (см. [infra/runtime/README.md](../infra/runtime/README.md)).
