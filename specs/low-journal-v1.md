# Журнал Low v1: формат файлов, поколения и ротация

Статус: **предложение** участнику 4 (телеметрия) для первой интеграции с HTTP Low.
Формат не утверждён: изменения согласуются с владельцем сборщика до реализации
адаптера (AGENTS.md, п. 7). Это внутренний формат Low, а не Event центра: адаптацию в
`contracts/event-v1.schema.json` выполняет сборщик. Журнал не заменяет spool сборщика.

Реализация: `honeypots/low/journal.py`, `honeypots/low/service.py`,
`honeypots/low/__main__.py`; подключение к контейнеру — `agent/runtime/drivers/low.py`
([runtime-drivers.md](runtime-drivers.md)).

## 1. Как сборщик получает журнал

Low пишет файлы в каталог `/journal` внутри контейнера. Драйвер монтирует в него
каталог хоста `<journal_root>/<deployment_id>/` (bind mount, чтение и запись). Сборщик
читает этот каталог на хосте вне контейнера; корневая файловая система контейнера
остаётся только для чтения. Драйвер при подготовке запуска создаёт каталог слота с
правами `0750` и назначает владельца `65532:65532`; на POSIX это требует root или
`CAP_CHOWN`. Сборщик читает каталог как root либо как участник группы `65532`;
подготовка хоста обеспечивает ему проход через родительские каталоги. На Windows
без `os.chown` смена владельца пропускается: это режим локальной разработки, а не
подтверждение прав контейнера на Linux. Контейнер получает только каталог своего
слота. SELinux-метки bind mount не настраиваются, этот режим не проверен и здесь
не заявляется поддержанным.

Без `--journal-dir` Low пишет диагностический JSONL в stdout: поля события из
раздела 3.2 **без поля `record`**, без `header`/`footer`, ротации и квоты файлового
журнала. Для интеграции со сборщиком этот поток не предназначен; ограничения
Docker-лога задаются отдельно и не превращают stdout в файловый контракт.

## 2. Файлы и поколения

- Имя файла: `low-<instance_id>-<journal_seq>.jsonl`, где `instance_id` — UUID
  экземпляра в нижнем регистре, `journal_seq` — не менее шести цифр с ведущими нулями
  (`000001`, `000002`, …). Один экземпляр — свой набор файлов; файлы разных
  экземпляров не смешиваются.
- **Поколение журнала** — один файл. Его однозначно определяет `journal_id` (UUID) в
  заголовке; `journal_seq` задаёт порядок файлов внутри экземпляра. Имя файла можно
  менять (переносить, архивировать): поколение определяет заголовок, а не имя.
- Кодировка UTF-8, перевод строки LF, одна JSON-запись на строку, только ASCII
  (`ensure_ascii`), без NaN. Файл только дописывается; закрытые файлы не изменяются.
- Права создаваемых файлов `0640` (POSIX).

## 3. Записи

Каждая строка — объект с полем `record`.

### 3.1 `header` (первая строка файла)

| Поле | Тип | Описание |
|---|---|---|
| `record` | `"header"` | |
| `schema` | `"honeyforge-low-journal/1"` | Версия формата. Несовместимое изменение — новая версия. |
| `journal_id` | UUID | Идентификатор поколения (файла). |
| `journal_seq` | int ≥ 1 | Номер файла внутри экземпляра; отказ создания не расходует номер. |
| `previous_journal_id` | UUID \| null | Предыдущее поколение текущего процесса Low; `null` при открытии первого файла новым процессом, в том числе при прежнем instance и `journal_seq > 1`. |
| `instance_id` | UUID | Экземпляр (создаёт драйвер; см. ниже). |
| `deployment_id` | UUID | Назначение центра. |
| `profile_revision` | int ≥ 1 | Ревизия профиля, применённая к экземпляру. |
| `opened_at` | RFC 3339 UTC, `Z` | Время создания файла; не нижняя граница времени его событий. |
| `first_seq` | int ≥ 1 | `seq` первого события, которое может оказаться в этом файле. |

### 3.2 `event`

| Поле | Тип | Описание |
|---|---|---|
| `record` | `"event"` | |
| `seq` | int ≥ 1 | Сквозной номер события внутри процесса Low, не обнуляется при ротации; новый процесс начинает счётчик заново. |
| `event` | `"connection"` \| `"request"` | Принято соединение / получены данные запроса. |
| `timestamp` | RFC 3339 UTC, `Z` | Время события на хосте Low. |
| `connection_id` | UUID | Стабильный идентификатор соединения; общий для всех его событий. |
| `protocol` | `"tcp"` \| `"http"` | Вид приманки (повторяет `service.protocol`). |
| `service` | `{protocol, port}` | Публичный порт из профиля, если он передан CLI; иначе фактический порт слушателя. |
| `peer` | `{host, port}` \| null | Адрес клиента. |
| `payload_b64` | string | Недоверенные байты в base64; для `connection` пусто. |

Для HTTP это байты запроса до `\r\n\r\n` (не более лимита `max_payload_bytes`
профиля). Low проверяет синтаксис и метод HTTP, но не исполняет содержимое, не
маршрутизирует запрос и не отражает клиентские байты в ответе.
Драйвер всегда открывает внутри контейнера TCP 2222 и HTTP 8080. Если сервис не
публикуется профилем, его внутренний слушатель остаётся открытым; события соединений
через сеть контейнера для него содержат внутренний порт 2222 или 8080. Отсутствие
публикации на хосте не означает отсутствие доступа из этой сети.

### 3.3 `footer` (последняя строка завершённого файла)

| Поле | Тип | Описание |
|---|---|---|
| `record` | `"footer"` | |
| `journal_id` | UUID | Совпадает с заголовком этого файла. |
| `last_seq` | int ≥ 0 | `seq` последнего события в файле; `first_seq - 1`, если событий нет. |
| `closed_at` | RFC 3339 UTC, `Z` | |
| `reason` | `"rotation"` \| `"shutdown"` | Причина закрытия. |

Файл **с концовкой** структурно завершён и больше не изменится; сама концовка не
подтверждает доставку в центр или успешное сохранение при потере хоста.
Файл **без концовки** либо ещё пишется (это самый новый `journal_seq` экземпляра),
либо оборван сбоем процесса.
Последняя строка файла без концовки без завершающего LF может быть записана не
полностью — сборщик её игнорирует до появления LF.

## 4. Идентификаторы и порядок

- **`instance_id`.** Создаёт runtime для новой попытки `start`, `apply_config`
  или `reset` и сохраняет до запуска контейнера. Повтор команды, ротация, `stop`,
  `inspect` и recovery существующего контейнера не меняют UUID. Неудачная попытка
  также может иметь сохранённый UUID: его наличие не доказывает успешный запуск.
  Новый процесс Low с прежней привязкой instance возможен и не является новым
  instance. `apply_config` пересоздаёт контейнер; ревизию читать из `profile_revision`.
- **`connection_id`.** UUID версии 4 на каждое принятое соединение, неизменен для его
  событий `connection` и `request`, не повторяется между соединениями и экземплярами.
  Подходит как основа идентификатора сессии.
- **Порядок.** Внутри одного процесса события строго упорядочены по `seq`,
  счётчик не сбрасывается при ротации. Новый процесс того же instance продолжает
  нумерацию `journal_seq` по существующим файлам, но начинает `seq` заново и пишет
  `previous_journal_id=null`. Поэтому `(instance_id, seq)` не уникален; порядок
  исходных записей задаётся `(journal_seq, смещение строки в файле)`. Поздний null
  сам по себе не доказывает доверенную границу процесса: переход сборщика через
  разрыв требует отдельного согласованного provenance, описанного в
  [low-telemetry-handoff.md](low-telemetry-handoff.md). `timestamp` берётся до
  передачи события в sink, а новый файл может открыться после этого при ротации или
  восстановлении: событие вправе быть раньше `opened_at` своего файла. Время UTC
  служит для отображения и сопоставления; строгий порядок между экземплярами по
  часам не гарантируется.
- **Пропуски `seq`.** Номер выдаётся перед записью. Пропуск означает событие, которое
  не удалось записать (ошибка диска, квота); соединение при этом закрывается без
  дальнейшего ответа. Повторов `seq` внутри одного процесса нет; после нового
  процесса того же instance прежние значения могут повторяться.
- **Идемпотентное чтение.** Позиция записи однозначна: `(journal_id, смещение начала
  строки)`. Повторное чтение того же файла даёт те же позиции.

## 5. Ротация, квота, надёжность

- Ротация по размеру: когда следующая запись вместе с резервом 512 байт под концовку
  не помещается в `--journal-max-bytes` (по умолчанию 8 МиБ, не менее 256 КиБ), Low
  закрывает текущий файл концовкой `rotation` и `fsync`, затем создаёт
  следующий с `previous_journal_id`. При ошибке концовки эта попытка события
  завершается ошибкой; новое поколение открывается только при следующем событии.
  Отдельная запись вместе с резервом должна помещаться в половину лимита файла;
  иначе sink отклоняет её до записи.
- Квота каталога `--journal-quota-bytes` (по умолчанию 256 МиБ) считается по обычным
  файлам с допустимым именем `low-<UUID>-<номер>.jsonl` каталога, без перехода по
  символическим ссылкам. Low ничего не удаляет; автоматическая очистка не
  реализована. Read-only сборщик сохраняет raw и checkpoint, но не выполняет
  unlink. Владелец janitor, receipt, архивирование полного файла с аварийным
  хвостом и восстановление после удаления predecessor ещё согласуются.
  Footer, checkpoint и ACK Event сами по себе не разрешают удаление исходника.
  Перед событием резервируется также 512 байт под концовку.
  При исчерпании квоты до записи события возвращается ошибка, соединение закрывается
  без дальнейшего ответа. Уже отправленный TCP-баннер отменить нельзя. Если текущий
  файл открыт, он не меняется и после освобождения места запись продолжается в него;
  если файл уже закрыт при ротации, создаётся следующее поколение. Неудачное создание
  заголовка не расходует `journal_seq`, в отличие от `seq` потерянного события.
- Ошибка записи события или его `fsync`: Low пытается обрезать файл до конца
  последней подтверждённой записи, закрывает его без концовки и сообщает ошибку
  сервису. Следующее событие открывает новое поколение с `previous_journal_id`.
  Если само обрезание не удалось, хвост может остаться; неполную строку без LF
  сборщик игнорирует. Ошибка не даёт права считать неподтверждённое событие сохранённым.
- Ошибка записи концовки или её `fsync` также передаётся вызывающему коду: Low
  пытается обрезать файл до последней подтверждённой записи и в любом случае
  закрывает его. Ротация при этом не выдается за успешную. При отказе обрезания
  хвост может остаться, поэтому наличие концовки само по себе не является seal.
- Устойчивость: файл открыт без буфера Python; данные полностью передаются ОС перед
  успешным возвратом `emit`. `fsync` выполняется при ротации и остановке, а его ошибка
  не скрывается. Успех локального закрытия не подтверждает чтение сборщиком или ACK
  центра. Режим `--journal-fsync` включает `fsync` после каждого события
  ценой пропускной способности. Журнал — буфер для сборщика, а не устойчивое
  хранилище: при потере хоста недоставленные записи теряются.
- Корректная остановка (SIGTERM/SIGINT, на Windows Ctrl+Break) закрывает слушатели
  и действующие соединения, затем пытается записать концовку `shutdown`. SIGKILL,
  падение процесса или принудительное удаление контейнера не выполняют обработчик
  остановки и оставляют открытый файл без концовки. Драйвер поэтому вызывает мягкую
  остановку перед удалением; timeout/отказ остановки всё равно допускает удаление,
  и наличие концовки в таком случае не гарантируется.

Пробы здоровья драйвера и любые подключения с хоста тоже порождают события: Low не
отличает их от клиентов. Они приходят с адреса хоста или шлюза сети контейнера,
но этот адрес сам по себе не доказывает, что событие является пробой. Доверенная
корреляция или отдельный management-порт и правило фильтрации ещё согласуются
(открытый вопрос 5).

## 6. Безопасность

Содержимое `payload_b64` и сами файлы — недоверенный ввод для сборщика. Сборщик не
переходит по символическим ссылкам, проверяет имя, схему и типы записей, а
`deployment_id`, `instance_id` и ревизию сверяет с доверенной конфигурацией агента:
заголовок ловушки не задаёт идентичность назначения. Доступные ему родительские
каталоги и пути задаёт оператор. Base64 декодируется с проверкой.

При запуске через профиль центра `max_payload_bytes` не больше 8192, а `LowService`
перед base64 обрезает вход до этого предела: base64 занимает не больше 10924 ASCII
байт. С фиксированными полями текущего сервиса, UUID и адресом сетевого peer запись
получается около 12 КиБ и помещается в лимит 64 КиБ текущего `LowAdapter`. Это оценка
конкретного пути `LowService`, а не гарантия для произвольных строк или Mapping,
переданных `RotatingJournalSink`: standalone CLI допускает до 65536 байт входа,
а sink ограничивает размер записи относительно выбранного лимита файла. Сборщику
нужен собственный жёсткий лимит строки и явная политика отказа. Low не принимает
пути, шаблоны и команды от клиента; пароли профиля в журнал не попадают (Low их
не получает).

Действующий `agent/telemetry/adapters/low.py` принимает другой предложенный формат
(`occurred_at`, `type`, `source`, `service`, `data`, `session_id`, `artifact_ids`) и
отклоняет служебные/неизвестные поля. Поэтому он несовместим с этим журналом даже
при подходящем размере строки: нужны согласованные с участником 4 чтение
`header`/`footer`, преобразование `event` и привязка позиции к `journal_id`.
Готовая интеграция с телеметрией или центром этим документом не заявляется.

### 6.1 Startup-выделение первого поколения

Runtime может передать идентичность первого поколения процесса заранее:
`--journal-first-id=<uuid>` и `--journal-first-seq=<n>`. Это нужно доверенной
границе процесса ([journal-process-boundary-proposal.md](journal-process-boundary-proposal.md),
§8.1): связь писателя и журнала хранит runtime, а не заголовок.

- Выделение относится **только** к первому поколению этого процесса: следующие
  поколения Low выбирает сам, как и без выделения.
- Если номер, вычисленный Low (максимум своего instance в каталоге плюс один),
  отличается от выделенного, процесс завершается кодом 2 **до открытия
  слушателей** и файла не создаёт. Неудачная попытка выделение не расходует.
- Существующий файл по-прежнему никогда не перезаписывается (`O_EXCL`).
- Формат записей не меняется: `writer_id` в заголовок не пишется, а
  `journal_id`, `journal_seq`, `previous_journal_id=null` и `first_seq=1`
  остаются обычными полями `header`.

## 7. Параметры запуска

| Параметр | Значение |
|---|---|
| `--journal-dir` | Каталог журнала. Включает файловый журнал и требует три параметра ниже. |
| `--instance-id`, `--deployment-id`, `--profile-revision` | Данные заголовка. |
| `--journal-max-bytes`, `--journal-quota-bytes` | Ротация и квота. |
| `--journal-fsync` | `fsync` после каждого события. |
| `--journal-first-id`, `--journal-first-seq` | Необязательное startup-выделение первого поколения этого процесса: `journal_id` и ожидаемый `journal_seq`. Задаются вместе и только вместе с `--journal-dir`. |
| `--tcp-public-port`, `--http-public-port` | Порты, которые видит клиент (`service.port`); по умолчанию равны портам привязки. |

## 8. Образец и проверка запуска

Образец настоящего журнала лежит в
[samples/low-journal-v1.sample.jsonl](samples/low-journal-v1.sample.jsonl). Его создал
настоящий процесс `python -m honeypots.low`: скрипт отправил на loopback 7 безвредных
соединений (TCP-баннер и произвольные байты, GET, HEAD, POST, слишком большой заголовок,
GET /probe), затем остановил процесс корректным сигналом. Это не данные
реальных клиентов. Воспроизведение:

```text
python -m infra.runtime.sample_low_journal --output <пустой каталог>
```

Тест `tests/infra/test_sample_low_journal.py` запускает тот же процесс и проверяет
формат файла по этому документу; он же проверяет и приложенный образец.

## 9. Приёмка и тесты

Заголовок/концовка и поля записей; ротация (граница размера, непрерывность `seq`,
`previous_journal_id`, концовка `rotation`); квота (отказ, закрытие соединения без
дальнейшего ответа, резерв концовки, продолжение открытого файла после освобождения
места); ошибка записи события/концовки и `fsync`, обрезание до подтверждённой границы,
отказ ротации и следующее поколение; неудачное открытие не расходует `journal_seq`;
номера продолжаются без перезаписи существующих файлов; одинаковый
`connection_id` у событий одного соединения и разный у разных; сквозной запуск
`python -m honeypots.low` как настоящий процесс с корректной остановкой и разбором
получившегося файла; драйвер передаёт параметры и монтирует каталог.

## 10. Открытые вопросы участнику 4

Реальные фрагменты с ротацией и ответ на предложения телеметрии приведены в
[low-telemetry-handoff.md](low-telemetry-handoff.md). Генератор поддерживает `--rotate`;
он не меняет схему журнала и не означает готовность адаптера Event v1.

1. Подходит ли чтение каталога на хосте (bind mount) и права доступа по группе.
2. Нужны ли разобранные поля HTTP (метод, путь, версия) в записи, или сборщик
   разбирает `payload_b64` сам.
3. Какие события Low соответствуют `connection.opened`, `http.request` и событиям
