# Исполнитель команд агента: Low и Medium

Основной сетевой контракт — `commands.md` и `../contracts/openapi.json`.
Этот документ описывает локальное исполнение, не изменяя API центра. Предложения
из `runtime-contract-proposal.md` не определяют командный API. Сроки D1–D5,
lease 60 секунд, продление каждые 20 секунд и hard deadline центра сохраняются
(срок исполнения 300 секунд одинаков для Low и Medium).
High и `reset` здесь не реализуются; неподдерживаемая команда получает failed ACK.

## Выбор драйвера по уровню назначения

Драйвер выбирается по `interaction_level` назначения через `DriverRegistry`
([runtime-drivers.md](runtime-drivers.md), раздел 6). Уровень исполняется, только если
на узле заданы его настройки: Low настроен всегда, Medium — когда оператор задал
`--medium-state-root`. Всё остальное — lease, durable стадии, подтверждение
фактического состояния, история `instance_id`/`applied_revision`, reconcile stop из
unknown — одинаково для всех настроенных уровней и не дублируется по уровням.

`LeasedBackend` проверяет перед каждой мутацией метку уровня того драйвера, который
исполняет команду: контейнер с меткой другого уровня не останавливается и не
удаляется, даже если его имя принадлежит пространству HoneyForge.

Для Medium подтверждение фактического состояния работает так же, как для Low, и
опирается на пробу его протокола: успешный start требует работающего контейнера этой
попытки и ответа строкой идентификации SSH, успешный stop — отсутствия контейнера и
явного отказа TCP-подключения ко всем портам профиля. Пароли профиля в ACK, журналы и
сообщения об ошибках не попадают: они существуют только в файле `userdb.txt` каталога
экземпляра.

## Поток и устойчивое состояние

Один процесс агента владеет каталогом состояния через межпроцессный замок.
Команды разных deployments исполняются последовательно. Перед изменением Docker
в SQLite с synchronous=FULL фиксируются безопасные метаданные команды, fingerprint
неизменяемого тела, lease, новый UUID попытки start и стадия исполнения.
Конфигурация профиля и пароли не записываются: после рестарта конфигурация получается
повторным claim(command_id). Bearer читается из HF_AGENT_TOKEN или закрытого файла;
после чтения токен не наследуется дочерними процессами. Lease token находится
в закрытом каталоге состояния. Поддерживается локальный диск, не общий сетевой том.

Для каждого deployment отдельно сохраняются обработанное поколение, последний
instance_id и историческая applied_revision. Generation учитывает stop и ошибки;
пропуски допустимы. Повтор известного command_id проверяется раньше поколения.
Другой fingerprint того же ID — отказ без мутации. Новая команда с
expected_generation ниже обработанного — STALE_GENERATION. Итог без lease_token
фиксируется атомарно с историей deployment до отправки ACK и больше не меняется.

После потери ACK сначала повторяется сохранённый ACK с последним token: terminal
claim отвечает COMMAND_FINISHED. При LEASE_EXPIRED/LEASE_MISMATCH незавершённой
команды агент получает новый lease того же ID и повторяет неизменный результат.
После COMMAND_FINISHED для незавершённой локальной операции выполнение прекращается;
она сохраняется как abandoned, фактический контейнер остаётся для отдельного stop
из unknown. Ошибка ACK_MISMATCH/ACK_CONFLICT останавливает процесс исполнителя и
требует исправления причины; локальная история к этому моменту уже записана и
автоматически не переписывается. Блокировка действует до истечения срока команды на
центре: затем повторный claim отвечает COMMAND_FINISHED, запись становится abandoned,
и очередь продолжается, а расхождение с центром устраняет stop с reconcile из unknown.
Сетевой сбой и 409 LEASE_* оставляют запись для повтора; неверный ответ центра
(INVALID_RESPONSE и другие нарушения протокола) останавливает процесс.

Если поколение центра отстаёт от истории агента (например, после восстановления БД
центра), accept отвечает STALE_GENERATION без мутаций и процесс останавливается.
Агент не стирает историю сам; процедура оператора — в `infra/runtime/executor.md`.

## Lease и физические операции

Перед исполнением выполняется renew; во время работы lease продлевается отдельной
корутиной. Время ограничивается одновременно UTC сроками центра и монотонным таймером
локального lease. Отказ центра в renew (4xx, неверный ответ) или достижение срока
закрывают разрешение на новые мутации. Сетевая ошибка и HTTP 5xx при renew
повторяются примерно через секунду, пока разрешение ещё действует: иначе одна
потерянная попытка превращала бы start в RECOVERY_UNCERTAIN без вызова docker run.
Каждый run/stop/remove отдельно проверяет разрешение. Уже начатая Docker
операция может закончиться после потери lease: агент её не отменяет и не освобождает
слот до окончания. Последующая автоматическая очистка также запрещена без lease.
Наблюдение inspect допускается, результат сохраняется для последующего восстановления;
ACK старым token после потери lease не отправляется.

Часы агента должны быть синхронизированы с часами центра (NTP; расхождение много
меньше 60 секунд). Если только что выданный lease по часам агента уже истёк (часы
агента спешат более чем на пять секунд), исполнение прекращается кодом CLOCK_SKEW
до любых Docker-операций. Чуть истёкший повторно выданный lease не доказывает
расхождение часов: агент повторяет claim без изменения стадии prepared/executing.
Отставание часов агента продлевает
локальное разрешение на величину расхождения: hard deadline центра соблюдается
только при синхронных часах.

При остановке процесса ожидается окончание начатой операции. SIGKILL/сбой хоста
оставляет стадию executing: следующий процесс сначала claim+renew, затем сверка
Docker. Пока результат неоднозначен, новый start не повторяется автоматически.

## Сверка и ACK

UUID start сохраняется до run и передаётся фабрике драйвера уровня. Recovery проверяет
managed, deployment_id, метку уровня этого драйвера, instance_id и revision,
неизменяемый container ID.
При найденном экземпляре текущей попытки start проводится health check, без нового
run. Если executing start не оставил контейнера, агент возвращает RECOVERY_UNCERTAIN:
не доказываем, что прежняя попытка никогда не выполнялась, и не запускаем её повторно.
Prepared означает, что мутация ещё не начиналась, поэтому после сверки её можно начать.
Чужой или некорректно маркированный контейнер не изменяется. Stop повторяем и
подтверждаем stopped только после inspect, подтверждающего отсутствие контейнера,
и TCP-проверки освобождения всех tcp/http-портов профиля. Если порт продолжает
принимать соединения либо проверка завершается таймаутом/ошибкой маршрута,
возвращается failed ACK PORT_STILL_OPEN без удаления чужого процесса. Описание
сообщает о невозможности подтвердить освобождение, поскольку таймаут не доказывает
наличие слушателя. Для wildcard bind проверяется соответствующий loopback.
Порты для этой проверки — все tcp/http-сервисы профиля, без проверки текста и
состава: профиль, который драйвер отверг при start (управляющий символ в тексте HTTP,
недопустимый баннер TCP, несколько сервисов одного вида — центр всё это принимает),
не мешает подтвердить stop.
Удаление всегда по неизменяемому ID, без возврата к имени при гонке.

Успешный start: running, новая идентичность попытки, целевая revision, generation
команды. Обычный stop сохраняет прежнюю applied_revision и instance_id независимо
от очищенного DriverStatus.revision. Stop с reconcile=true может сохранить найденные
метки того же deployment, включая start, ACK которого центр не получил.
При сбое ACK содержит безопасный код и краткий текст без конфигурации и вывода Docker.
Running на неудачном start допускается только для ожидаемого прежнего instance,
фактически наблюдаемого работающим; новую неуспешную попытку нельзя выдавать за
подтверждённый running. Наблюдение прежнего экземпляра сохраняет UUID истории;
UUID попытки сообщается при наблюдении этой попытки либо при отсутствии наблюдения,
если backend.run уже был запрошен или восстанавливается executing. Одна запись
mark_executing до вызова run не доказывает существование новой ловушки. Все известные
UUID этого deployment сохраняются для последующего stop, включая прежнюю попытку
при недоступном inspect. Managed/deployment/level/revision и неизменяемый container ID
остаются обязательными; чужие контейнеры не подхватываются. Applied_revision не меняется.

Команды ненастроенных уровней и действий получают failed ACK UNSUPPORTED_COMMAND с
runtime_state=failed без обращения к Docker. Поэтому узел регистрируется ровно с теми
уровнями, которые заданы на нём настройками: по умолчанию `["low"]`, а с каталогом
состояния Cowrie — `["low", "medium"]`.

### Коды ошибок в ACK

Центр сохраняет код в `error_code` задания, описание — в `error`. Описание фиксировано
для кода (`_ERROR_MESSAGES` в `engine.py`), не называет уровень ловушки и не содержит
вывода Docker, конфигурации или паролей.
`runtime_state` failed ACK отражает наблюдение: `running` — только если наблюдается
работающий подтверждённый экземпляр (для stop — экземпляр результата: из истории, а
при reconcile — найденный; для start — ожидаемый центром), иначе `failed`. В таблице —
основные случаи; точные условия задают `engine.py` и `drivers/low.py`.

| Код | Когда возникает |
|---|---|
| `UNSUPPORTED_COMMAND` | Команда уровня, не настроенного на узле, или не start/stop; Docker не вызывается. |
| `UNSUPPORTED_PROFILE` | Драйвер не может перевести профиль при start. Low: несколько сервисов одного вида, недопустимый баннер TCP, управляющие символы в тексте HTTP. Medium: не один ssh-сервис, баннер не строка идентификации SSH, нет учётных записей, пароль с символом, который userdb Cowrie считает шаблоном. |
| `INSTANCE_MISMATCH` | Экземпляр, ожидаемый центром, история агента или наблюдение не совпадают с известными UUID назначения. |
| `INVALID_STATE` | Контейнер в слоте другого назначения или уровня, с неполной идентичностью либо не совпадает с сохранённой попыткой при recovery. |
| `START_FAILED` | `docker run` завершился ошибкой, параметры запуска недопустимы или состояние экземпляра на хосте нельзя подготовить (каталог журнала Low, каталог экземпляра с конфигурацией и userdb Medium). |
| `HEALTHCHECK_FAILED` | Ловушка не ответила ожидаемо на опубликованных портах в пределах срока запуска: Low — баннер TCP или HTTP 200, Medium — строка идентификации SSH. |
| `CLEANUP_FAILED` | Не удалось удалить контейнер (отказ мягкой остановки сам по себе кода не даёт): при stop, при удалении остатка прежнего запуска перед start и при уборке после неудачного start, в том числе когда Docker недоступен именно при удалении. Недоступный Docker при наблюдении даёт `BACKEND_UNAVAILABLE`. |
| `BACKEND_UNAVAILABLE` | Docker недоступен для наблюдения или операции. |
| `RECOVERY_UNCERTAIN` | После рестарта start в стадии executing не нашёл контейнер своей попытки. |
| `START_UNCONFIRMED` | После start нет работающего контейнера этой попытки с целевой revision. |
| `STOP_UNCONFIRMED` | После stop контейнер слота всё ещё существует. |
| `PORT_STILL_OPEN` | Контейнера нет, но освобождение опубликованных портов не подтверждено. |

В ACK не попадают:
- `CLOCK_SKEW` и `CONFIG_MISMATCH` — процесс останавливается до мутаций, центр по
  сроку переводит задание в expired, а назначение в unknown;
- `LEASE_LOST` — lease закрыт, ACK старым token не отправляется, запись ждёт
  повторной выдачи;
- `EXECUTION_DEADLINE_CHANGED` (центр изменил hard deadline) и
  `LEASE_RESPONSE_MISMATCH` (ответ renew относится к другой команде) — во время
  операции закрывают lease, а при первом renew до неё останавливают процесс.

Интерфейс, который переводит известные коды драйвера фиксированными фразами
(`specs/frontend.md`), для кодов `INVALID_STATE` и `CLEANUP_FAILED` должен учитывать
расширенный смысл из этой таблицы; это согласуется с владельцем фронтенда.

## Регистрация и heartbeat

Отдельная точка входа enroll использует существующий POST /agent/v1/enroll без
Authorization, одноразовый HF_ENROLLMENT_TOKEN и объявленные уровни узла. Уровни
задаются повторяемым `--level` (по умолчанию только `low`), приводятся к каноническому
порядку и проверяются по набору уровней, для которых в агенте есть драйвер: Medium
объявляется явно, потому что требует заранее доставленного образа Cowrie и каталога
состояния именно на этом хосте. Она сохраняет
agent_token в новый файл через эксклюзивное создание, режим 0600 на POSIX и fsync;
ссылки и существующий файл отвергаются без перезаписи. Исполнитель принимает один
источник Bearer: HF_AGENT_TOKEN или --token-file. Файл должен быть обычным, без
ссылок, с закрытыми правами и текущим владельцем на POSIX; Windows ACL проверяет оператор.

POST /agent/v1/heartbeat с Bearer отправляется сразу и каждые 10 секунд отдельной
задачей, в том числе во время долгой Docker-операции. Ошибки содержат безопасный код
и повторяются; несовпадение capabilities узла с уровнями, настроенными в этом процессе,
выдаёт предупреждение и автоматически не исправляется: центр может присылать команды
уровня, который процесс не исполняет. Проверяются
ответы enroll и HostRead по действующим control-plane/OpenAPI без изменения API.

Ошибки выполнения содержат русский текст по коду, без вывода Docker и конфигурации.
CLI повторяет только NETWORK_ERROR, HTTP >=500 и 409 LEASE_EXPIRED/LEASE_MISMATCH;
статус >=500 проверяется раньше кода тела. Остальные ошибки прекращают polling,
включая INVALID_RESULT при расхождении устойчивого результата.

## Приёмка

- HTTP claim/renew/ACK: Bearer, ограничения ответа/таймаута, запрещённые redirects,
  проверка полей и сроков, безопасные ошибки, соответствие OpenAPI. Таймаут общий на
  весь запрос: по сроку сторожевой таймер разрывает сокет и при медленном чтении тела,
  включая chunked, держа собственную ссылку на сокет, поэтому поток не остаётся работать
  даже после того, как urllib передал сокет ответу и обнулил connection.sock; HTTP идёт
  в отдельном пуле потоков и не занимает пул Docker-операций.
- Enroll → heartbeat → online с объявленными capabilities → start → HTTP 200 → stop →
  порт освобождён; heartbeat продолжается независимо от исполнения команд.
- Medium: start и stop проходят claim/renew/ACK с подтверждением состояния; метка
  уровня у контейнера своя; оставшийся после stop контейнер даёт STOP_UNCONFIRMED,
  занятый после удаления порт — PORT_STILL_OPEN без остановки чужого процесса;
  команда medium на узле без настроек Medium и действие reset дают
  UNSUPPORTED_COMMAND без вызовов Docker. Настоящий Cowrie в этих тестах не
  запускается: подмена backend отвечает строкой идентификации SSH
  ([runtime-drivers.md](runtime-drivers.md), раздел 8).
- Проверены эксклюзивная запись/права/ссылки файла токена и безопасные описания ошибок.
- Start → настоящий LowService → ACK → stop, отдельно интеграция с FastAPI/PostgreSQL
  и Docker в CI/на согласованном сервере; подмена backend явно обозначается.
- Повтор terminal команды, потеря ответа ACK и рестарт не повторяют run.
- Stop и ошибки увеличивают generation, история revision/instance переживает рестарт.
- Потеря lease во время задержанного run не разрешает remove/следующий run;
  повторная выдача сверяет контейнер и выполняет health check.
- Hard deadline не продлевается, expired операция не блокирует отдельный stop из unknown.
- Проверены конфликт ID, stale generation, неожиданная идентичность контейнера,
  ошибки диска, взаимное исключение процессов и отключение сети.
- Неудачный start с поздно появившимся контейнером или недоступным inspect сообщает
  управляемую идентичность; прежний известный контейнер не становится фантомной новой
  попыткой. Последующий обычный stop убирает его (с подменой и на настоящем центре).
- Временная ошибка renew не закрывает lease, отказ центра закрывает; спешащие часы
  дают CLOCK_SKEW без Docker-операций.
- Настоящий HttpCommandClient ↔ uvicorn ↔ PostgreSQL: lease истёк до ACK, повторная
  выдача, тот же ACK, ровно один run; loopback-центр не идёт через прокси окружения.

## Связка с телеметрией

Новый Low JSONL пока не поддерживается адаптером Event v1. Для Димы предоставляется
генератор реальных строк `python -m infra.runtime.sample_low_journal` и отдельный
handoff с connection/HTTP/TCP/ротацией/усечением. Предложения из ответа телеметрии
не считаются подтверждением реализации: тип TCP request (`tcp.request`), source_seq, UID/GID,
cleanup и квоты требуют окончательного согласования. Менять Event v1 в этом PR
не требуется.

Medium пишет собственный журнал Cowrie (`cowrie.json`) и TTY-записи в каталог
экземпляра на хосте `<state_root>/<deployment_id>/<instance_id>/state/`. Исполнитель
только создаёт этот каталог и ничего из него не читает: формат и способ чтения с
участником 4 не согласованы, поэтому интеграция Medium с телеметрией не заявляется, а
примеры Cowrie/TTY остаются следующим этапом. Каталоги прежних экземпляров не
удаляются: признак «журнал прочитан» тоже требует согласования.
