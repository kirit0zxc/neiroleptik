# Предложения контрактов runtime: требуется согласование

Таблица, действия и lifecycle ниже — предложения участникам 2 и 4, не утверждённый
HTTP API. Решения по доставке команд, которые уже принял владелец backend, собраны в
разделе «Ответ владельца backend»; это согласованная основа, но ни центр, ни агент её
ещё не реализуют, а точные схемы в `contracts/openapi.json` не внесены. Общий OpenAPI
оформляется владельцем backend, без дублирующих контрактов.

| Поле | Предложение |
|---|---|
| schema_version | Версия формата, отдельно от версии конфигурации |
| revision / applied_revision | Желаемая / последняя успешно проверенная конфигурация |
| command_id | UUID команды, одинаковый при повторной доставке |
| expected_generation | Поколение слота, к которому адресована команда |
| generation | Монотонный номер воплощения слота |
| instance_id | UUID экземпляра, меняется при создании нового overlay |
| event_id / artifact_id | Стабильные идентификаторы повторной доставки |

Предлагаемые действия: start, stop, reset; параметры только из разрешённой схемы.
Ни профиль, ни команда не содержат исполняемой shell-строки. Ошибки:
COMMAND_CONFLICT, STALE_GENERATION, BUSY, NETWORK_CHECK_FAILED,
EVIDENCE_SEAL_FAILED, STORAGE_FULL, RECOVERY_REQUIRED.

Lifecycle: stopped → preparing → ready → active → sealing → resetting → ready.
Failed всегда закрывает вход. Stop/TTL заканчиваются остановкой, без автоматического
нового lease. Restart и повтор команды не продлевают TTL и не создают поколение.
Состояние VM, связь с центром и состояние доставки показываются отдельно.

На D1 требуется договор участника 4 о `seal(instance_id)`: завершить источники,
устойчиво сохранить файлы и manifest, подтвердить локальную очередь доставки.
Manifest связывает artifact_id, instance_id, session_id, тип, размер, SHA-256,
завершённость и локальное хранилище. Успешный локальный seal разрешает reset;
ACK центра разрешает удаление локальной доставленной копии по политике хранения.
Ошибка seal запрещает уничтожать исходные доказательства/overlay.

События передаются как минимум один раз; центр устраняет дубликаты по event_id.
Поздние события и token старого instance не перепривязываются к новому.
Honeytoken в демонстрации открывает отдельный тестовый клиент после извлечения URL
из легенды; исходящий доступ из guest для этого не требуется.

## Ответ владельца backend (09.10.2026)

Статус: согласовано как основа, **не реализовано**. Ниже — пересказ решений владельца,
а не описание работающего API: ручек `/agent/v1/commands/*` в центре и клиента команд в
агенте пока нет. Точные схемы фиксирует владелец backend в `contracts/openapi.json`; до
этого клиент команд в runtime не реализуется.

- Команды доставляются исходящим HTTPS-опросом агента: `POST /agent/v1/commands/claim`,
  `POST /agent/v1/commands/{command_id}/renew`, `POST /agent/v1/commands/{command_id}/ack`;
  опрос примерно раз в 5 секунд со случайным сдвигом.
- `command_id` — глобально уникальный UUID, команда закреплена за узлом. Lease 60 секунд,
  продление каждые 20 секунд, команда несёт выданный центром `lease_token`; просроченное
  подтверждение не меняет deployment. Срок получения команды 5 минут, срок выполнения
  5 минут для Low/Medium и 15 минут для High (отдельно от TTL самой ловушки High).
- Единый ACK подтверждает результат операции и применение конфигурации: `deployment_id`,
  запрошенная `revision`, фактическая `applied_revision`, `generation`, `instance_id`
  (может быть null, если экземпляр не создан), результат, состояние ловушки
  (`running` для успешных start/reset, `stopped` для stop, `failed` при ошибке) и
  ошибка `{code, message}`. Повтор того же ACK возвращает сохранённый ответ, другой
  результат той же команды — 409 `ACK_CONFLICT`. Центр сохраняет ACK и обновляет
  deployment одной транзакцией; только после этого UI показывает running. При ошибке
  новая ревизия не считается применённой.
- `generation` выдаёт центр; несовпадающий `expected_generation` — `STALE_GENERATION` без
  выполнения. На один deployment одновременно допускается одна изменяющая команда.
- Агент хранит журнал команд на диске: повтор завершённой команды возвращает прежний
  результат, выполняющаяся продолжается, после сбоя сначала проверяется фактическое
  состояние экземпляра. Локальная основа для этого — `CommandJournal` из
  [runtime-d1.md](runtime-d1.md); к доставке команд он ещё не подключён.
- Ограничения Low (не более одного `tcp` и одного `http`, разные порты, баннер TCP
  1–200 печатных ASCII без перевода строки) центр проверяет при создании и обновлении
  профиля; драйвер сохраняет защитную проверку `UNSUPPORTED_PROFILE`. `banner` для
  `http` — однострочный текст страницы-заглушки (`text/plain; charset=utf-8`).
- `capabilities` содержат только проверенные на узле возможности (сейчас `["low"]`);
  центр отклоняет размещение уровня, которого нет в capabilities.
- Образ Low собирается и публикуется GitHub Actions в GHCR после ревью и слияния;
  в deployment закрепляется digest `sha256:…`, агент запускает именно его. Локальная
  сборка на runtime-хосте — только для разработки. Сервер runtime готовит владелец.

## Открытые вопросы

1. Участник 4: схема Event, контракт seal, неполные передачи, квоты, центральный ACK,
   формат журнала Low для сборщика — [low-journal-v1.md](low-journal-v1.md).
2. Участники 1 и 2: поля состояния ловушки для UI (состояние, healthy, instance_id,
   применённая ревизия, ошибка, состояние VM, срок жизни) и где центр их отдаёт.

Минимальные примеры и контрактные тесты добавляются после согласования схем.
