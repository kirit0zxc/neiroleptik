# Требования следующего этапа телеметрии

Статус: проект внутренней спецификации и тестового стенда. Основание — два скриншота пользователя от 11.10.2026 и актуальные границы PR26. Имена новых внутренних классов и методов выбираются при реализации; внешние договорённости этим документом не утверждаются.

## Атомарная конверсия raw в очередь

Вход: сохранённая проверенная raw-запись, доверенная привязка источника, внедрённый mapper и явно заданные лимиты шага. Чтение не меняет исходные bytes, raw-checkpoint или файлы Low. Mapper возвращает один валидный Event либо явный результат «служебная строка без события»; исключение не означает пропуск.

Ledger хранит устойчивую идентичность исходной позиции, результат обработки и идентичность/контрольное представление результата, достаточные для обнаружения несовместимого повтора. Источник включает agent/deployment/instance/revision и journal_id/offset по существующей raw-модели. Конкретную схему описать до реализации. Нельзя использовать один путь файла или только offset как глобальную идентичность.

Для новой event-записи pending и ledger фиксируются одной SQLite-транзакцией на одном соединении. Для служебной строки атомарно сохраняется завершённый результат без pending. Ошибка mapper, валидации, квоты, INSERT или commit не оставляет отметку успешной обработки. Отдельный commit в существующем append до записи ledger недопустим; нужен совместимый внутренний транзакционный интерфейс без изменения поведения прежних вызовов.

После commit повтор той же позиции не вставляет Event заново, в том числе после ACK, карантина и перезапуска. Изменение исходного содержимого либо конфликт результата не перезаписывает прежнее доказательство. Версия mapper не является разрешением повторно отправить ранее обработанную позицию: повторная конверсия/миграция требует отдельного решения. Невалидный Event не создаёт pending или ledger.

Два потребителя одной позиции дают максимум одну конверсию в хранилище. Mapper не выполняет внешние побочные действия; потенциальный повтор вычисления при гонке безопасен. Шаг ограничен количеством записей/bytes, возвращает прогресс и безопасную причину остановки. Ошибки не содержат raw, пароли или SQL-содержимое. Cleanup ledger/raw/snapshots не добавляется.

Приёмка: атомарность, рестарт, конкурентность, сохранение результата после ACK, совместимость существующей spool и отсутствие production mapping.

## Интеграционное приложение Event PostgreSQL REST WS

Использовать существующие EventStorage, publisher, read adapter, history, catch-up, presenter и stream. Создать тестовую сборку приложения с явно внедрёнными зависимостями и настоящим PostgreSQL в изолированной схеме. Не регистрировать новые routes в рабочем create_app и не добавлять production-миграции.

Тестовый HTTP ingress принимает ограниченный batch по существующему согласованному ACK-контракту, нормализует элементы и вызывает реальный storage. Его маршруты, тестовая авторизация и проверки identity должны быть явными; это не доказательство production authorization. ACK формируется только после успешного commit. Нельзя подменять SQL-хранилище коллекцией в памяти или обходить publisher при проверке потока.

Повтор того же события подтверждается без новой записи/outbox/publication; другой оригинал того же ID даёт конфликт, хорошие соседние элементы обрабатываются по контракту. Publisher публикует только committed данные и переживает перезапуск. REST и WS видят один committed журнал; догрузка и live не теряют события. Проверять пару agent_id/event_id и десятичные stream_seq выше 2^53.

Внедрить явно тестовую политику маскирования, сохраняющую оригинал неизменным. Проверки cookie/Origin/revoke должны использовать существующие сервисы доступа, если они входят в собираемый router. Тестовая конфигурация не ослабляет рабочие Settings.

Приёмка: настоящий HTTP sender → тестовый ingress → PostgreSQL → publisher → REST/WS, включая потерю ответа после commit. Отдельно отметить отсутствие браузерного и production Low-прогона.

## Нагрузка и пределы дисковой очереди

Воспроизводимый ограниченный стенд принимает количество/размер событий, частоту входа, длительность отказа и скорость/режим приёмника. Отчёт содержит окружение, версии, seed, объём базы/WAL/SHM, свободное место, максимум backlog, скорость поступления и досылки, время очистки pending и задержки с определением границ измерения.

Не обещать целевые throughput/p95 до замера. Отдельно считать размер BLOB и физический диск. Ошибки записи проверять fault injection/SQLite-лимитом; настоящий ENOSPC — только в ограниченном тестовом volume/образе, не заполнением системного диска. Симуляцию ошибки не выдавать за настоящий ENOSPC. После ошибки неподтверждённые данные сохранены, checkpoint/ledger не продвинуты ошибочно. Остановка ловушек и retention остаются на согласовании runtime.

## TTY на фиксированных образцах

До реальных Cowrie-образцов зафиксировать небольшой тестовый формат, его происхождение и версию. Если используется документированный формат движка, сверить его с официальным описанием конкретной версии. Не называть собственный fixture форматом Cowrie.

Конвертер принимает поток bytes и лимиты, возвращает упорядоченные фрагменты с временем/направлением и явными признаками неполноты/ошибок. Определить единицы времени, правила равных/обратных меток, Unicode и границы фрагментов. Не декодировать каждый сетевой кусок независимо, теряя разорванные UTF-8 символы. Учитывать EOF внутри header/payload, неизвестный тип, чрезмерную длину и некорректную кодировку без неограниченной памяти.

Терминальные последовательности не исполняются и не превращаются в HTML. Политика отображения управляющих символов должна быть явной. DTO остаётся внутренним; публичный replay согласуется отдельно. Совместимость с Cowrie и SFTP будет подтверждена после получения версии и настоящих журналов.

## Автоматическая приёмка

Скрипт создаёт детерминированный набор тестовых Event, фиксирует ожидаемые ID и canonical payload, отключает только тестовый канал доставки, накапливает очередь, восстанавливает канал и сверяет БД/REST/WS. Считать уникальность по agent_id/event_id; счётчика записей недостаточно. После рестартов и повтора сверять также payload и отсутствие повторных публикаций. Управление отказом не должно затрагивать сеть пользователя или общий стенд.

Сохранять машинно-читаемый итог, длительности и причины отказов, без секретов. Недоступный PostgreSQL/порт — явная ошибка или отдельно отмеченная непроведённая проверка, не зелёный результат. Настоящий Low подключается после утверждения mapping; синтетический сценарий не закрывает Low→UI.
